# 로봇공학 강의자료 — 작업 흐름

이 문서는 **어떻게 일하는가**를 정한다.
자료가 **어떻게 생겼는가**(블록 형식·문체·HTML 규칙)는 `_notes/강의자료_제작지침.md`에 있다.
두 문서는 겹치지 않는다. 서식이 궁금하면 그쪽을, 절차가 궁금하면 이쪽을 본다.

## 0. 무엇이 어디에 적혀 있나

먼저 볼 것은 맨 윗줄이다. 위에서 아래로 읽으면 큰 그림에서 세부로 좁혀진다.

| 파일 | 무엇이 들어 있나 | git |
|---|---|---|
| `_notes/강의계획_00_전체순서.md` | 30회차가 무엇인지 한 장 요약 | 미추적 |
| `_notes/강의자료_제작지침.md` | 블록 7종·문체·HTML 규칙 | 미추적 |
| `_notes/강의계획_1~4부_*.md` | 회차별 상세 계획 4개 | 미추적 |
| `_inbox/` | 노션에서 받은 원본 md 32개 + `figures/` 90장 | 미추적 |
| `examples/` | 코드·빌드 파일을 실제로 만들어 돌려 보는 곳 | 미추적 |
| `docker/` | 검증용 ROS 2 Jazzy 컨테이너 정의 (Dockerfile·compose) | **추적** |
| `l01.html` ~ `l30.html` | 배포되는 강의자료 | 추적 |
| `assets/lecture.css` | 공용 스타일 | 추적 |

`_notes/`·`_inbox/`·`examples/`는 git이 추적하지 않는다. 다른 컴퓨터로 옮길 때는 폴더째 복사해야 한다.

## 1. ROS는 호스트에 깔지 않는다 — 전부 도커 컨테이너 안에서 돈다

서버는 **우분투 22.04**다. ROS 2 Jazzy는 우분투 24.04를 요구하므로 호스트에 그냥 깔리지 않는다.
그래서 **호스트는 건드리지 않고, 우분투 24.04 + ROS 2 Jazzy 컨테이너 하나를 만들어 그 안에서 전부 실행한다.**

| 어디서 | 무엇을 | 왜 |
|---|---|---|
| **호스트 (우분투 22.04)** | 파일 편집, git·gh, HTML 쓰기 | 편집기와 저장소는 호스트에 있는 게 편하다 |
| **컨테이너 (우분투 24.04 + Jazzy)** | 빌드, 실행, `ros2` 명령, RViz2 | 호스트를 ROS 설치로 더럽히지 않는다 |

정의는 `docker/Dockerfile`과 `docker/compose.yaml`에 있다. 이 두 파일은 git이 추적한다.
호스트의 `examples/`가 컨테이너의 `/work`에 그대로 붙으므로, **편집은 호스트에서 하고 빌드는 컨테이너에서 한다.**

### 세션을 열면 먼저 이 시스템이 무엇인지 확인한다

```bash
cat /etc/os-release | head -2                    # 호스트 배포판
grep -qi microsoft /proc/version && echo "WSL" || echo "네이티브/서버"
docker --version; docker compose version         # 도커가 있나
docker images | grep robotics-jazzy              # 이미지가 이미 만들어져 있나
echo "DISPLAY=$DISPLAY"                          # GUI 연결 여부
ip -4 addr | grep inet | grep -v 127.0.0.1       # 네트워크 대역
```

**출력을 그대로 붙이지 말고 "무엇을 할 수 있고 무엇을 못 하는가"로 옮겨 보고한다.**

- 도커가 없다 → 아무 실습도 못 한다. 설치할지 사용자에게 먼저 묻는다.
- 이미지가 없다 → 아래 순서로 만든다. 처음 한 번은 20~40분 걸린다.
- `DISPLAY`가 비었다 → RViz2·Gazebo 그림을 못 찍는다. 해당 자리를 표시해 두고 넘어간다.
- 네트워크 대역이 터틀봇과 다르다 → 실물 로봇 회차(27~30회)는 여기서 검증할 수 없다.

### 컨테이너를 만들고 들어가는 법

```bash
cd robotics/docker
docker compose build                 # 이미지 만들기 (처음 한 번)
xhost +local:docker                  # GUI를 쓸 때만, 호스트에서 한 번
docker compose run --rm ros          # 셸 열기. /work 가 곧 robotics/examples
```

컨테이너 안에서는 `source /opt/ros/jazzy/setup.bash`가 이미 걸려 있어 `ros2` 명령이 바로 먹는다.
빌드는 `/work`에서 `colcon build`로 한다. 나온 산출물은 호스트의 `examples/`에도 그대로 보인다.

### 도커 이미지가 곧 「ROS 2 설치」 회차의 자료다

`Dockerfile`에 적힌 설치 명령은 학생이 자기 WSL에서 칠 명령과 같다.
**이미지 빌드가 성공했다는 것은 그 명령들이 실제로 동작한다는 증거다.**
설치 회차 자료를 쓸 때는 `Dockerfile`을 원본으로 삼고, 명령을 고치면 이미지를 다시 빌드해서 확인한다.

### 서버와 WSL은 맡는 일이 다르다

| 어디서 | 무엇을 | 왜 |
|---|---|---|
| **우분투 서버 (주 작업장)** | 자료 28편 제작, C++·ROS 실습 대부분, RViz 그림 | 도커로 Jazzy가 돌고 `tmux`로 세션이 살아남는다 |
| **WSL (보조)** | 학생이 보는 설치·GUI 화면 확인, 실물 터틀봇 통신 | 학생은 도커가 아니라 WSL에 직접 깐다. 화면이 다르다 |

**학생은 도커를 쓰지 않는다.** 자기 WSL에 직접 설치한다.
그래서 서버 컨테이너에서 잘 돌았다고 자료가 끝난 것이 아니다. 설치·GUI 관련 화면은 WSL에서 한 번 더 본다.

서버에서 작업하다 WSL을 봐야 하는 자리가 나오면 **자료를 멈추지 말고** 그 자리에
`<!-- TODO: WSL 확인 -->` 주석을 남기고 계속 쓴다. 나중에 WSL에서 그 주석만 훑어 한 번에 처리한다.

## 2. 자료에 들어가는 명령어와 코드는 전부 직접 실행해서 확인한다

**이 강의의 자료에는 검증하지 않은 명령어를 넣지 않는다.** 가장 중요한 규칙이다.
학생이 그대로 따라 쳤을 때 안 되는 자료는 없느니만 못하다.

- 명령어는 컨테이너 안에서 실제로 실행하고, **실제로 나온 출력을 자료에 붙인다.**
  기억이나 추측으로 출력을 지어내지 않는다. 출력이 길면 잘라 쓰되 고쳐 쓰지 않는다.
- 코드는 `examples/` 안에서 **빌드하고 실행까지 시킨 뒤** 자료에 옮긴다.
  컴파일만 되고 실행 결과를 안 본 코드는 검증한 것이 아니다.
- **실패도 자료가 된다.** 흔히 나는 오류 메시지는 그대로 받아 적어 함정 블록(`_notes/강의자료_제작지침.md` 3-3절)에 넣는다.
- 이 시스템에서 도저히 실행할 수 없는 것(실물 로봇, GUI 없음)은
  `<!-- TODO: 미검증 — 이유 -->` 주석을 남기고, 무엇을 못 봤는지 사용자에게 보고한다.

예를 들어 `ros2 topic hz /scan`의 출력을 자료에 쓰려면, 라이다가 실제로 돌고 있는
시스템에서 그 명령을 쳐서 나온 숫자를 써야 한다. "보통 초당 5회쯤 나온다"고 쓰지 않는다.

## 3. 코드는 자료 안이 아니라 examples 폴더에서 만든다

파일을 여러 개 만들어야 하는 작업(C++ 프로젝트, CMake 빌드, ROS 2 패키지)은
`robotics/examples/` 안에 실제 폴더를 만들어 거기서 한다. 자료 HTML에 코드를 바로 쓰지 않는다.

```
robotics/examples/
├── l06_class_template/          # 회차번호 두 자리 + 짧은 영문 이름
│   ├── CMakeLists.txt
│   ├── main.cpp
│   └── build/                   # 빌드 산출물도 여기 (전부 미추적)
└── l20_topic_pubsub/            # ROS 2 패키지도 같은 규칙
    ├── package.xml
    └── src/
```

- 폴더 이름은 `l{회차}_{영문_요약}`으로 짓는다. 어느 회차 코드인지 나중에 찾을 수 있어야 한다.
- 빌드 산출물(`build/`, `install/`, `log/`)을 지우지 않아도 된다. 폴더 전체가 git 미추적이다.
- 돌려서 확인이 끝나면 **소스를 자료 HTML로 옮긴다.** 옮길 때 줄이거나 고치면 다시 돌려 확인한다.
- 자료의 코드와 `examples/`의 코드가 갈라지면 `examples/` 쪽이 맞다. 실제로 돌아간 것이 그쪽이다.
- **이 폴더는 컨테이너의 `/work`에 그대로 붙어 있다.** 호스트에서 파일을 만들고, 컨테이너 셸에서 빌드·실행한다.
  ROS 2 패키지는 `/work`에서 `colcon build --packages-select {패키지}`로 빌드한다.

## 4. 한 회차를 만드는 순서

0. **브랜치를 확인한다.** 이 요청의 브랜치가 이미 있으면 그대로 쓰고, 없으면 만든다.
   **자료 한 편마다 브랜치를 새로 파지 않는다.** 브랜치와 PR은 사용자가 한 번에 시킨 일 단위다 (루트 `CLAUDE.md` 2절).
1. `_notes/강의계획_{해당 부}.md`에서 그 회차 계획을 읽는다. 무엇을 다루고 몇 분인지 확인한다.
2. `_inbox/`에 대응하는 원본 md가 있으면 읽는다. 재활용할 것과 버릴 것을 가른다.
3. `_notes/강의자료_제작지침.md`에서 이 회차에 쓸 블록 종류를 정한다.
4. 코드·명령어를 `examples/`에서 만들고 **돌려서 확인한다.** (2·3절)
5. 이미 만든 `l13.html`(코딩형)이나 `l18.html`(명령어형)을 본으로 삼아 HTML을 쓴다.
6. `index.html`에 링크를 추가한다. **빠뜨리면 학생이 자료를 찾지 못한다.**
7. `../prompts.md`에 요청 프롬프트를 기록한다. 형식은 루트 `CLAUDE.md`의 「프롬프트 기록 규칙」을 따른다.
8. 커밋한다. 여기서 끝이다. **push도 PR도 병합도 하지 않는다.**
   요청받은 일이 전부 끝나면 그때 사용자에게 병합을 권하고, "머지해줘"를 들으면 한 번에 처리한다 (루트 `CLAUDE.md` 2절).

## 5. 커밋 전에 세 가지를 확인한다

- **개인정보** — 학번·이름·점수·제출물이 섞이지 않았나. 이 저장소는 전부 공개된다.
- **미검증 표시** — `grep -rn "TODO" robotics/*.html`로 남은 것을 세고, 사용자에게 몇 개인지 알린다.
- **링크** — 새로 만든 자료가 `index.html`에 들어갔나.

## 6. 아직 정하지 않은 것

작업 중 이 항목에 걸리면 혼자 정하지 말고 사용자에게 묻는다.

- 터틀봇3가 Jazzy를 지원하는가 — 배포판은 **Jazzy로 확정**했다(2026-08-28, 기존 자료의 Iron은 2024-11 지원 종료).
  다만 ROBOTIS의 터틀봇3 패키지가 Jazzy에서 도는지는 컨테이너에서 직접 확인해야 한다. 안 되면 소스 빌드 여부를 묻는다.
- 콘 트랙 규격 실측값 — 콘 간격과 트랙 폭
- 주행 중 콘이 쓰러졌을 때 처리 규칙
