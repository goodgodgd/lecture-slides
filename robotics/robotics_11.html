복사와 이동 — 값을 넘길 때 무슨 일이 일어나나

오늘 답할 질문
  1. 함수에 값을 넘길 때 정확히 무슨 일이 일어나나?
  2. "복사가 비싸다"는 말은 얼마나 비싸다는 뜻인가?
  3. std::move는 무엇을 옮기나? 옮기고 난 원본은 어떻게 되나?
  4. 반환할 때도 move를 붙이면 더 빨라지나?

실제 회사의 C++ 코드 1천만 줄을 1년간 추적한 연구가 있다. 거기서 나온 항목 중 1위가 오늘 다루는 것이다. AI가 짠 코드는 사람이 짠 코드보다 복사·할당 오버헤드가 1.39배 많았다. 같은 연구에서 정확성·안전성 문제는 오히려 사람의 0.94배였다.

두 숫자를 나란히 놓으면 이 회차의 논지가 나온다. AI는 틀린 코드를 더 많이 만들지 않는다. 둔한 코드를 만든다. 둔한 코드는 컴파일되고, 실행되고, 맞는 답을 낸다. 그래서 아무도 지적하지 않는다. 학생이 검사 목록으로 훑지 않으면 그대로 로봇에 올라간다.

오늘은 그 「둔함」이 어디서 생기는지 딱 하나만 판다. 값을 넘길 때 사본이 만들어진다는 것, 그리고 그 사본이 대부분 아무 이득이 없다는 것이다. 말로 하면 뻔해 보이므로 두 가지 방법으로 실제로 잰다 — 복사 횟수와 시간이다.

한 장 요약 — 학기가 끝나도 이 표만 남으면 된다 🔴 사람이 한다

무엇을 먼저 볼지: 맨 윗줄 하나가 오늘의 결론이다. 나머지 네 줄은 전부 첫 줄의 예외다.

이렇게 쓴다언제수준
void f(const T & x) 기본값. 읽기만 할 때. 고민되면 이것부터 놓는다 [요구]
void f(T x) 어차피 사본이 필요할 때. 또는 int·float처럼 8바이트 이하의 작은 값 [판단]
void f(T & x) 원본을 고쳐야 할 때. 함수가 결과를 인자에 써 넣을 때 [판단]
std::move(x) 사본이 필요하지만 원본을 다시 안 쓸 때. 알맹이만 넘긴다 [요구]
return std::move(x) 쓰지 않는다. 붙이면 오히려 컴파일러의 최적화를 막는다 [요구]
해석: 오늘 외울 것은 첫 줄 하나다. 받은 코드에서 함수 인자를 보고 "이거 왜 const &가 아니지?"를 물을 수 있으면 이 회차는 성공이다. 마지막 줄은 AI가 자주 하는 실수여서 따로 넣었다. 좋은 뜻으로 붙인 move가 손해가 되는 유일한 자리다.

① 라이다 콜백 한 번이 값 720개를 새로 만들고 있다 🔴 사람이 한다

언제 이게 필요해지나

라이다가 준 거리 값을 받아서 앞이 막혔는지를 판단하려고 한다. 터틀봇3의 라이다는 한 바퀴를 돌면서 360개의 거리 값을 한 묶음으로 보낸다. 이 묶음이 초당 5번 이상 들어온다.

여기서 중요한 사실이 하나 있다. 우리는 그 값을 읽기만 한다. 고치지도 않고, 따로 보관하지도 않는다. 읽고 판단하고 버린다.

오늘 쓸 그릇의 이름부터 정해 둔다. 라이다 메시지를 흉내 낸 것이다.

struct ScanMsg {
  std::vector<float> ranges;   // 거리 값 360개가 들어 있다
};

실제 ROS 2 코드에서는 이 자리에 sensor_msgs::msg::LaserScan이라는 긴 이름이 온다. 모양과 성질은 같다. 오늘은 이름이 짧은 ScanMsg로 쓴다.

AI가 보통 주는 코드 🔴
void scan_callback(ScanMsg msg)                   // ① 값으로 받음
{
  std::vector<float> ranges = msg.ranges;         // ② 또 복사
  float front = ranges.at(0);                     // 정면 거리
  // ... 앞이 막혔는지 판단한다
}

무엇이 문제인가

이 코드는 컴파일되고, 실행되고, 맞는 값을 낸다. 그래서 코드 리뷰에서 그냥 넘어간다. 문제는 눈에 안 보이는 곳에 있다.

표시한 자리여기서 실제로 일어나는 일
① ScanMsg msg 함수가 시작될 때 float 360개짜리 사본이 하나 만들어진다. 부른 쪽의 원본은 그대로 있고, 함수 안에는 똑같은 것이 하나 더 생긴다
② std::vector<float> ranges = msg.ranges; 그 사본에서 또 360개를 복사한다. 이름을 짧게 쓰려고 한 줄인데 값이 통째로 복제됐다
둘을 합치면 메시지 하나가 들어올 때마다 값 720개를 새로 만든다. 초당 5번이면 초당 3,600개다

그리고 결정적인 것은 이 일이 아무 이득 없이 일어난다는 점이다. 사본을 만드는 이유는 보통 원본을 건드리지 않고 고치기 위해서인데, 이 함수는 아무것도 고치지 않는다. 읽고 버린다. 비용만 있고 목적이 없다.

이렇게 말하면 된다

콜백에서 메시지를 값으로 받지 말고 const 참조로 받아 줘. 안에서 ranges도 새 변수에 복사하지 말고 const 참조로 별칭만 잡아 줘.
받은 코드
void scan_callback(const ScanMsg & msg)           // ① 참조로 받음 — 사본이 없다
{
  const std::vector<float> & ranges = msg.ranges; // ② 이름표만 하나 더 붙였다
  float front = ranges.at(0);                     // 정면 거리
  // ... 앞이 막혔는지 판단한다
}

🆕 이 코드에서 처음 나오는 것

std::vector<float>
같은 종류의 값을 여러 개 담는 표준 그릇이다. 여기서는 거리 값 360개가 이 안에 들어 있다. 오늘은 "값이 잔뜩 든 상자"로만 보면 된다. 그릇 자체를 다루는 법은 따로 있다.
ranges.at(0)
몇 번째 값인지를 주고 꺼낸다. 여기서는 정면 방향의 거리를 꺼냈다. 범위를 벗어난 번호를 주면 그 자리에서 오류를 낸다 — 조용히 이상한 값을 주지 않는다. 검사 없이 빠르게 꺼내는 ranges[0]도 있다.
ranges.size()
지금 그 안에 값이 몇 개 들어 있는지 알려 준다. 오늘은 이 숫자가 360에서 0으로 바뀌는 장면을 보게 된다 — 그것이 이 회차의 함정이다.

제대로 다루는 곳: 12회(컨테이너 — vector·array·reserve)

쓸 때 / 안 쓸 때 — 이 표가 오늘의 결론이다

무엇을 먼저 볼지: 첫 줄이 기본값이고 나머지 두 줄은 예외다. 예외를 고를 이유가 없으면 첫 줄이다.

이렇게 받는다언제왜
const T & 기본값. 함수가 값을 읽기만 할 때 사본이 안 만들어진다. const가 붙어 있어 원본을 못 고친다는 것이 함수 이름 옆에 적혀 있는 셈이다
T (값) 어차피 사본이 필요할 때 (보관하거나, 받아서 고쳐 쓸 때).
또는 int·float·bool처럼 작은 값		 작은 값은 참조로 받는 것이 오히려 손해다. 참조도 결국 8바이트짜리 주소를 넘기는 일이기 때문이다
T & 원본을 고쳐야 할 때 결과를 인자에 써 넣는 함수다. 부르는 쪽에서 값이 바뀔 수 있다는 것을 알아야 하므로 함부로 쓰지 않는다

기준선은 대략 포인터 하나의 크기, 즉 8바이트다. 이보다 크면 참조를 생각하고, 이보다 작으면 그냥 값으로 받는다. 말로만 하면 감이 안 오므로 실제로 재 봤다. 

$ g++ -std=c++17 -O2 -o type_size type_size.cpp && ./type_size
포인터 하나            :  8 바이트
int                    :  4 바이트
float                  :  4 바이트
double                 :  8 바이트
std::string            : 32 바이트 (+ 글자는 따로)
std::vector<float>     : 24 바이트 (+ 값 360개는 따로 1440 바이트)
ScanMsg                : 24 바이트 (+ 값 360개는 따로)
해석: std::vector<float>가 24바이트라는 것에 속으면 안 된다. 이 24바이트는 「값이 어디 있는지 적어 둔 쪽지」의 크기이고, 실제 값 360개는 따로 1,440바이트를 차지한다. 그리고 복사할 때는 쪽지가 아니라 1,440바이트를 통째로 새로 만든다. int는 4바이트라 8바이트보다 작다 — const int &로 받는 것은 오히려 손해다. 잰 곳: 컨테이너(우분투 24.04.4, g++ 13.3.0 -O2).

한 줄 점검

받은 코드에서 메시지·문자열·배열을 값으로 받는 함수가 있나? 있다면 그 함수가 원본을 고치는가?

② 복사를 세어 보면 1회와 0회다 🔴 사람이 한다

"복사가 일어난다"는 말은 화면에 아무것도 안 뜬다. 그래서 믿기 어렵다. 복사를 눈으로 보는 방법이 하나 있다. 복사가 일어날 때 숫자를 하나 올리게 만드는 것이다.

C++에는 "이 객체가 복사될 때 실행되는 함수"가 있다. 거기에 세는 코드를 한 줄 넣으면 된다. 아래가 그 코드다. 오늘 나오는 두 프로그램 중 첫 번째다.

count_copies.cpp — 복사가 몇 번 일어나는지 센다
#include <iostream>
#include <vector>

int g_copy = 0;
int g_move = 0;

struct ScanMsg {
  std::vector<float> ranges;

  ScanMsg() : ranges(360, 1.0f) {}
  ScanMsg(const ScanMsg & o) : ranges(o.ranges) { ++g_copy; }                 // 복사
  ScanMsg(ScanMsg && o) noexcept : ranges(std::move(o.ranges)) { ++g_move; }  // 이동
  ScanMsg & operator=(const ScanMsg &) = delete;
};

// AI가 흔히 주는 모양 — 값으로 받고, 안에서 또 복사한다
float callback_by_value(ScanMsg msg)
{
  std::vector<float> ranges = msg.ranges;      // 여기서 float 360개가 또 복사된다
  return ranges.at(0);
}

// 고친 모양 — 참조로 받고, 별명만 잡는다
float callback_by_ref(const ScanMsg & msg)
{
  const std::vector<float> & ranges = msg.ranges;
  return ranges.at(0);
}

int main()
{
  ScanMsg msg;

  g_copy = g_move = 0;
  callback_by_value(msg);
  std::cout << "값으로 받기      : ScanMsg 복사 " << g_copy << "회\n";
  std::cout << "                   (안쪽 vector 복사는 세지 않았는데도 이만큼이다)\n";

  g_copy = g_move = 0;
  callback_by_ref(msg);
  std::cout << "const 참조로 받기: ScanMsg 복사 " << g_copy << "회\n";

  std::cout << "\nstd::move 로 넘기면\n";
  g_copy = g_move = 0;
  ScanMsg tmp;
  ScanMsg taken(std::move(tmp));
  std::cout << "  복사 " << g_copy << "회, 이동 " << g_move << "회\n";
  std::cout << "  넘겨준 쪽 tmp.ranges.size() = " << tmp.ranges.size()
            << "  ← 껍데기만 남았다. 이제 tmp 를 읽으면 안 된다\n";
  std::cout << "  받은 쪽 taken.ranges.size() = " << taken.ranges.size() << "\n";
  return 0;
}

🆕 이 코드에서 처음 나오는 것

ScanMsg(const ScanMsg & o)
복사 생성자다. 이 객체가 복사될 때 자동으로 불린다. 평소에는 안 써도 컴파일러가 만들어 준다. 여기서는 몇 번 불리는지 세려고 손으로 썼다.
ScanMsg(ScanMsg && o)
이동 생성자다. 꺾쇠 두 개(&&)가 "이건 곧 버려질 임시 값이다"라는 표시다. 복사 생성자와 달리 알맹이를 새로 만들지 않고 가져온다.
noexcept
"이 함수는 예외를 던지지 않는다"는 약속이다. 이동 생성자에는 거의 항상 붙인다 — 이 약속이 없으면 표준 라이브러리가 안전을 위해 이동 대신 복사를 골라 버린다.
operator=(const ScanMsg &) = delete;
= delete는 "이 동작은 아예 못 쓰게 막는다"는 뜻이다. 여기서는 a = b 같은 대입까지 세면 이야기가 복잡해지므로 막아 두었다. 실수로 쓰면 실행이 아니라 컴파일에서 걸린다.

컨테이너에서 빌드해 돌린 결과다.

$ g++ -std=c++17 -O2 -o count_copies count_copies.cpp && ./count_copies
값으로 받기      : ScanMsg 복사 1회
                   (안쪽 vector 복사는 세지 않았는데도 이만큼이다)
const 참조로 받기: ScanMsg 복사 0회

std::move 로 넘기면
  복사 0회, 이동 1회
  넘겨준 쪽 tmp.ranges.size() = 0  ← 껍데기만 남았다. 이제 tmp 를 읽으면 안 된다
  받은 쪽 taken.ranges.size() = 360
해석: 첫 줄과 셋째 줄을 나란히 본다. 1회와 0회다. 그리고 이 1회는 ScanMsg 껍데기를 센 것이고, 그 안에서 일어난 float 360개 복사는 세지도 않았다. const & 두 글자가 그 전부를 없앤다. 잰 곳: 컨테이너(우분투 24.04.4, g++ 13.3.0 -O2).

③ 하는 일이 같은데 22배가 났다 🔴 사람이 한다

횟수를 셌으니 이번에는 시간이다. 횟수만으로는 "그래서 얼마나 손해인가"에 답할 수 없다. 두 코드가 하는 일을 완전히 똑같이 맞추고, 인자를 받는 방식만 다르게 해서 잰다. 비교 대상이 없으면 숫자 하나는 아무 뜻이 없기 때문이다.

copy_cost.cpp — 같은 일을 10만 번 시키고 시간을 잰다
#include <chrono>
#include <cstdio>
#include <vector>

struct ScanMsg { std::vector<float> ranges = std::vector<float>(360, 1.0f); };

float by_value(ScanMsg msg)             { return msg.ranges.at(0); }
float by_ref(const ScanMsg & msg)       { return msg.ranges.at(0); }

int main()
{
  const int LOOPS = 100000;
  ScanMsg msg;
  double sink = 0.0;

  auto t0 = std::chrono::steady_clock::now();
  for (int i = 0; i < LOOPS; ++i) { sink += by_value(msg); }
  auto t1 = std::chrono::steady_clock::now();
  const double v = std::chrono::duration<double, std::milli>(t1 - t0).count();

  t0 = std::chrono::steady_clock::now();
  for (int i = 0; i < LOOPS; ++i) { sink += by_ref(msg); }
  t1 = std::chrono::steady_clock::now();
  const double r = std::chrono::duration<double, std::milli>(t1 - t0).count();

  std::printf("값으로 받기      : %8.2f ms\n", v);
  std::printf("const 참조로 받기: %8.2f ms\n", r);
  std::printf("차이             : %.0f배  (%d회 기준, sink=%.0f)\n", v / r, LOOPS, sink);
  return 0;
}

🆕 이 코드에서 처음 나오는 것

std::chrono::steady_clock::now()
지금 시각을 찍는다. 중간에 뒤로 가지 않는 시계라서 시간을 재는 데 쓴다. 여기서는 반복문 앞뒤로 한 번씩 찍어 두 시각의 차이를 구했다.
std::chrono::duration<double, std::milli>(t1 - t0).count()
두 시각의 차이를 밀리초 단위 숫자로 바꾼다. std::milli가 "밀리초로 세라"는 뜻이고, count()가 숫자를 꺼낸다. 단위가 코드에 적혀 있어 나중에 초인지 밀리초인지 헷갈릴 일이 없다.
double sink
측정에만 쓰는 장치다. 결과를 아무 데도 안 쓰면 컴파일러가 계산 자체를 지워 버린다. 그러면 0초가 나온다. 그래서 결과를 sink에 더해 두고 마지막에 출력한다.
std::printf("%8.2f", v)
자릿수를 맞춰 출력한다. %8.2f는 전체 8칸, 소수점 아래 2자리라는 뜻이다. 여기서는 두 줄의 숫자를 세로로 맞춰 보이게 하려고 썼다.
$ g++ -std=c++17 -O2 -o copy_cost copy_cost.cpp && ./copy_cost
값으로 받기      :     3.66 ms
const 참조로 받기:     0.17 ms
차이             : 22배  (100000회 기준, sink=200000)
해석: 22배라는 배수에만 눈이 가지만, 한 번당으로 나눠 보는 것이 더 정직하다. 3.66밀리초를 10만 번으로 나누면 한 번에 0.037마이크로초다. 콜백 한 번만 보면 아무도 못 느낀다. 문제는 이런 자리가 코드 곳곳에 흩어져 있다는 것이고, 앞에서 본 연구의 1.39배가 바로 그 흩어진 것들을 합친 숫자다. 잰 곳: 컨테이너(우분투 24.04.4, g++ 13.3.0 -O2).
이 파일에서 불필요한 복사가 일어나는 자리를 전부 찾아서 표로 정리해 줘. 고치기 전에 어디가 왜 복사인지부터 알려 줘.

④ std::move는 "이제 안 쓸 거니 가져가라"는 말이다 🔴 사람이 한다

const &로 해결되지 않는 경우가 있다. 사본이 정말로 필요한 경우다. 콜백에서 받은 스캔을 클래스 안에 보관해 두고 다음 콜백에서 비교하려면, 함수가 끝나도 값이 살아 있어야 한다. 참조는 원본이 사라지면 같이 못 쓰게 된다.

그런데 여기에 조건이 하나 더 붙으면 이야기가 달라진다. 넘겨주는 쪽이 그 값을 다시 안 쓸 거라면, 알맹이를 새로 만들 이유가 없다. 있는 알맹이의 주인만 바꾸면 된다. 그 요청이 std::move다. 

ScanMsg tmp;                        // ranges 에 360개가 들어 있다
ScanMsg taken(std::move(tmp));      // "가져가라" — 알맹이의 주인이 taken 으로 바뀐다

🆕 이 코드에서 처음 나오는 것

std::move(x)
이름과 달리 아무것도 옮기지 않는다. "이 값은 이제 안 쓸 거니 가져가도 된다"고 표시만 해 준다. 실제로 알맹이를 가져가는 일은 이동 생성자가 한다. 여기서는 taken이 tmp의 360개를 새로 만들지 않고 넘겨받게 하는 데 썼다.

앞에서 돌린 count_copies의 마지막 부분이 이것을 그대로 보여 준다.

std::move 로 넘기면
  복사 0회, 이동 1회
  넘겨준 쪽 tmp.ranges.size() = 0  ← 껍데기만 남았다. 이제 tmp 를 읽으면 안 된다
  받은 쪽 taken.ranges.size() = 360

무엇을 먼저 볼지: 오른쪽 열의 "원본을 다시 쓰나"가 판단 기준이다.

상황이렇게 한다원본을 다시 쓰나
읽기만 한다const T &로 받는다. move가 필요 없다쓴다
보관해야 하는데 원본도 계속 쓴다그냥 복사한다. 복사가 정답인 자리다쓴다
보관해야 하고 원본은 버린다std::move로 넘긴다안 쓴다
함수에서 만들어 돌려준다아무것도 안 붙인다 (⑤절에서 본다)해당 없음
해석: std::move는 빠르게 만드는 주문이 아니다. "원본을 포기하겠다"는 선언이다. 포기할 생각이 없으면 붙이면 안 된다. AI에게 시킬 때도 "빠르게 해 줘"가 아니라 "이 변수는 이 줄 이후로 안 쓴다"고 말해야 맞는 코드가 온다.
이 함수에서 msg는 보관한 뒤로는 다시 쓰지 않아. 복사하지 말고 알맹이를 넘기도록 고쳐 줘. 넘긴 뒤에 msg를 읽는 코드가 남아 있으면 알려 줘.
⚠️ 가져간 다음 원본을 읽으면 — 크래시가 나면 차라리 낫다

std::move로 넘긴 뒤의 원본은 「비어 있지만 멀쩡한 물건」이 된다. 부서진 것이 아니다. 그래서 컴파일러도 막지 않고 실행도 멈추지 않는다. 다음 코드는 문법도 맞고 실행도 끝까지 된다. 

ScanMsg taken(std::move(tmp));       // 알맹이를 가져갔다

float sum = 0.0f;
for (size_t i = 0; i < tmp.ranges.size(); ++i) {     // 0바퀴 돈다
  sum += tmp.ranges[i];
}
float avg = sum / tmp.ranges.size();                  // 0으로 나눈다

실제로 돌려 본 결과다.

$ g++ -std=c++17 -O2 -Wall -o moved_from moved_from.cpp && ./moved_from
넘기기 전 tmp.ranges.size() = 360
넘긴 뒤   tmp.ranges.size() = 0
① 빈 것을 그대로 계산: 합 0.0, 평균 -nan  ← 크래시가 아니라 틀린 답이다
② tmp.ranges.at(0) 은 예외를 냈다: vector::_M_range_check: __n (which is 0) >= this->size() (which is 0)
가져간 쪽 taken.ranges.size() = 360  ← 값은 여기 있다

①이 무서운 쪽이다. 프로그램은 아무 일 없다는 듯 끝났고, 결과만 틀렸다. 평균이 -nan으로 나왔는데 이 값을 그대로 조향 각도로 쓰면 로봇은 이유를 알 수 없게 이상하게 움직인다.

②는 운이 좋은 쪽이다. at()은 범위를 검사하므로 그 자리에서 오류를 낸다. 틀린 답이 조용히 흘러가는 것보다, 그 줄에서 멈추는 편이 낫다.

규칙은 한 줄이다. std::move로 넘긴 변수는 그 줄 이후로 읽지 않는다. 다시 쓸 생각이면 애초에 move를 붙이지 않는다.

⑤ 반환할 때는 move를 붙이지 않아도 된다 🔴 사람이 한다

여기가 AI가 자주 틀리는 자리다. 그리고 틀리는 방향이 특이하다. 좋은 뜻으로 붙인 move가 손해를 낸다.

함수 안에서 만든 것을 돌려주는 코드를 보자. "복사를 피해야 하니까 move를 붙이자"는 판단은 얼핏 오늘 배운 것과 같아 보인다. 그런데 이 자리에서는 반대다.

AI가 보통 주는 코드 🔴
ScanMsg make_moved()
{
  ScanMsg s;
  // ... s 를 채운다
  return std::move(s);      // "복사를 피하려고" 붙였다
}
이게 맞다
ScanMsg make_plain()
{
  ScanMsg s;
  // ... s 를 채운다
  return s;                 // 그냥 돌려준다
}

무엇이 문제인가

컴파일러는 함수 안에서 만든 것을 돌려줄 때, 그것을 부른 쪽의 자리에 직접 만든다. 옮기지도 복사하지도 않는다. 애초에 사본이 생기지 않는다. std::move를 붙이면 이 최적화가 막힌다. 복사가 이동으로 바뀌는 것이 아니라, 없어도 될 이동이 하나 생긴다.

말로 하면 믿기 어려우므로 세어 봤다.

$ g++ -std=c++17 -O2 -Wall -o return_move return_move.cpp && ./return_move
return s;            : 복사 0회, 이동 0회  (ranges 360개)
return std::move(s); : 복사 0회, 이동 1회  (ranges 360개)
해석: 위쪽은 복사도 이동도 0회다. 아무 일도 안 일어났다. 아래쪽은 이동이 1회 생겼다. move를 붙여서 일이 하나 늘었다. 잰 곳: 컨테이너(우분투 24.04.4, g++ 13.3.0 -O2).

다행히 이 실수는 컴파일러가 직접 잡아 준다. 경고를 켜고 빌드하면 아래 메시지가 뜬다. 

$ g++ -std=c++17 -O2 -Wall -c return_move.cpp
return_move.cpp: In function ‘ScanMsg make_moved()’:
return_move.cpp:28:19: warning: moving a local object in a return statement prevents copy elision [-Wpessimizing-move]
   28 |   return std::move(s);
      |          ~~~~~~~~~^~~
return_move.cpp:28:19: note: remove ‘std::move’ call

🆕 이 출력에서 처음 나오는 것

-Wall
컴파일할 때 경고를 켜는 옵션이다. 안 켜면 위 메시지는 아예 안 뜬다. 여기서는 실행해 보지 않고도 문제를 알아내는 데 썼다.
[-Wpessimizing-move]
경고 줄 끝의 대괄호는 그 경고의 이름이다. 이 이름은 "오히려 나쁘게 만드는 move"라는 뜻이다. 마지막 줄에서 컴파일러가 고치는 법까지 알려 준다 — std::move를 지우라는 것이다.

쓸 때 / 안 쓸 때

자리std::move왜
함수 안에서 만든 것을 return붙이지 않는다붙이면 없어도 될 이동이 생기고 컴파일러 최적화가 막힌다
이미 있는 값을 다른 곳에 넘길 때붙인다원본을 다시 안 쓸 거라면 알맹이만 넘기는 것이 맞다
멤버 변수에 보관할 때넘겨받은 인자를 다시 안 쓰면 붙인다보관은 사본이 필요한 자리다. 사본을 만드는 방법이 복사와 이동 둘이다
반환문에 std::move를 붙이지 말아 줘. 지역 변수를 그대로 return하고, -Wall을 켠 빌드 명령도 같이 알려 줘.

⑥ 서버에서 8%인 것이 라즈베리파이에서는 「밀림」이 된다 🔴 사람이 한다

지금까지 잰 숫자는 전부 노트북급 컴퓨터에서 나온 것이다. 거기서는 22배가 나도 실제로는 3.66밀리초와 0.17밀리초의 차이다. 사람은 못 느낀다. 그래서 서버 프로그램에서는 이 이야기가 비용 문제로 끝난다. 전기를 조금 더 쓰고, 서버를 한 대 더 사면 되는 문제다.

로봇에서는 다른 종류의 문제가 된다. 터틀봇3의 계산은 로봇 위에 올라간 라즈베리파이가 한다. 노트북보다 한참 느리고, 그 느린 컴퓨터가 라이다·바퀴·통신을 동시에 감당한다.

여기서 콜백 하나가 늦어지면 그냥 늦어지고 끝나지 않는다. 라이다는 기다려 주지 않는다. 초당 5번, 계속 새 메시지를 보낸다. 처리가 밀리면 메시지가 줄을 서서 쌓이고, 로봇은 몇 초 전의 세상을 보고 판단하게 된다.

그때 로봇의 증상은 "느리다"가 아니라 "늦게 선다"이다. 콘을 지나치고 나서 조향을 시작하고, 벽에 닿고 나서 멈춘다. 코드에는 아무 오류가 없다. 22회에서 이 「밀림」을 숫자로 다시 만나고, 밀린 메시지를 어떻게 버릴지 정하는 법을 배운다.

이럴 때이렇게 말한다

코드를 받자마자"이 파일에서 불필요한 복사가 일어나는 자리를 전부 찾아서 표로 정리해 줘. 고치기 전에 어디가 왜 복사인지부터 알려 줘."
보관해야 하는 값이 있을 때"이 변수는 보관한 뒤로 다시 쓰지 않아. 복사하지 말고 알맹이를 넘기도록 고쳐 줘."
반환문에 move가 보일 때"반환문에 std::move를 붙이지 말아 줘. 지역 변수를 그대로 return해 줘."

해석: 셋째 줄이 오늘 가장 중요한 프롬프트다. "빠르게 해 줘"라고 말하지 않았다는 것에 주목한다. 빠르게 해 달라고 하면 AI는 아무 데나 move를 붙인다. "다시 쓰지 않는다"는 사실을 알려 주면 맞는 자리에만 붙는다. 이 사실은 코드를 짠 사람만 안다.

✅ 오늘의 점검

조금 더 알아두면 시험 범위 아님

왜 return s;에는 복사가 아예 안 생기나 (복사 생략)

C++에는 복사 생략(copy elision)이라는 규칙이 있다. 함수가 돌려주는 값은 부른 쪽이 받을 자리에 처음부터 만들어진다. 만들어 놓고 옮기는 것이 아니라, 애초에 그 자리에서 만든다. 그래서 복사도 이동도 0회다.

C++17부터는 임시 값을 돌려주는 경우에 이 생략이 의무가 됐다. 컴파일러가 마음대로 하는 최적화가 아니라 표준이 그렇게 하라고 정한 것이다. 우리가 쓰는 -std=c++17이 그 표준이다.

std::move를 붙이면 돌려주는 것이 "곧 버려질 임시 값"으로 바뀌면서 이 규칙의 조건에서 벗어난다. 그래서 이동이 하나 생긴다.

이동 생성자에 noexcept를 안 붙이면 생기는 일

값을 담는 그릇은 자리가 모자라면 더 큰 자리를 새로 잡아 있던 것들을 옮긴다. 옮기는 도중에 오류가 나면 원래 것도 새 것도 성치 않은 상태가 된다.

그래서 표준 라이브러리는 이렇게 정해 두었다. 이동 생성자에 noexcept가 붙어 있으면 이동을 쓰고, 없으면 복사를 쓴다. 복사는 실패해도 원본이 멀쩡하기 때문이다.

결과는 이렇다. noexcept 한 단어를 빠뜨리면 이동이 조용히 복사로 바뀐다. 코드는 그대로 돌아가고 결과도 맞다. 느려질 뿐이다. 오늘 계속 본 "맞지만 둔한 코드"의 전형적인 예다.

복사 생성자를 손으로 쓰면 딸려 오는 것들 (다섯 개 규칙)

한 객체에는 복사·이동과 관련된 함수가 다섯 개 있다.

  • 복사 생성자 — ScanMsg(const ScanMsg &)
  • 복사 대입 — operator=(const ScanMsg &)
  • 이동 생성자 — ScanMsg(ScanMsg &&)
  • 이동 대입 — operator=(ScanMsg &&)
  • 소멸자 — ~ScanMsg()

이 중 하나라도 손으로 쓰면 나머지도 같이 생각해야 한다. 하나만 쓰고 나머지를 컴파일러에 맡기면 짝이 안 맞는 일이 생긴다. 오늘 예제에서 = delete로 대입을 막아 둔 것도 그 때문이다.

더 좋은 방법은 다섯 개 전부 안 쓰는 것이다. 값을 std::vector·std::string 같은 표준 그릇에 담아 두면 복사·이동·정리를 그릇이 알아서 한다. 우리 예제가 다섯 개를 손으로 쓴 것은 횟수를 세기 위해서일 뿐이고, 평소 코드에서는 하나도 쓸 일이 없다.

참조로 받으면 항상 이득인가 — 아닌 자리

아니다. 세 가지 자리에서는 값으로 받는 것이 맞다.

  • 작은 값 — int(4바이트)·float(4바이트)·bool. 주소를 넘기는 데도 8바이트가 든다. 값보다 주소가 더 크다.
  • 어차피 사본을 만들 함수 — 받아서 고쳐 쓰거나 보관할 거라면 값으로 받은 뒤 std::move로 넘기는 편이 낫다. 참조로 받고 안에서 복사하면 결과가 같고 줄만 는다.
  • 원본이 언제 사라질지 모르는 값 — 참조는 원본이 사라지면 같이 못 쓴다. 다른 스레드나 다음 콜백까지 살아 있어야 하면 사본이 필요하다.

기준선은 오늘 잰 8바이트다. 그보다 크면 참조부터 생각하고, 위 세 가지에 걸리면 값으로 되돌린다.
