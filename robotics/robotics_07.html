코드를 읽기 위한 최소 장비

오늘 답할 질문
  1. ROS 2 예제를 열면 보이는 ::, ->, &, <>는 각각 무엇인가?
  2. 전처리기·네임스페이스·템플릿·참조·포인터는 각각 무슨 문제를 풀려고 생긴 것인가?
  3. 함수에 값을 넘겼는데 고친 것이 원본에 반영되지 않는다면 무엇을 빠뜨린 것인가?
  4. AI가 준 C++ 코드를 보고 "여기가 이상하다"고 말하려면 최소한 무엇을 알아야 하나?

오늘은 문법 수업이 아니라 읽기 연습이다. 이 강의는 학생이 C++ 코드를 처음부터 짜기를 요구하지 않는다. 코드는 에이전트가 짠다. 학생이 하는 일은 받은 코드를 읽고 판단하는 것이다.

그런데 읽으려면 최소한의 장비가 필요하다. const std::vector<float> & ranges라는 한 조각에 기호가 넷 들어 있는데, 그중 하나라도 모르면 학생은 그 줄에서 읽기를 멈춘다. 멈추면 그 아래 스무 줄이 통째로 안 읽힌다.

그래서 오늘은 기호 여덟 개만 다룬다. 절마다 먼저 그 문법이 무엇이고 왜 생겼는지를 설명하고, 그다음에 라이다 값으로 「멈출까 갈까」를 정하는 작은 프로그램에 그것을 적용한다. 프로그램은 옛날 C 방식으로 먼저 짜 두고, 절이 넘어갈 때마다 문법 하나씩으로 고쳐 간다. 깊은 이야기는 그 문법이 실제로 문제를 일으키는 회차에서 다시 한다.

한 장 요약 — 학기가 끝나도 이 표만 남으면 된다

무엇을 먼저 볼지: 맨 오른쪽 「이것만 알면 된다」 열만 읽어도 오늘 수업은 끝난다. 순서는 오늘 프로그램에 적용하는 순서다.

기호이름코드에서 이렇게 보인다이것만 알면 된다
#include 전처리기 지시문 #include <vector> 컴파일 전에 헤더 파일의 선언을 그 자리에 붙인다. 없으면 이름을 못 알아본다
<> 템플릿 인자 std::vector<float> vector는 클래스 템플릿이고, 꺾쇠 안의 원소 타입을 넣어야 실제 타입이 된다
auto 타입 추론 auto n = ranges.size(); 타입을 컴파일러가 오른쪽을 보고 채운다. 실행 중에 바뀌는 것이 아니다
& 참조 void f(std::vector<float> & r) 원본에 붙인 다른 이름. 복사가 아니다. 이 한 글자가 없으면 고친 것이 원본에 안 남는다
const 상수 한정자 float g(const Scan & s) 못 바꾼다는 약속. 어기면 컴파일이 안 된다
struct · . 구조체 · 멤버 접근 struct Scan { ... }; / scan.frame 값 여러 개를 한 타입으로 묶는다. 객체의 멤버는 점으로 꺼낸다
namespace · :: 네임스페이스 · 범위 지정 연산자 std::cout, lidar::Scan 이름들을 상자에 넣어 부딪치지 않게 한다. 앞이 네임스페이스, 뒤가 그 안의 이름
* · -> · nullptr 포인터 · 멤버 접근 · 널 포인터 Scan * p = nullptr; / p->frame 포인터는 객체의 주소를 담는 변수다. 비어 있을 수 있고, 빈 채로 ->를 쓰면 죽는다
해석: 여덟 줄 중 넷째 줄(참조 &)만 색이 다르다고 생각하면 된다. 나머지는 "알아보면 끝"이지만, &는 있고 없고에 따라 프로그램이 실제로 하는 일이 달라진다. 오늘 ⑤절에서 그 차이가 출력에 그대로 찍힌다. 이 강의에서 AI 코드를 고치는 일의 절반이 이 한 글자를 넣는 일이다. 깊은 이야기는 11회에서 실제 시간을 재면서 한다.

① 오늘 만들 것 — 정면 장애물 판정기, 옛날 방식으로 먼저 🟡 맡기되 검사

무엇을 만드나

라이다가 잰 정면 거리 값 몇 개를 받아 가장 가까운 장애물까지의 거리를 찾고, 그것이 정지 거리보다 가까우면 STOP, 아니면 GO를 찍는 프로그램이다. 27회의 콘 트랙 주행에서 로봇이 실제로 하는 판단을 가장 작게 줄인 것이다. 라이다는 벽이 너무 멀거나 빛이 안 돌아오면 「측정 실패」를 보내는데, 그 값이 INFINITY(무한대)다. 6회 측정 코드에도 이 값이 있었다. 이것을 건너뛰는 것까지가 오늘 프로그램의 전부다.

읽는 법

  • 먼저 이 프로그램을 오늘 배울 문법을 하나도 안 쓰고, 옛날 C 방식 그대로 짠다. 이대로도 돌아간다.
  • ②절부터는 절마다 「개념」이 먼저 온다 — 그 문법이 무엇이고 어떤 문제를 풀려고 생겼는지. 그다음 「예제에 적용」에서 지금 프로그램의 어디가 불편한지를 보고, 그 문법으로 고친다.
  • 고치는 자리는 고치기 전(붉은 테두리)과 고친 뒤(푸른 테두리)를 따로 놓는다. 더하기만 하는 단계는 더한 뒤의 모양만 보인다.
  • 그 아래 📄 「전체 코드」 상자를 누르면 그 단계까지의 main.cpp 전체가 나온다. 파일 첫 줄의 주석에 버전(v1, v2, …)이 적혀 있다. 어느 버전을 펼쳐도 그대로 빌드되고 돌아간다. 오른쪽 위 「복사」로 통째로 가져갈 수 있다.
  • 「실제로 나온 출력」은 그 버전이 찍은 것 전부다. 출력이 안 변하는 단계가 많은데, 그것도 배울 점이다.

1단계 (v1) — 옛날 방식 그대로

C에서 하던 대로 짰다. 값은 배열에, 화면 출력은 printf로, 무한대 판정은 isfinite로. 오늘 배울 문법은 하나도 없다. 그런데도 멀쩡히 돌아간다는 것을 먼저 본다. 

// 7회 정면 장애물 판정기 — v1 (1단계: 옛날 방식 그대로)
#include <stdio.h>     // printf
#include <math.h>      // isfinite, INFINITY

int main()
{
  // 라이다가 잰 정면 8방향 거리 (m). INFINITY 는 측정 실패
  float ranges[8] = {1.20f, 0.83f, INFINITY, 0.65f, 0.71f, INFINITY, 2.40f, 3.10f};
  float stop_dist = 0.7f;                  // 이보다 가까우면 멈춘다

  float best = 1e9f;                       // 아직 아무것도 못 봤다는 뜻으로 큰 값
  for (int i = 0; i < 8; i++) {
    if (!isfinite(ranges[i])) continue;    // 측정 실패는 건너뛴다
    if (ranges[i] < best) best = ranges[i];
  }
  printf("가장 가까운 장애물 %.2f m\n", best);
  if (best < stop_dist) printf("STOP\n");
  else                  printf("GO\n");
  return 0;
}

🆕 이 코드에서 처음 나오는 것

float ranges[8] = { ... };
실수 원소 8개짜리 배열이다. 원소 개수를 코드에 박아 넣는다. 여기서는 라이다 정면 8방향의 거리를 담았다. ranges[i]가 i번째 원소이고 첫 원소는 0번이다.
1e9f
10억을 실수로 적은 것이다(1×10⁹). 여기서는 "아직 아무 값도 못 봤다"는 뜻의 출발값으로 썼다. 어떤 실제 거리든 이것보다는 작다.
continue;
반복문에서 이번 바퀴의 나머지를 건너뛰고 다음 바퀴로 간다. 여기서는 측정 실패 값을 최솟값 후보에서 빼는 데 썼다.

빌드는 CMake 로 한다 — 네 줄이면 된다

6회에서 g++ 한 줄로 빌드했다. 오늘부터는 같은 폴더에 CMakeLists.txt를 하나 두고 빌드한다. 파일이 하나뿐인 지금은 g++과 차이가 없지만, ⑩절에서 파일이 넷이 되는 순간 이 네 줄이 일을 대신한다. 지금은 내용을 이해하지 않아도 된다. 그대로 복사해 두고, 9회에서 한 줄씩 읽는다. 

cmake_minimum_required(VERSION 3.16)
project(scan_guard CXX)
set(CMAKE_CXX_STANDARD 17)
add_executable(scan_guard main.cpp)

준비된 build/에서 실제로 컴파일한다. 코드를 고칠 때마다 이것만 다시 친다.

② 전처리기와 #include, 그리고 std:: 🟢 맡긴다

개념 — 컴파일 전에 한 번 더 거치는 단계가 있다

C++ 소스 파일은 컴파일러에 곧장 들어가지 않는다. 그 앞에 전처리기(preprocessor)라는 단계가 있어서, 파일 안의 #으로 시작하는 줄을 먼저 처리한다. 이 줄들을 전처리기 지시문(preprocessor directive)이라고 한다. 지시문은 C++ 문장이 아니다. 세미콜론으로 끝나지 않고, 글자를 자르고 붙이는 일만 한다.

가장 많이 보는 지시문이 #include다. 하는 일은 하나다 — 지정한 파일의 내용을 그 줄 자리에 통째로 붙여 넣는다. 그렇게 붙여 넣어지는 파일을 헤더(header)라고 하고, 헤더에는 보통 "이런 이름의 함수·타입이 있다"는 선언이 들어 있다. 컴파일러는 파일을 위에서 아래로 읽으면서 모르는 이름이 나오면 그 자리에서 오류를 내므로, 남이 만든 것을 쓰려면 그 선언을 먼저 붙여 두어야 한다. 그것이 #include가 맨 위에 있는 이유다.

무엇을 먼저 볼지: 꺾쇠와 따옴표가 찾는 곳을 정한다.

모양어디서 찾나무엇을 가져올 때
#include <vector>시스템에 깔린 표준·라이브러리 헤더C++ 표준 라이브러리, ROS 2 같은 남의 라이브러리
#include "front.hpp"내 프로젝트 폴더에서 먼저, 없으면 시스템내가 만든 헤더 — ⑩절
#include <cmath> vs <math.h>같은 내용의 C++ 판 / C 판C++에서는 c를 앞에 붙이고 .h를 뗀 이름을 쓴다. 안의 이름이 std::에 들어간다

여기서 std::가 나온다. C++ 표준 라이브러리가 주는 이름은 전부 std라는 네임스페이스(namespace) 안에 들어 있다. 네임스페이스는 이름들을 담아 두는 상자이고, 상자 안의 이름은 상자::이름으로 부른다. 그 두 콜론이 범위 지정 연산자(scope resolution operator)다. 왜 상자에 넣어 두는지, 내 상자는 어떻게 만드는지는 ⑧절에서 다룬다. 지금은 std::가 붙어 있으면 "표준 라이브러리의 그것"이라고 읽으면 된다.

예제에 적용 — %.2f 한 글자를 잘못 적으면

v1의 printf는 값의 타입마다 %d·%f 같은 서식을 사람이 골라 적어야 한다. 실수를 %d(정수용)로 찍으면 어떻게 될까. v1에서 그 한 글자만 바꿔 돌려 봤다.

$ ./build/scan_guard

해석: 경고만 내고 컴파일은 되고, 실행도 되고, 엉뚱한 숫자가 찍힌다. 로봇이 10억 미터 앞에 장애물이 있다고 믿는 셈이다. 판정은 best로 하니 STOP은 맞게 나왔지만, 이런 종류의 실수는 실행해 봐야 안다.

2단계 (v2) — printf를 std::cout으로

C++ 표준 라이브러리에는 타입을 보고 알아서 찍는 출력 도구가 있다. std::cout이다. 서식 글자가 없으니 잘못 적을 자리도 없다. 이것을 쓰려면 그 선언이 든 헤더 <iostream>을 #include해야 한다. 무한대 판정도 C++ 헤더 <cmath>의 std::isfinite로 바꾼다.

고치기 전 (v1)

#include <math.h>      // isfinite, INFINITY
  // …

③ 템플릿 — 꺾쇠 안은 템플릿 인자다 🟢 맡긴다

개념 — 타입을 인자로 받는 설계도

"실수 여러 개를 담는 것"과 "문자열 여러 개를 담는 것"은 하는 일이 같다. 담고, 꺼내고, 몇 개인지 센다. 다른 것은 무엇을 담느냐뿐이다. 그런데 C++은 타입이 정해져야 코드가 되는 언어라, 그 둘을 따로 짜야 할 것 같다. 이 문제를 푸는 장치가 템플릿(template)이다 — 타입을 인자로 받는 설계도를 한 번 써 두면, 컴파일러가 인자로 받은 타입마다 실제 코드를 찍어 낸다.

설계도에 타입을 넣어 주는 자리가 꺾쇠다. std::vector<float>에서 std::vector가 클래스 템플릿(class template), 꺾쇠 안의 float이 템플릿 인자(template argument)다. 인자를 넣기 전의 std::vector는 아직 타입이 아니다. std::vector<float>가 돼야 변수를 만들 수 있다.

표준 라이브러리에서 값을 여러 개 담는 클래스 템플릿들을 컨테이너(container)라고 부르고, 담긴 값 하나하나를 원소(element)라고 한다. 이 과목에서 쓰는 컨테이너는 사실상 std::vector 하나다.

무엇을 먼저 볼지: 꺾쇠를 보면 "원소 타입이 무엇인가"만 읽으면 된다.

④ 타입 추론 — auto는 타입을 안 적어도 되는 자리다 🟢 맡긴다

개념 — 타입은 정해져 있되, 적는 사람이 바뀐다

C++은 정적 타입 언어다. 모든 변수의 타입은 컴파일할 때 정해지고, 프로그램이 도는 동안 절대 바뀌지 않는다. 파이썬처럼 같은 변수에 숫자를 넣었다가 문자열을 넣는 일은 없다. 그래서 변수를 만들 때마다 타입을 적어 왔다 — int n = 3;.

그런데 타입은 대개 오른쪽 초기값을 보면 이미 정해져 있다. ranges.size()가 돌려주는 값의 타입은 컴파일러가 이미 알고 있다. 사람이 그것을 한 번 더 옮겨 적는 것이 std::vector<float>::size_type이고, 옮겨 적다가 틀리면 컴파일은 되면서 조용히 값이 바뀌거나 복사가 한 번 일어난다. 타입 추론(type deduction)은 그 옮겨 적기를 컴파일러에게 맡기는 것이다. 변수 타입 자리에 auto를 쓰면 컴파일러가 오른쪽 초기값의 타입으로 채운다. 적는 사람이 컴파일러로 바뀌었을 뿐, 타입이 없어진 것이 아니다.

auto가 가장 자주 보이는 자리가 범위 기반 for(range-based for)다. for (auto r : ranges) { ... }는 컨테이너의 원소를 처음부터 끝까지 하나씩 r에 담아 몸통을 돌린다. 번호도 조건도 안 적으니 8이나 n을 잘못 적을 자리가 없고, r의 타입은 원소 타입에서 추론된다.

⑤ 참조 — & 한 글자가 없으면 고친 것이 원본에 안 남는다 🔴 사람이 한다

개념 — 함수는 기본적으로 사본을 받는다

C++에서 함수에 값을 넘기면 기본적으로 통째로 복사해서 넘긴다. 이것을 값 전달(pass by value)이라고 한다. 함수 안의 인자는 사본이고, 함수 안에서 그것을 고쳐도 원본은 그대로다. 함수가 끝나면 사본은 버려진다. int·float 하나를 넘길 때는 이것이 오히려 편하다. 넘긴 쪽의 변수가 함부로 바뀌지 않으니까.

그런데 두 경우에 값 전달이 문제가 된다. 하나는 함수가 원본을 고쳐야 할 때 — 사본을 고쳐 봐야 소용이 없다. 다른 하나는 넘기는 것이 클 때 — 거리 값 360개가 든 컨테이너를 부를 때마다 복사하면 그만큼 시간과 메모리를 쓴다. 이 둘을 푸는 장치가 참조(reference)다. 타입 뒤에 &를 붙이면 그 이름은 사본이 아니라 원본에 붙인 다른 이름(별명)이 된다. 참조를 통해 고치면 원본이 고쳐지고, 아무것도 복사되지 않는다. 이것이 참조 전달(pass by reference)이다.

참조는 만들 때 반드시 원본을 정해야 하고, 그 뒤로 다른 원본으로 바꿀 수 없으며, 비어 있을 수도 없다. 그래서 쓰기가 단순하다 — 원본 변수를 쓰듯이 그냥 쓴다. 이 점이 ⑨절의 포인터와 다르다.

⑥ 상수 — const는 컴파일러에게 하는 약속이다 🟡 맡기되 검사

개념 — 안 바꿀 것이라고 미리 말해 두면 컴파일러가 지켜 준다

큰 프로그램에서 가장 찾기 어려운 버그는 "어디선가 이 값이 바뀌었다"는 종류다. 바뀐 자리를 찾으려면 코드 전체를 뒤져야 한다. const는 상수 한정자(const qualifier)다. 타입 앞에 붙이면 "이것은 만든 뒤에 바꾸지 않는다"는 약속이 되고, 약속을 어기는 줄이 있으면 실행 전에 컴파일러가 막는다. 실행해 봐야 아는 버그가 컴파일 오류로 앞당겨지는 것이 이 키워드의 값어치다.

⑤절의 참조와 짝을 이루는 자리가 있다. 참조로 받으면 복사는 없어지지만, 그 대신 함수가 원본을 건드릴 수 있게 된다. 읽기만 하는 함수라면 그럴 필요가 없다. 그래서 const T & — const 참조로 받는다. "원본을 복사 없이 보되, 바꾸지는 않겠다." 읽기만 하는 함수 인자의 기본값이 이 모양인 이유다.

무엇을 먼저 볼지: 가운데 열의 위치가 뜻을 정한다. 오늘은 앞의 둘을 쓴다.

⑦ 구조체 — 짝을 이루는 값은 struct로 묶는다 🟢 맡긴다

개념 — 값 여러 개를 한 타입으로 만든다

변수 하나에는 값 하나가 든다. 그런데 현실의 데이터는 대개 여러 값이 짝을 이룬다. 라이다 스캔 한 번은 거리 값들만이 아니라 어느 좌표계에서 잰 것인지, 언제 잰 것인지가 같이 온다. 이것들을 따로따로 변수로 두면 함수에 넘길 때마다 여럿을 따로 넘겨야 하고, 짝이 어긋나도 아무도 모른다.

구조체(struct)는 값 여러 개를 하나로 묶어 새 타입을 만드는 문법이다. struct Scan { std::string frame; std::vector<float> ranges; };라고 쓰면 Scan이라는 타입이 생기고, 안에 든 frame·ranges 하나하나를 멤버(member)라고 한다. 이 타입으로 만든 변수 — Scan scan;의 scan — 를 객체(object)라고 부른다. 객체의 멤버는 점으로 꺼낸다: scan.frame. 이 점이 멤버 접근 연산자(member access operator)다.

③절의 ranges.size()도 같은 점이다 — ranges가 std::vector<float> 타입의 객체이고, size가 그 안의 멤버(함수)다. 표준 라이브러리의 vector도, 우리가 만드는 Scan도 "값과 함수를 묶은 타입"이라는 점에서 같은 것이다. 구조체에 함수와 private가 붙으면 클래스가 되는데, 그것은 8회에서 한다.

⑧ 네임스페이스 — 이름을 상자에 넣어 부딪치지 않게 한다 🟢 맡긴다

개념 — 프로그램이 커지면 이름이 겹친다

v7에서 만든 Scan은 짧고 흔한 이름이다. 프로그램이 커져서 카메라 라이브러리도 Scan을 만들고 ROS 2 메시지에도 Scan이 있으면, 컴파일러는 어느 것을 말하는지 정할 수 없다. 이름을 길게 짓는 것(lidar_scan_t)은 C 시절의 해법이고, C++의 해법이 네임스페이스(namespace)다.

namespace lidar { ... }로 감싸면 그 안에서 만든 이름은 전부 lidar라는 상자에 들어간다. 밖에서 부를 때는 범위 지정 연산자 ::로 상자를 밝힌다 — lidar::Scan. 같은 이름 Scan이 다른 상자에 있어도 camera::Scan과 lidar::Scan은 다른 타입이므로 부딪치지 않는다. 상자는 겹칠 수 있다. ROS 2의 sensor_msgs::msg::LaserScan은 sensor_msgs 상자 안의 msg 상자 안의 LaserScan이다.

②절의 std::가 바로 이것이었다. 표준 라이브러리는 자기 이름을 전부 std 상자에 넣어 두었고, 그래서 우리가 vector나 count라는 이름을 마음대로 써도 표준의 것과 부딪치지 않는다. 어느 상자에도 넣지 않은 이름(main, nearest)은 전역 네임스페이스에 있다고 말한다.

무엇을 먼저 볼지: 왼쪽 열의 앞부분만 보면 그것이 누구 것인지 안다.

⑨ 포인터 — 아직 스캔이 없을 수도 있다 🟡 맡기되 검사

개념 — 객체의 주소를 담는 변수

프로그램의 모든 변수는 메모리 어딘가에 놓이고, 그 자리에는 번호가 있다. 그것이 주소(address)다. 포인터(pointer)는 객체 자체가 아니라 객체의 주소를 담는 변수다. 타입 뒤에 *를 붙여 만든다 — lidar::Scan * p. 어떤 변수의 주소를 얻을 때는 변수 앞에 &를 붙인다 — &scan. 이것은 주소 연산자이고, ⑤절의 참조 &와 글자만 같고 뜻이 다르다. 타입 뒤에 붙으면 참조, 변수 앞에 붙으면 주소다.

포인터가 가리키는 객체의 멤버는 점이 아니라 화살표로 꺼낸다 — p->frame. (*p).frame이라고 써도 같은데, 너무 자주 쓰다 보니 짧은 표기가 생겼다. 화살표도 멤버 접근 연산자다. 왼쪽이 객체이면 점, 포인터이면 화살표. 하는 일은 같다.

참조와 달리 포인터는 아무것도 안 가리키는 상태가 될 수 있다. 그 값이 nullptr(널 포인터)다. "아직 없다"를 나타낼 수 있다는 것이 포인터의 쓸모이고, 동시에 위험이다 — 널 포인터에 화살표를 쓰면 프로그램이 그 자리에서 죽는다. 그래서 포인터를 받는 함수는 비었는지부터 확인하는 것이 습관이다.

무엇을 먼저 볼지: 「비어 있을 수 있나」 행이 둘을 가르는 핵심이다.

참조 T &포인터 T *
무엇을 담나원본에 붙인 다른 이름원본의 주소
비어 있을 수 있나없다. 만들 때 원본을 정한다있다. nullptr
다른 원본으로 바꿀 수 있나없다있다. 대입하면 된다
멤버 접근r.framep->frame
언제함수 인자 — 오늘 ⑤·⑥절「없을 수도 있는 것」 — ROS 2 콜백의 메시지
해석: ROS 2가 콜백에 메시지를 포인터로 넘기는 이유가 이 표 둘째 행이다. 자세히는 스마트 포인터인데, 읽는 법은 오늘의 화살표와 같다. 12회에서 다룬다. 포인터로 new/delete를 직접 하는 일은 이 강의에서 하지 않는다(10회에서 왜 안 하는지를 본다).

  else                  std::cout << "GO\n";

void report(const lidar::Scan * s, float stop_dist)
{
  if (s == nullptr) {
    std::cout << "아직 스캔이 없다\n";
    return;
  }
  const float best = nearest(s->ranges);   // -> — 포인터가 가리키는 객체의 멤버를 꺼낸다
  std::cout << "[" << s->frame << "] 가장 가까운 장애물 " << best << " m\n";
  if (best < stop_dist) std::cout << "STOP\n";
  else                  std::cout << "GO\n";
}

int main()
{
  const float stop_dist = 0.7f;            // 프로그램 도중에 바뀌면 안 되는 값
  const lidar::Scan * latest = nullptr;    // 아직 아무 스캔도 안 가리킨다

  report(latest, stop_dist);               // 스캔이 오기 전

  lidar::Scan scan{"base_scan", {1.20f, 0.83f, INFINITY, 0.65f, 0.71f, INFINITY, 2.40f, 3.10f}};
  fill_missing(scan.ranges);               // . — 객체의 멤버를 꺼낸다 (멤버 접근)
  latest = &scan;                          // scan 의 주소를 넣는다. 이제 scan 을 가리킨다
  report(latest, stop_dist);               // 스캔이 온 뒤
  return 0;
}

// 측정 실패(inf)를 센서 최대 사거리 8 m 로 바꿔 넣는다
void fill_missing(std::vector<float> & r)      // & — 원본을 받는다. 고쳐야 하니까
{
  for (auto & x : r) {
    if (!std::isfinite(x)) x = 8.0f;

{
  float best = 1e9f;

    if (x < best) best = x;
  }
  return best;
}

⑩ 헤더와 소스 나누기 — 그리고 AI가 거기서 하는 실수 🔴 사람이 한다

개념 — 선언과 정의를 두 파일로 나눈다

②절에서 #include는 다른 파일의 내용을 그 자리에 붙여 넣는 것이라고 했다. 표준 라이브러리만 그렇게 가져오는 것이 아니다. 우리가 만든 것도 그렇게 가져온다. 여기서 C++이 파이썬과 크게 다른 점이 하나 나온다 — "무엇이 있는지"(선언, declaration)와 "어떻게 하는지"(정의, definition)를 다른 파일에 나눠 적는다.

선언은 함수의 이름·인자·반환 타입만 적고 세미콜론으로 끝낸다 — float front(const std::vector<float> & ranges);. 정의는 중괄호 안의 코드까지 적은 것이다. 컴파일러가 어떤 함수를 부르는 자리에서 필요한 것은 선언뿐이고, 정의는 프로그램 전체에서 딱 한 번만 있으면 된다. 그래서 선언은 헤더(.hpp)에 두어 쓰는 파일마다 #include하고, 정의는 소스(.cpp)에 한 번만 둔다. 소스 파일이 여럿이면 각각 따로 컴파일한 뒤 마지막에 하나로 이어 붙이는데, 그 단계가 링크(link)다.

무엇을 먼저 볼지: 왼쪽 열이 헤더, 오른쪽이 소스다. 헤더 쪽이 짧아야 정상이다.

헤더 (.hpp) — 무엇이 있는지소스 (.cpp) — 어떻게 하는지
클래스에 무슨 함수가 있는지그 함수가 실제로 무엇을 하는지
함수 이름과 인자 모양, 그리고 세미콜론중괄호 안의 코드 전부
쓰는 쪽이 #include로 읽는다빌드할 때만 쓰인다
고치면 이걸 읽는 파일이 전부 다시 컴파일된다고쳐도 이 파일만 다시 컴파일된다
해석: 마지막 줄이 나누는 진짜 이유다. 파이썬은 파일을 고치면 그 파일만 다시 읽으면 되지만, C++은 헤더 하나를 고치면 그것을 읽는 파일 전부를 다시 컴파일해야 한다. 그래서 헤더는 가볍게 유지한다. 아래 AI 실수가 정확히 이 지점을 어긴다.

예제에 적용 — 정면 거리 함수 front()를 따로 뺀다

오늘 프로그램과 별개로 작은 프로젝트 하나를 만든다. 거리 값들 중 가운데 것을 돌려주는 front() 하나를 헤더(front.hpp)와 소스(front.cpp)로 나누고, main.cpp가 헤더를 #include해서 쓴다. 파일이 셋이니 CMakeLists.txt의 add_executable 뒤에 소스 둘을 이어 적는다.

실수 1 — AI가 헤더에 함수의 내용까지 적는다

소스가 main.cpp 하나뿐인 지금은 이 헤더로도 빌드가 되고 잘 돈다. 그래서 알아채기 어렵다. 문제는 프로젝트가 커져서 두 번째 소스 파일이 같은 헤더를 #include하는 순간이다. #include는 붙여 넣기이므로 front의 정의가 두 벌 만들어지고, 각 파일의 컴파일은 되는데 마지막에 둘을 이어 붙이는 링크 단계에서 터진다. 아래는 소스를 하나 더 두고 실제로 그렇게 해서 나온 오류다(8회에서 소스가 둘이 되면 직접 만난다).

실수 2 — 안 쓰는 #include를 남긴다

코드를 여러 번 고치다 보면 더 이상 안 쓰는 헤더가 맨 위에 그대로 남는다. 오늘 프로그램도 v2에서 <stdio.h>를 지우지 않았다면 그 뒤로 계속 남아 있었을 것이다. AI는 이것을 잘 지우지 않는다. 지워도 되는지 확신이 없기 때문이다.

📝 연습문제 — 옛날 방식 코드를 오늘 배운 것으로 고쳐 본다 🟡 맡기되 검사

아래는 「왼쪽과 오른쪽 중 어느 쪽이 더 비어 있나」를 정하는 프로그램이다. 값 8개 중 앞의 넷이 왼쪽, 뒤의 넷이 오른쪽 방향의 거리다. 오늘 프로그램의 v1처럼 옛날 방식으로만 짰다. 이대로도 돌아간다.

연습문제 — 옛날 방식 원본 (main.cpp · CMakeLists.txt 는 ①절 것을 그대로 쓴다)

빌드해서 돌리는 법: cmake -S . -B build && cmake --build build && ./build/scan_guard

main.cpp
// 7회 연습문제 — 어느 쪽으로 돌까. 옛날 방식으로 짠 코드
#include <stdio.h>
#include <math.h>

// 앞의 절반은 왼쪽, 뒤의 절반은 오른쪽 방향의 거리다
float side_min(float r[], int from, int to)
{
  float best = 1e9f;
  for (int i = from; i < to; i++) {
    if (!isfinite(r[i])) continue;
    if (r[i] < best) best = r[i];
  }
  return best;
}

int main()
{
  float ranges[8] = {0.42f, 0.55f, INFINITY, 0.90f, 1.80f, 2.10f, INFINITY, 1.65f};
  float left  = side_min(ranges, 0, 4);
  float right = side_min(ranges, 4, 8);
  printf("왼쪽 %.2f m, 오른쪽 %.2f m\n", left, right);
  if (left > right) printf("LEFT\n");
  else              printf("RIGHT\n");
  return 0;
}

조금 더 알아두면 시험 범위 아님

using과 using namespace std; — 자주 보이지만 조심할 것

std::를 매번 적기 귀찮아서 생략하게 해 주는 문법이 있다. 두 가지 모양이다. 

using std::cout;          // ① 이 이름 하나만 std:: 없이 쓰겠다
using namespace std;      // ② std 안의 이름을 전부 std:: 없이 쓰겠다

①은 괜찮고 ②는 조심해야 한다. ②를 쓰면 표준 라이브러리의 모든 이름이 전역 네임스페이스에 굴러다니게 되고, 내가 만든 이름과 부딪치면 어느 것이 불렸는지 알 수 없는 상황이 생긴다 — ⑧절에서 네임스페이스가 막으려던 바로 그 문제다. count·distance·data처럼 흔한 이름이 표준에도 있다.

특히 헤더 파일에서는 둘 다 쓰지 않는다. 헤더를 읽는 모든 파일에 그 생략이 딸려 들어가기 때문이다. AI가 준 헤더 맨 위에 using namespace std;가 보이면 지워 달라고 하면 된다.

using에는 긴 타입에 짧은 별명을 붙이는 용법도 있다. ROS 2 코드에서 자주 보게 된다. 

using LaserScan = sensor_msgs::msg::LaserScan;   // 별명을 붙였다
중괄호로 초기화하는 모양 — Scan scan{"base_scan", {0.83f, 0.85f}}

⑦절의 Scan scan{...}이 이 모양이다. 중괄호 안에 값을 순서대로 나열하면 그대로 채워진다. 바깥 중괄호가 Scan을 채우고, 안쪽 중괄호가 ranges를 채운다.

옛날에는 소괄호 ()만 있었는데 C++11부터 중괄호도 쓸 수 있게 됐다. 중괄호 쪽에 이득이 하나 있다 — 값이 잘려 나가는 변환을 막아 준다. int x{3.14};는 소수점이 잘리므로 컴파일러가 거부한다. int x(3.14);는 아무 말 없이 3이 된다.

그래서 값을 채울 때는 중괄호가 조금 더 안전하다. 다만 std::vector에서는 v(5)(원소 5개)와 v{5}(값 5 하나)가 다른 뜻이 되니 컨테이너를 만들 때는 소괄호와 중괄호를 헷갈리지 않게 쓴다. 6회의 ranges(N)과 오늘의 ranges{1.20f, ...}가 그 둘이다.

auto가 참조와 const를 안 물려받는다는 것

auto는 오른쪽의 타입을 그대로 가져오지 않는다. const와 &는 떼어 버리고 알맹이만 가져온다. ⑤절의 for (auto & x : r)에서 &를 직접 적어야 했던 이유가 이것이다. 

const std::vector<float> & r = scan.ranges;

auto        a = r;   // 복사본이 생긴다   (const 와 & 가 떨어졌다)
const auto & b = r;   // 복사가 없다      (직접 적어 줘야 한다)

그래서 ROS 2 코드에는 const auto &가 세트로 붙어 다닌다. auto만 쓰면 복사가 조용히 한 번 일어난다. 6회에서 본 「AI 코드의 복사 오버헤드 1.39배」 중 상당수가 이 모양이다.

규칙은 더 있지만 이 강의에서 외울 필요는 없다. 기억할 것은 하나다 — 읽기만 할 거면 const auto &라고 통째로 적는다. 11회에서 이 차이를 시간으로 재 본다.
