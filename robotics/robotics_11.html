RAII와 스마트 포인터 — 지우는 일을 소멸자에게 맡긴다

오늘 답할 질문
  1. new로 만든 객체를 delete하는 일은 왜 사람이 맞추기 어려운가?
  2. delete를 소멸자 안에 넣으면 무엇이 달라지나?
  3. 그렇게 만든 포인터를 복사하면 무슨 일이 일어나나?
  4. std::unique_ptr와 std::shared_ptr는 무엇이 다르고, 무엇을 보고 고르나?
  5. ROS 2 코드에 늘 보이는 ::SharedPtr은 무엇인가?

9회에서 소멸자는 객체가 스코프를 벗어날 때 자동으로 불린다는 것을 봤다. 10회 ⑤절에서는 std::unique_ptr를 설명 없이 한 번 썼다. 오늘은 그 둘을 잇는다. 소멸자가 자동으로 불린다는 사실 하나로 「지우는 일」을 사람 손에서 떼어 낼 수 있다 — 그 방법을 직접 클래스로 만들어 보고, 표준 라이브러리에 이미 있는 것(unique_ptr·shared_ptr)으로 넘어간다.

오늘은 용어 여섯 개를 다룬다. 절마다 먼저 그 문법이 무엇이고 왜 생겼는지를 설명하고, 그다음에 센서를 켜고 끄는 작은 프로그램에 그것을 적용한다. 프로그램은 new와 delete로 먼저 짜 두고, 절이 넘어갈 때마다 고쳐 간다.

① 오늘 만들 것 — 센서를 켜고 끄는 함수, new와 delete로 먼저 🔴 사람이 한다

무엇을 만드나

센서 하나를 켜고, 상태가 나쁘면 그만두고, 좋으면 측정을 시작하는 함수 setup()이다. 센서 객체는 켜질 때와 꺼질 때 한 줄씩 찍는다 — 이 두 줄이 오늘 내내 「정리가 됐는지」를 눈으로 보는 장치다.

개념 — 동적 할당과 그 짝

지금까지 객체는 Sensor s("라이다", true);처럼 변수로 만들었다. 이렇게 만든 객체는 스코프를 벗어나면 저절로 사라진다(9회 ③절). new Sensor(...)는 다르다. 스코프와 무관하게 살아 있는 객체를 만들고 그 주소(포인터)를 돌려준다. 이것을 동적 할당(dynamic allocation)이라고 한다. 스코프를 벗어나도 안 사라지므로 다 쓴 뒤 사람이 delete로 지워야 한다. 지우지 않은 객체는 프로그램이 끝날 때까지 메모리를 차지하는데, 이것을 메모리 누수(memory leak)라고 한다. 

Sensor * s = new Sensor("라이다", true);   // 만든다 — 주소를 받는다
s->start();                                 // 포인터로 멤버를 부를 때는 ->
delete s;                                   // 지운다 — 소멸자가 불리고 메모리가 반납된다

규칙은 「new 하나에 delete 하나」로 짧다. 어려운 것은 함수를 빠져나가는 길이 하나가 아니라는 것이다. 중간에 return이 있으면 그 길에도 delete가 있어야 하고, 나중에 return을 하나 더 넣으면 delete도 하나 더 넣어야 한다.

읽는 법

  • 먼저 new와 delete로 짠다. AI에게 그냥 시키면 흔히 받는 모양이다. 돌아가지만 한쪽 길에서 샌다.
  • ②절부터는 절마다 「개념」이 먼저 온다 — 그 문법이 무엇이고 어떤 문제를 풀려고 생겼는지. 그다음 「예제에 적용」에서 지금 프로그램의 어디가 불편한지를 보고, 그 문법으로 고친다.
  • 고치는 자리는 고치기 전(붉은 테두리)과 고친 뒤(푸른 테두리)를 따로 놓는다. 더하기만 하는 단계는 더한 뒤의 모양만 보인다.
  • 그 아래 📄 「전체 코드」 상자를 누르면 그 단계의 main.cpp 전체가 나온다. 첫 줄 주석에 버전(v1, v2, …)이 있다. 어느 버전을 펼쳐도 그대로 빌드되고 돌아간다.
  • 컴파일 오류나 실행 오류를 보이는 자리는 한 곳만 일부러 고장 낸 변형 파일이다. 그것도 전체를 상자에 뒀다.
  • 「실제로 나온 출력」에는 그 절이 새로 찍는 줄만 보인다. 전체 출력은 실습 「성공 화면」에 한 번 있다.
  • 빌드는 CMake다. 파일이 main.cpp 하나라 CMakeLists.txt는 끝까지 안 바뀐다(③절의 변형 하나만 두 줄이 더 있다).

② RAII — 스마트 포인터를 직접 만든다 🟡 맡기되 검사

개념 — delete를 소멸자가 하게 한다

return마다 delete를 챙기는 대신 쓸 수 있는 사실이 하나 있다. 9회 ③절에서 본 대로 변수로 만든 객체의 소멸자는 스코프를 벗어날 때 반드시 불린다 — 끝까지 가서 나가든, 중간의 return으로 나가든 마찬가지다. 그러면 주소를 들고 있다가 자기 소멸자에서 delete하는 작은 클래스를 하나 만들고, 그 클래스를 변수로 두면 된다. 모양은 이렇다. 

class 이름
{
public:
  이름(T * p) : p_(p) {}      // 생성자 — 주소를 받아 둔다
  ~이름() { delete p_; }      // 소멸자 — 받아 둔 것을 지운다
private:
  T * p_;
};

이 클래스의 변수가 사라지는 순간 소멸자가 불리고, 소멸자가 delete한다. 사람이 delete를 적는 자리가 코드에서 없어진다. 이렇게 주소를 맡아 두었다가 자기가 사라질 때 지워 주는 클래스를 스마트 포인터(smart pointer)라고 한다.

메모리만 그런 것이 아니다. 열어 둔 파일처럼 쓰고 나면 돌려줘야 하는 것을 통틀어 자원(resource)이라고 하는데, 자원을 객체의 생성자에서 얻고 소멸자에서 돌려주는 이 설계 방식을 RAII라고 부른다. Resource Acquisition Is Initialization(자원 획득이 곧 초기화)의 약자인데, 이름보다 「소멸자가 돌려준다」 한 줄이 중요하다. 표준 라이브러리의 std::vector·std::string도 이렇게 만들어져 있고, 파일을 쓰는 std::ofstream은 생성자에서 파일을 열고 소멸자에서 닫는다. 그래서 close()를 직접 부르지 않아도 스코프를 벗어나는 순간 파일이 닫힌다.

해석: 코드에서 delete가 사라졌는데 두 센서가 다 꺼졌다. 카메라는 중간의 return으로 나갔지만 그 순간 s의 소멸자가 불렸고, 그 소멸자가 delete했다. 줄이 줄어든 것이 이득의 전부가 아니다. 나가는 길을 하나 더 만들어도 고칠 것이 없다 — 사람이 챙겨야 하는 항목 하나가 아예 사라졌다.

③ 복사 생성자와 = delete — 지울 책임을 진 객체는 복사를 막는다 🔴 사람이 한다

개념 — 복사도 생성자가 한다

SensorPtr b = a;처럼 객체를 다른 객체의 사본으로 만들 때도 생성자가 불린다. 이것을 복사 생성자(copy constructor)라고 하고, 모양은 SensorPtr(const SensorPtr & o) — 같은 타입을 const 참조로 받는 생성자다. 직접 안 쓰면 컴파일러가 멤버를 하나씩 그대로 복사하는 복사 생성자를 만들어 준다. a = b처럼 이미 있는 객체에 대입할 때도 같은 일을 하는 함수(복사 대입 연산자, operator=)가 만들어진다.

대부분은 그것으로 충분하다. 그런데 SensorPtr의 멤버는 주소 하나다. 멤버를 그대로 복사하면 a와 b가 같은 주소를 들게 되고, 둘 다 사라질 때 둘 다 delete한다 — 같은 객체를 두 번 지운다. 이미 지운 메모리를 다시 건드리는 일이라 무슨 일이 일어날지 정해져 있지 않다.

해결은 복사를 아예 못 하게 막는 것이다. 함수 선언 뒤에 = delete를 붙이면 「이 함수는 없다, 부르는 코드가 있으면 컴파일을 멈춰라」는 뜻이 된다. 

  SensorPtr(const SensorPtr &) = delete;               // 복사 생성자를 막는다
  SensorPtr & operator=(const SensorPtr &) = delete;   // 복사 대입도 막는다

④ unique_ptr와 make_unique — 방금 만든 것이 표준에 있다 🟡 맡기되 검사

개념 — SensorPtr의 표준판, 그리고 소유권

②·③절에서 만든 것 — 생성자에서 주소를 받고, 소멸자에서 delete하고, 복사는 막은 클래스 — 이 표준 라이브러리에 이미 있다. <memory> 헤더의 std::unique_ptr<T>다. 템플릿이라 Sensor뿐 아니라 어떤 타입이든 맡을 수 있고, get()을 거치지 않고 p->ok()로 바로 쓸 수 있다. 짝으로 쓰는 std::make_unique<T>(인자…)는 new T(인자…)와 unique_ptr로 감싸는 일을 한 번에 한다. 그래서 코드에 new도 delete도 안 보인다.

「이 객체를 지울 책임이 누구에게 있나」를 소유권(ownership)이라고 한다. unique_ptr는 이름 그대로 소유자가 하나인 스마트 포인터다. 복사가 막혀 있으니 소유자가 둘이 될 수 없다.

그러면 만든 곳과 쓰는 곳이 다를 때는 어떻게 하나? 이런 일은 대개 함수를 부를 때 생긴다. 센서는 main이 만들었는데 그것을 맡아 돌리는 것은 다른 함수인 경우다. unique_ptr를 값으로 받는 매개변수에 그냥 넘기면 매개변수를 복사로 만들어야 하므로 막힌다. 복사 대신 std::move를 쓴다. run(std::move(a))는 「a는 이제 안 쓴다」는 표시이고, unique_ptr는 이 표시를 보면 들고 있던 주소를 매개변수에 넘기고 자기는 빈 포인터(nullptr)가 된다. 객체는 그대로 하나이고 소유자만 바뀐다. 이것을 이동(move)이라고 한다. 넘겨준 a는 비어 있으므로 그 뒤로 a를 쓰지 않는다.

함수가 그 객체로 무엇을 하느냐에 따라 넘기는 모양이 달라진다. 보통은 아래 셋 중 하나다.

⑤ shared_ptr — 소유자가 여럿일 때만 🔴 사람이 한다

개념 — 소유자 수를 세다가 마지막이 지운다

한 객체를 여러 곳이 같이 쓰고, 누가 마지막까지 쓸지 미리 알 수 없는 경우가 있다. 이때는 소유자를 하나로 정할 수 없다. std::shared_ptr<T>는 복사가 된다. 대신 지금 소유자가 몇인지 — 참조 횟수(reference count) — 를 세어 두고, 소유자가 하나 사라질 때마다 하나씩 줄이다가 0이 되는 순간 지운다. 만들 때는 std::make_shared<T>(인자…)를 쓴다.

std::unique_ptr<T>std::shared_ptr<T>
소유자하나여럿
복사안 된다 (컴파일 오류)된다 — 복사할 때마다 소유자가 하나 는다
함수에 값으로 넘기면std::move가 있어야 한다 — 넘긴 쪽은 빈다복사된다 — 넘긴 쪽도 계속 소유자다
언제 지워지나소유자가 사라질 때참조 횟수가 0이 될 때 — 마지막 소유자가 사라질 때
만드는 법std::make_unique<T>(인자…)std::make_shared<T>(인자…)
비용맨 포인터와 같다소유자 수를 여러 스레드에서 안전하게 세느라 복사하고 지울 때마다 비용이 든다

함수에 넘길 때 이 차이가 그대로 드러난다. shared_ptr를 값으로 받는 함수에 넘기면 매개변수가 복사본이 되어 함수가 도는 동안 소유자가 하나 늘고, 함수가 끝나면 다시 준다. 부른 쪽도 계속 소유자이므로 ④-2처럼 처리 결과를 돌려받을 필요가 없다 — 둘이 같은 객체를 보고 있어서 함수가 한 일은 부른 쪽에서도 그대로 보인다. 부른 쪽이 더 쓰지 않을 거면 std::move로 넘길 수도 있다. 그러면 복사 없이 함수가 소유권을 받고, 그 함수가 마지막 소유자라면 함수가 끝날 때 지운다.

AI는 「메모리를 안전하게 관리해 줘」라고 하면 shared_ptr을 주는 경우가 많다. 돌아가고 새지도 않는다. 그런데 대개 필요 없는 선택이다. 비용보다 더 중요한 것은 코드가 말하는 내용이다 — shared_ptr이 보이면 읽는 사람은 「여러 곳이 같이 쓰는구나」라고 이해한다. 실제로는 한 곳만 쓰는데 shared_ptr이면 코드가 읽는 사람을 헷갈리게 한다.

무엇을 먼저 볼지: 왼쪽 두 질문에 답하는 순서가 곧 고르는 순서다. 첫 줄을 빠뜨리기 쉽다.

// 11회 센서 켜고 끄기 — v5 (5단계: 소유자가 여럿이면 shared_ptr)
#include <iostream>
#include <memory>
#include <string>

class Sensor
{
public:
  Sensor(const std::string & n, bool ok) : n_(n), ok_(ok) { std::cout << "  [" << n_ << " 켜짐]\n"; }
  ~Sensor() { std::cout << "  [" << n_ << " 꺼짐]\n"; }
  bool ok() const { return ok_; }
  void start() { std::cout << "  " << n_ << " 측정 시작\n"; }
  const std::string & name() const { return n_; }
private:
  std::string n_;
  bool ok_;
};

// 센서 하나를 켜고, 상태가 나쁘면 그만두고, 좋으면 측정을 시작한다
void setup(const std::string & name, bool ok)
{
  std::unique_ptr<Sensor> s = std::make_unique<Sensor>(name, ok);   // 표준 스마트 포인터
  if (!s->ok()) {
    std::cout << "  " << name << " 상태 불량 — 그만둔다\n";
    return;
  }
  s->start();
}

// 센서를 맡아서 끝까지 쓰는 함수 — 소유권을 받아 간다
void run(std::unique_ptr<Sensor> s)
{
  s->start();
  std::cout << "  run 이 끝난다\n";
}   // 여기서 매개변수 s 가 사라지며 센서를 지운다

// 센서를 받아 처리한 뒤 돌려주는 함수 — 소유권을 받았다가 다시 넘겨준다
std::unique_ptr<Sensor> warm_up(std::unique_ptr<Sensor> s)
{
  std::cout << "  " << s->name() << " 예열 끝\n";
  return s;                // 돌려줄 때는 std::move 를 쓰지 않는다
}

// 센서를 같이 쓰는 함수 — 값으로 받으면 shared_ptr 가 복사되어 소유자가 하나 는다
void use_shared(const std::string & who, std::shared_ptr<Sensor> cam)
{
  std::cout << "  " << who << ": " << cam->name() << " 사용 중 (참조 횟수 " << cam.use_count() << ")\n";
}   // 여기서 매개변수 cam 이 사라진다. 참조 횟수가 0 이 되었을 때만 지운다

{
  std::cout << "① 나가는 길이 둘인 함수\n";
  setup("라이다", true);
  setup("카메라", false);

  std::cout << "\n④-1 unique_ptr 를 함수에 넘겨주고 끝 — 함수가 지운다\n";
  {
    std::unique_ptr<Sensor> a = std::make_unique<Sensor>("라이다", true);
    run(std::move(a));                                  // 소유권이 a 에서 run 의 s 로 간다
    std::cout << "  돌아온 뒤 a 는 비었나? " << (a == nullptr ? "그렇다" : "아니다") << "\n";
  }

  std::cout << "\n④-2 unique_ptr 를 넘겼다가 처리 결과로 돌려받는다\n";
  {
    std::unique_ptr<Sensor> b = std::make_unique<Sensor>("카메라", true);
    b = warm_up(std::move(b));                          // 넘겼다가 돌려받아 다시 b 에 담는다
    std::cout << "  돌려받은 b 로 계속 쓴다: " << b->name() << "\n";
  }
  std::cout << "  중괄호를 나오자 b 가 지웠다\n";

  std::cout << "\n⑤ shared_ptr 를 함수에 넘긴다 — 마지막 소유자가 지운다\n";
  {
    std::shared_ptr<Sensor> p = std::make_shared<Sensor>("카메라", true);
    std::cout << "  참조 횟수 = " << p.use_count() << "\n";
    use_shared("주행 모듈", p);                          // 복사해서 넘긴다. p 도 계속 소유자다
    std::cout << "  돌아온 뒤 참조 횟수 = " << p.use_count() << ", p 로 계속 쓴다: " << p->name() << "\n";
    use_shared("기록 모듈", std::move(p));               // 더 안 쓸 거면 넘겨준다. 이제 함수가 마지막 소유자다
    std::cout << "  돌아온 뒤 p 는 비었나? " << (p == nullptr ? "그렇다" : "아니다") << "\n";
  }
  return 0;
}
해석: 주행 모듈에서는 1 → 2 → 1이다. 함수가 도는 동안 매개변수 cam이 소유자 하나를 더했고, 함수가 끝나 cam이 사라질 때는 꺼지지 않았다 — 아직 p가 소유자이기 때문이다. 돌려받지 않았는데도 p로 그대로 쓴다. 기록 모듈에는 std::move(p)로 넘겼으니 복사가 없어 횟수가 1 그대로이고, 이제 cam이 마지막 소유자다. 그래서 [카메라 꺼짐]이 main으로 돌아오기 전에 찍혔다 — ④-1의 run과 같은 모양이다.
이 코드에서 shared_ptr을 쓴 자리마다 소유자가 정말 여럿인지 확인해 줘. 한 곳만 쓰는 것은 unique_ptr로 바꾸고, 포인터가 아예 필요 없는 자리는 그냥 변수로 바꿔 줘. 왜 바꿨는지 한 줄씩 적어 줘.

⑥ 타입 별칭 — using으로 긴 타입에 짧은 이름을 붙인다 🟡 맡기되 검사

개념 — 새 타입이 아니라 같은 타입의 다른 이름

std::shared_ptr<sensor_msgs::msg::LaserScan>처럼 타입 이름이 길어지면 줄 하나가 화면을 넘어간다. 타입 별칭(type alias)은 using 새이름 = 원래타입;으로 같은 타입에 다른 이름을 붙이는 것이다. 새 타입이 생기는 것이 아니라서 원래 이름으로 만든 것과 별칭으로 만든 것을 서로 대입할 수 있다. 별칭을 클래스 안에 두면 클래스::별칭으로 부른다 — 7회의 범위 지정 연산자 ::가 여기서 다시 쓰인다. 만들 일은 드물지만 읽을 일은 아주 많다.

예제에 적용 — 스캔 구조체를 넣고 별칭을 하나 붙인다

#include <iostream>
#include <memory>
#include <string>

class Battery
{
public:
  Battery() : volt_(11.8f) { std::cout << "  [Battery 생성]\n"; }
  ~Battery() { std::cout << "  [Battery 소멸자]\n"; }
  float read() const { return volt_; }
private:
  float volt_;
};

class Logger
{
public:
  Logger(const std::string & name) : name_(name) { std::cout << "  [" << name_ << " 기록 시작]\n"; }
  ~Logger() { std::cout << "  [" << name_ << " 기록 끝]\n"; }
  void note(const std::string & s) { std::cout << "  " << name_ << ": " << s << "\n"; }
private:
  std::string name_;
};

// 전압 한 줄을 파일에 남긴다. dry_run 이면 아무것도 안 쓰고 나간다
bool log_once(bool dry_run)
{
  Battery * b = new Battery();
  std::ofstream f("health_log.txt", std::ios::app);
  if (dry_run) { return false; }
  f << "battery = " << b->read() << "\n";
  f.close();
  delete b;
  return true;
}

int main()
{
  std::shared_ptr<Logger> log = std::make_shared<Logger>("health");   // 쓰는 곳은 main 하나뿐이다
  std::ofstream("health_log.txt");             // 파일을 비운다
  std::cout << "① 기록\n";      log_once(false);
  std::cout << "② 연습 실행\n"; log_once(true);

  std::ifstream in("health_log.txt");          // 파일을 읽기용으로 연다
  std::string line;
  while (std::getline(in, line)) { log->note("파일: " + line); }   // 한 줄씩 읽는다
  return 0;
}

✅ 오늘의 점검

조금 더 알아두면 시험 범위 아님

이동은 클래스 안에서 어떻게 만들어지나 — 이동 생성자와 &&

복사에 복사 생성자가 있듯이 이동에는 이동 생성자(move constructor)가 있다. 모양은 T(T && o)이고, &&는 「곧 버려질 값」을 받는 참조(우측값 참조)다. unique_ptr는 이 생성자 안에서 상대의 주소를 가져오고 상대를 nullptr로 비운다. std::move(a)는 a를 「곧 버려질 값」으로 표시해 이 생성자가 골라지게 할 뿐, 스스로 아무것도 옮기지 않는다.

표준 라이브러리 타입(vector·string·스마트 포인터)은 이동 생성자를 이미 갖고 있으므로 직접 만들 일은 드물다. AI 코드에 T(T && o) noexcept가 보이면 「이동 생성자구나」하고 읽을 수 있으면 충분하다.

왜 돌려줄 때는 std::move를 쓰지 않나 — return s;

std::move는 「이 변수는 이제 안 쓴다」는 표시다. 부르는 쪽의 warm_up(std::move(b))에서는 컴파일러가 그 줄 뒤에 b를 또 쓸지 알 수 없으므로 사람이 표시해 줘야 한다. 돌려주는 쪽의 return s;는 다르다. 그 줄이 끝나면 s는 바로 사라지므로 아무도 다시 볼 수 없다는 것을 컴파일러가 안다. 그래서 지역 변수나 매개변수 이름 하나를 돌려줄 때는 컴파일러가 알아서 이동한다. 붙여도 같은 일을 할 뿐이고, 지역 변수라면 오히려 컴파일러의 최적화를 막을 수도 있다.

단, 함수가 끝나도 남아 있는 것을 돌려줄 때는 이야기가 다르다. 클래스 안에서 멤버를 돌려주는 return s_;는 복사로 본다. 소유권을 넘겨줄 생각이면 return std::move(s_);라고 써야 한다. unique_ptr라면 빠뜨렸을 때 컴파일 오류가 나므로 빌드에서 알 수 있다.

make_shared가 shared_ptr(new T)보다 나은 이유

shared_ptr은 객체 말고 참조 횟수를 둘 자리도 따로 필요하다. std::shared_ptr<Sensor> p(new Sensor(...))라고 쓰면 메모리를 두 번 잡는다 — 객체 한 번, 참조 횟수 한 번. std::make_shared<Sensor>(...)는 둘을 한 번에 잡는다. 쓰는 모양도 더 짧고 코드에 new가 안 보이므로 고민할 이유가 없다.

서로를 가리키면 아무도 안 지워진다 (순환 참조)

shared_ptr은 참조 횟수가 0이 될 때 객체를 지운다. 그런데 A가 B를 잡고 B가 A를 잡으면 둘 다 영원히 1 이상이다. 둘을 쓰던 코드가 다 끝나도 둘 다 안 지워진다. 이것이 스마트 포인터를 쓰고도 메모리가 새는 거의 유일한 경우다. 해결하는 도구(std::weak_ptr)가 표준에 있지만, 이 과목의 코드에서는 그런 구조를 만들지 않는 것이 답이다.

파이썬이나 자바에는 쓰레기 수집기(garbage collector)가 있다. 안 쓰는 메모리를 나중에 알아서 회수해 준다. 편하지만 두 가지가 다르다.
