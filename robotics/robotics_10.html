상속·다형성과 RAII — 뒷정리를 사람이 하지 않는다

오늘 답할 질문
  1. ROS 2 예제 첫 줄의 class MyNode : public rclcpp::Node — 이 콜론은 무슨 뜻인가?
  2. override는 안 써도 컴파일이 되는데 왜 붙이라고 하나?
  3. 소멸자에 virtual을 안 붙였을 뿐인데 왜 메모리가 새나? 그런데 왜 아무 오류도 안 나나?
  4. C++ 코드에는 왜 delete가 거의 안 보이나?

오늘 배울 것은 둘이다. 앞의 셋은 상속과 다형성이고, 뒤의 하나는 RAII다. 성격이 달라 보이지만 한 줄로 이어진다. 둘 다 「객체가 사라질 때 무슨 일이 일어나는가」의 이야기다.

그중 세 번째 질문이 이 회차의 핵심이다. 가상 소멸자를 빠뜨린 코드는 크래시도 안 나고 경고 한 줄도 안 뜬다. 그냥 조용히 메모리가 샌다. 그래서 이 버그는 몇 달씩 살아남는다. 그리고 AI가 기반 클래스를 만들어 줄 때 가장 자주 빠뜨리는 자리가 정확히 여기다.

마지막 질문의 답이 RAII다. 한 문장으로 하면 "객체가 사라질 때 뒷정리가 자동으로 된다"이다. 이 순서에는 이유가 있다 — RAII를 먼저 이해해야 12회의 스마트 포인터가 「왜 있는지」가 설명된다. 스마트 포인터는 새로운 발명이 아니라 오늘 배우는 이 원리를 메모리에 적용한 것뿐이다.

한 장 요약 — 학기가 끝나도 이 표만 남으면 된다

무엇을 먼저 볼지: 가운데 「빠뜨리면」 열만 읽어도 검사 목록이 된다.

이게 보이면빠뜨리면 어떻게 되나수준
class B : public A—. A가 하던 것을 B가 물려받는다는 뜻이다[알아보기]
virtual float read()하위 클래스 것이 안 불린다. 위쪽 것이 그대로 불린다[판단]
float read() override이름을 오타 내도 컴파일이 통과한다. 실행하면 답이 틀린다[요구]
🔴 virtual ~Sensor()하위 클래스 소멸자가 아예 안 불린다. 오류도 크래시도 없다[요구]
{ } 중괄호—. 벗어나는 순간 안에서 만든 것의 소멸자가 불린다[판단]
std::ofstream · std::lock_guardclose()·unlock()을 안 불러도 된다. 부르면 오히려 실수한다[판단]
new / delete가 보인다나가는 길이 늘어날 때마다 짝 맞추기를 사람이 해야 한다[요구]
해석: 굵게 표시한 네 번째 줄이 오늘의 중심이다. 나머지는 빠뜨리면 컴파일러가 알려 주거나 결과가 눈에 띄게 이상해진다. 가상 소멸자만 다르다. 아무 일도 안 일어난 것처럼 보인다. 그래서 검사 목록에 올려 두지 않으면 영원히 못 찾는다.

① 종류가 늘어날 때마다 if 문을 고치고 싶지 않다 🟡 맡기되 검사

언제 이게 필요해지나

센서가 여럿이다. 라이다도 있고 초음파도 있다. 밖에서 하고 싶은 일은 하나다 — "값을 읽어라." 센서 종류가 무엇인지는 알고 싶지 않다.

기존 방법으로는 왜 안 되나

배운 것만 가지고 짜면 이렇게 된다.

종류를 밖에서 따지는 코드 🔴
float read_any(int kind, const Lidar & l, const Sonar & s)
{
  if (kind == 0) { return l.read(); }
  else if (kind == 1) { return s.read(); }
  return -1.0f;
}

돌아가긴 한다. 문제는 센서를 하나 더 붙이는 순간이다. 이런 if가 프로젝트 여기저기에 열 군데쯤 흩어져 있고, 열 군데를 다 찾아 고쳐야 한다. 하나를 놓치면 그 자리만 조용히 옛 동작을 한다. kind라는 숫자를 사람이 관리해야 하는 것도 실수의 자리다.

그래서 이렇게 한다

"모든 센서는 read()를 갖는다"를 클래스 하나로 못 박아 놓고, 각 센서가 그것을 물려받게 한다. 이것이 상속이다.

물려받는 코드
class SensorBad {
public:
  virtual float read() = 0;      // "읽는 함수는 반드시 있다. 내용은 자식이 채운다"
};

class LidarBad : public SensorBad {
public:
  float read() override { return buf_.at(0); }
private:
  std::vector<float> buf_;
};

🆕 이 코드에서 처음 나오는 것

class LidarBad : public SensorBad
콜론 뒤가 물려받을 클래스다. LidarBad는 SensorBad가 약속한 것을 전부 갖고 시작한다. 여기서는 "라이다도 센서다"를 코드로 적은 것이다.
virtual float read()
"이 함수는 자식이 갈아 끼울 수 있다"는 표시다. 여기서는 밖에서 SensorBad로 불러도 실제로는 LidarBad의 것이 불리게 만드는 데 썼다.
= 0 (순수 가상)
뒤에 = 0이 붙으면 내용이 아예 없다는 뜻이다. 여기서는 "읽는 함수는 반드시 있어야 한다. 다만 어떻게 읽는지는 센서마다 다르다"를 강제하는 데 썼다. 하나라도 안 채우면 그 클래스는 객체를 만들 수 없다.
float read() override
"위에 있는 read()를 갈아 끼우는 중이다"라고 컴파일러에게 알린다. 안 써도 동작은 같다. 왜 굳이 쓰는지는 ③절에서 실험으로 확인한다.
바뀐 것if 문 방식상속 방식
센서를 하나 더 붙이면if가 있는 모든 자리를 고친다새 클래스 하나만 만든다
빠뜨리면조용히 옛 동작을 한다= 0을 안 채우면 컴파일이 안 된다
종류를 나타내는 숫자사람이 관리한다 (kind == 0)없다
해석: 이득은 코드가 짧아진 것이 아니다. 실수할 자리가 컴파일 오류로 바뀐 것이다. if 문 방식은 빠뜨려도 프로그램이 돈다. 상속 방식은 빠뜨리면 빌드가 멈춘다. 이 강의에서 "좋은 코드"는 대체로 이런 뜻이다 — 틀렸을 때 조용하지 않은 코드.
센서 종류를 if / else if 로 나눠 처리하는 코드가 있어. 기반 클래스 하나를 만들고 종류마다 상속하는 구조로 바꿔 줘. 기반 클래스의 소멸자는 virtual 로, 자식 쪽 함수에는 override 를 붙여 줘. 바뀌는 부분만 보여 줘.
📌 ROS 2 에서 이 문법을 만나는 자리
class MyNode : public rclcpp::Node
{
  // ...
};

ROS 2에서 노드를 만드는 코드는 거의 예외 없이 이 한 줄로 시작한다. rclcpp::Node가 이미 만들어 놓은 것(이름 짓기, 발행, 구독, 파라미터)을 통째로 물려받고, 우리는 우리 것만 얹는다. 지금은 이 콜론이 무슨 뜻인지만 알면 된다. 19회에서 제대로 다룬다.

② virtual은 「여기는 갈아 끼울 수 있다」는 표시다 🟡 맡기되 검사

virtual이 붙은 함수와 안 붙은 함수는 불리는 방식이 다르다. 밖에서 SensorBad *로 잡아 놓고 read()를 부를 때,

기반 클래스의 함수가실제로 불리는 것언제 정해지나
virtual이 붙어 있다진짜 들어 있는 물건의 함수 (LidarBad::read)실행할 때
virtual이 없다잡고 있는 손잡이의 함수 (SensorBad::read)컴파일할 때
해석: "손잡이"와 "물건"이 다를 수 있다는 것이 요점이다. SensorBad *는 손잡이고 실제로 매달린 것은 LidarBad다. virtual은 "손잡이 말고 물건을 보고 정하라"는 뜻이다. 이 한 줄이 ④절의 가상 소멸자 이야기 전체를 미리 설명한다 — 소멸자도 함수이기 때문이다.

그런데 위 코드처럼 = 0을 붙여 내용을 아예 비워 두면 한 가지가 더 따라온다. 그 클래스로는 객체를 만들 수 없다. 만들려고 하면 이런 오류가 난다. 

error: invalid new-expression of abstract class type ‘LidarBad’

abstract class는 "채워야 할 칸이 남아 있는 클래스"라는 뜻이다. = 0인 함수를 하나라도 안 채웠다는 신호이므로, 이 메시지가 뜨면 자식 클래스에서 함수 이름을 잘못 적지 않았는지부터 본다. 바로 다음 절이 그 이야기다.

③ override 한 단어가 오타를 컴파일 오류로 바꾼다 🟡 맡기되 검사

실험 1 — override가 붙어 있을 때 오타를 내면

read()를 raed()로 잘못 쳤다고 하자. 한 글자다. 실제로 그렇게 고쳐서 컴파일해 본 화면이다. 

$ g++ -std=c++17 -o t t.cpp
t.cpp:18:9: error: ‘float LidarBad::raed()’ marked ‘override’, but does not override
   18 |   float raed() override { return buf_.at(0); }
      |         ^~~~
t.cpp:34:9: error: ‘float LidarGood::raed()’ marked ‘override’, but does not override
   34 |   float raed() override { return buf_.at(0); }
      |         ^~~~

어느 줄을 보나: marked ‘override’, but does not override가 전부다. "네가 override라고 적었는데, 위에 그런 이름의 함수가 없다"는 뜻이다. 실행하기 전에, 그것도 정확한 줄 번호와 함께 잡혔다.

실험 2 — override가 없을 때 같은 오타를 내면

같은 오타인데 override만 뗀 코드다. 이번엔 기반 클래스에 기본 동작을 넣어 뒀다.

#include <iostream>
#include <memory>

class Sensor {
public:
  virtual ~Sensor() {}
  virtual float read() { return -1.0f; }   // 기반 클래스의 기본 동작
};

class LidarTypo : public Sensor {
public:
  float raed() { return 0.83f; }           // 오타. override 를 안 붙였다
};

class LidarOverride : public Sensor {
public:
  float read() override { return 0.83f; }  // 여기서 오타를 내면 컴파일이 멈춘다
};

int main()
{
  std::unique_ptr<Sensor> a = std::make_unique<LidarTypo>();
  std::unique_ptr<Sensor> b = std::make_unique<LidarOverride>();
  std::cout << "override 를 안 붙인 쪽 read() = " << a->read() << "\n";
  std::cout << "override 를 붙인 쪽   read() = " << b->read() << "\n";
  return 0;
}
$ g++ -std=c++17 -Wall -o override_typo override_typo.cpp
$ ./override_typo
override 를 안 붙인 쪽 read() = -1
override 를 붙인 쪽   read() = 0.83
⚠️ 경고 한 줄 없이 통과했다

-Wall(모든 경고 켜기)을 붙였는데도 아무 말이 없다. 컴파일러 입장에서는 틀린 것이 없다 — raed()라는 새 함수를 하나 만든 것일 뿐이니까.

결과만 다르다. 실제 거리는 0.83 m인데 -1이 나왔다. 기반 클래스의 기본값이 그대로 나온 것이다. 로봇에서 이런 일이 나면 "센서가 고장 났나"부터 의심하게 된다. 원인은 한 글자짜리 오타이고, 그것을 찾는 데 반나절이 든다.

override가 있을 때override가 없을 때
이름을 잘못 쳤다컴파일이 멈춘다 — 줄 번호까지 나온다통과한다. 경고도 없다
인자 타입을 잘못 썼다컴파일이 멈춘다통과한다
실행하면—기반 클래스의 값이 나온다. 그게 답인 줄 안다
드는 비용한 단어없음
해석: override는 동작을 바꾸지 않는다. 하는 일은 하나뿐이다 — "내 의도는 갈아 끼우는 것이었다"를 코드에 적어 두는 것. 그 한 줄 덕분에 의도와 실제가 어긋나는 순간 컴파일러가 멈춰 준다. 한 단어를 적어서 반나절을 사는 거래다.
이 코드에서 기반 클래스의 함수를 갈아 끼우는 함수 전부에 override 를 붙여 줘. 붙였더니 컴파일이 안 되는 곳이 있으면 고치지 말고 먼저 알려 줘 — 거기가 진짜 버그일 수 있어.

④ 가상 소멸자가 없으면 소멸자가 아예 안 불린다 🔴 사람이 한다

여기가 이 회차의 핵심이다. 같은 코드를 두 벌 만들어 놓고 virtual 한 단어만 다르게 해서 실제로 돌려 봤다. 아래가 그 프로그램 전체다.

examples/l10_raii/virtual_dtor.cpp — 전체
// 10회 — 가상 소멸자가 없으면 무슨 일이 생기나
// 두 경우를 한 프로그램에서 나란히 돌려 출력을 비교한다.
#include <iostream>
#include <memory>
#include <vector>

// ── ① 기반 클래스에 virtual 소멸자가 없다 ──────────────────
class SensorBad {
public:
  virtual float read() = 0;
  ~SensorBad() { std::cout << "  [SensorBad 소멸자]\n"; }   // virtual 이 없다
};

class LidarBad : public SensorBad {
public:
  LidarBad() : buf_(360, 0.0f) { std::cout << "  [LidarBad 생성] 360칸 확보\n"; }
  ~LidarBad() { std::cout << "  [LidarBad 소멸자] 360칸 반납\n"; }
  float read() override { return buf_.at(0); }
private:
  std::vector<float> buf_;
};

// ── ② 같은 코드에 virtual 만 붙였다 ────────────────────────
class SensorGood {
public:
  virtual float read() = 0;
  virtual ~SensorGood() { std::cout << "  [SensorGood 소멸자]\n"; }
};

class LidarGood : public SensorGood {
public:
  LidarGood() : buf_(360, 0.0f) { std::cout << "  [LidarGood 생성] 360칸 확보\n"; }
  ~LidarGood() override { std::cout << "  [LidarGood 소멸자] 360칸 반납\n"; }
  float read() override { return buf_.at(0); }
private:
  std::vector<float> buf_;
};

int main()
{
  std::cout << "① virtual 소멸자가 없는 경우\n";
  {
    std::unique_ptr<SensorBad> s = std::make_unique<LidarBad>();
    s->read();
  }
  std::cout << "② virtual 소멸자를 붙인 경우\n";
  {
    std::unique_ptr<SensorGood> s = std::make_unique<LidarGood>();
    s->read();
  }
  return 0;
}

🆕 이 코드에서 처음 나오는 것

std::unique_ptr<SensorBad> s = std::make_unique<LidarBad>();
손잡이는 SensorBad인데 실제로 매달린 물건은 LidarBad인 상황을 만드는 줄이다. make_unique가 물건을 만들고, unique_ptr가 그것을 붙잡는다. 중괄호를 벗어나면 붙잡고 있던 것을 알아서 지운다 — 그래서 이 예제에 쓴 것이다. 지금은 모양만 봐 두면 된다.
buf_(360, 0.0f)
생성자 옆의 초기화 자리에서 값 0.0f짜리 칸 360개를 만든다. 여기서는 "소멸자가 안 불리면 이만큼이 안 돌아온다"를 눈에 보이게 하려고 360으로 뒀다 — 터틀봇3 라이다가 한 바퀴에 주는 값의 개수와 같은 숫자다.
buf_.at(0)
배열의 0번째 값을 꺼낸다. buf_[0]과 하는 일이 같은데, 범위를 벗어나면 그 자리에서 알려 준다는 점이 다르다. 여기서는 라이다 값을 하나 읽는 시늉만 하는 데 썼다.
std::cout << "…"
화면에 찍는다. <<를 이어 붙이면 여러 개를 차례로 내보낸다. 여기서는 생성자와 소멸자가 언제 불리는지를 눈으로 보려고 썼다.

⚠️ 「LidarBad 소멸자」 줄이 아예 안 찍혔다

①에서 찍힌 줄은 둘이고 ②에서 찍힌 줄은 셋이다. 없는 줄은 [LidarBad 소멸자] 360칸 반납이다. 그 소멸자가 불리지 않았다. float 360칸이 그대로 남았고 프로그램이 끝날 때까지 돌아오지 않았다.

그런데 화면 어디에도 오류 메시지가 없다. 크래시도 없다. 종료 코드도 정상이다. "동작한다"는 기준으로 보면 ①은 통과한 프로그램이다.

그래서 이 버그는 오래 산다. 콘솔 프로그램에서는 몇 초 뒤 프로그램이 끝나면서 운영체제가 어차피 다 회수하므로 아무도 눈치채지 못한다. 문제는 몇 시간씩 돌아야 하는 로봇 노드에서 터진다. 센서 객체를 만들고 지우기를 반복할수록 안 돌아온 360칸이 쌓인다.

왜 그런가 — ②절의 한 줄이 그대로 적용된다

손잡이는 SensorBad이고 물건은 LidarBad다. virtual이 없으면 손잡이를 보고 정한다. 그래서 SensorBad의 소멸자만 불렸다. 소멸자도 함수이기 때문에 규칙이 똑같다.

AI가 보통 주는 기반 클래스 🔴
class SensorBad {
public:
  virtual float read() = 0;
  ~SensorBad() { }              // ← virtual 이 없다
};
한 단어만 붙이면 된다
class SensorGood {
public:
  virtual float read() = 0;
  virtual ~SensorGood() { }     // ← 이것 하나
};
🔴 AI가 하는 실수 — 기반 클래스에 가상 소멸자를 안 붙인다

read()에는 virtual을 잘 붙인다. 소멸자에서만 빠뜨린다. 이유는 짐작할 만하다. 인터넷의 짧은 예제들은 대부분 상속을 동작을 설명하려고 쓰지 수명을 설명하려고 쓰지 않는다. 그런 예제에는 소멸자 자체가 없다. AI는 그 흔한 모양을 재현한다.

그리고 이 실수는 검사로 안 걸린다. 빌드가 되고, 테스트가 통과하고, 로봇도 돈다. 그래서 사람이 눈으로 볼 항목 목록에 넣어 두는 수밖에 없다.

이 코드에 다른 클래스가 상속하는 기반 클래스가 있으면 소멸자에 virtual 이 붙어 있는지 확인해 줘. 안 붙은 곳이 있으면 어느 클래스인지 알려 주고 붙여 줘. 상속을 안 당하는 클래스에는 붙이지 마.

🆕 소멸자 옆에서 보게 되는 것 하나 더

~ScanBuffer() noexcept { … }

class ScanBuffer {

class PlainBuffer {

⑤ RAII — 객체가 사라질 때 뒷정리가 자동으로 된다 🟡 맡기되 검사

앞 절에서 계속 본 것이 있다. 중괄호를 벗어나는 순간 소멸자가 불렸다. 아무도 부르라고 시키지 않았는데 불렸다. 이 성질 하나에 이름을 붙인 것이 RAII다.

한 문장: 객체가 사라질 때 뒷정리가 자동으로 된다.
원래 이름은 Resource Acquisition Is Initialization인데 이 이름은 잊어도 된다. 기억할 것은 「중괄호가 곧 수명이다」 한 줄이다.
examples/l10_raii/raii_scope.cpp — 전체
// 10회 — RAII: 중괄호를 벗어나면 뒷정리가 자동으로 된다
#include <fstream>
#include <iostream>
#include <mutex>
#include <string>

class Talker {
public:
  explicit Talker(std::string n) : n_(std::move(n)) { std::cout << "  " << n_ << " 열림\n"; }
  ~Talker() { std::cout << "  " << n_ << " 닫힘\n"; }
private:
  std::string n_;
};

std::mutex m;

int main()
{
  std::cout << "① 중괄호 하나가 곧 수명이다\n";
  {
    Talker a("바깥");
    {
      Talker b("안쪽");
      std::cout << "  안쪽 중괄호 안이다\n";
    }
    std::cout << "  안쪽을 빠져나왔다\n";
  }

  std::cout << "② 파일도 같은 원리다 — close() 를 부르지 않았다\n";
  {
    std::ofstream f("raii_out.txt");
    f << "라이다 값 0.83\n";
    std::cout << "  파일에 한 줄 썼다\n";
  }
  std::ifstream in("raii_out.txt");
  std::string line; std::getline(in, line);
  std::cout << "  다시 읽어 보니: \"" << line << "\"  → 이미 닫혀서 내용이 저장됐다\n";

  std::cout << "③ 잠금(lock)도 같은 원리다 — unlock() 을 부르지 않았다\n";
  {
    std::lock_guard<std::mutex> g(m);
    std::cout << "  잠근 채로 일하는 중\n";
  }
  std::cout << "  중괄호를 나오면서 자동으로 풀렸다\n";
  return 0;
}

🆕 이 코드에서 처음 나오는 것 (1) — 자원을 잡는 세 가지

std::ofstream f("raii_out.txt")
파일을 쓰기용으로 연다. 이 줄에서 열리고, 중괄호를 나갈 때 닫힌다. 여기서는 close()를 한 번도 부르지 않았는데도 내용이 저장됐다는 것을 보이려고 썼다. 읽기용은 std::ifstream이고 아래 줄에 나온다.
std::mutex m
한 번에 한 사람만 들어가게 하는 자물쇠다. 여러 갈래가 동시에 같은 값을 건드리면 깨지므로, 그 자리를 잠그는 데 쓴다. 여기서는 잠금이 자동으로 풀리는 것을 보여 주기 위한 재료로만 썼다.
std::lock_guard<std::mutex> g(m)
이 줄에서 잠그고 중괄호를 나갈 때 자동으로 푼다. 여기서는 unlock()을 부르지 않았는데도 풀리는 것을 보이려고 썼다. 자물쇠는 안 푸는 실수가 특히 무섭다 — 프로그램이 그 자리에서 영원히 멈춘다.
std::getline(in, line)
파일에서 한 줄을 읽어 line에 담는다. 여기서는 방금 쓴 내용이 실제로 저장됐는지 확인하는 데 썼다.

🆕 이 코드에서 처음 나오는 것 (2) — 클래스 쪽 두 단어

explicit Talker(std::string n)
"이 생성자는 몰래 불리면 안 된다"는 표시다. 안 붙이면 Talker t = "바깥"; 같은 줄이 말없이 통과한다. 인자 하나짜리 생성자에는 붙이는 것이 기본이라고 알아 두면 된다.
std::move(n)
"이 값은 이제 안 쓸 테니 가져가라"는 표시다. 복사하지 않고 알맹이를 옮긴다. 여기서는 생성자가 받은 문자열을 멤버 n_에 넘기면서 복사를 한 번 줄이는 데 썼다. 지금은 이 자리에 이런 것이 오는구나 정도만 보면 된다.

제대로 다루는 곳: 11회(복사와 이동 — std::move와 이동 후의 객체)

⑥ 파일도 잠금도 메모리도 전부 같은 원리다 🟡 맡기되 검사

같은 프로그램의 나머지 두 부분이다. 하는 일은 전혀 다른데 정리되는 방식이 똑같다. 

② 파일도 같은 원리다 — close() 를 부르지 않았다
  파일에 한 줄 썼다
  다시 읽어 보니: "라이다 값 0.83"  → 이미 닫혀서 내용이 저장됐다
③ 잠금(lock)도 같은 원리다 — unlock() 을 부르지 않았다
  잠근 채로 일하는 중
  중괄호를 나오면서 자동으로 풀렸다

잰 곳: 컨테이너(우분투 24.04.4 LTS, g++ 13.3.0)

②를 눈여겨본다. f.close()를 부른 줄이 코드에 없다. 그런데 중괄호를 나온 뒤 파일을 다시 열어 읽었더니 라이다 값 0.83이 그대로 들어 있었다. 중괄호를 나가면서 ofstream의 소멸자가 파일을 닫고 내용을 밀어 넣은 것이다.

③도 마찬가지다. unlock()을 부른 줄이 없는데 잠금이 풀렸다. lock_guard의 소멸자가 대신 풀어 줬다.

무엇을 먼저 볼지: 가운데 「사람이 부르면」 열을 본다. 셋 다 부를 필요가 없다.

무엇을 잡나사람이 부르면안 부르면
메모리 (std::vector·unique_ptr)delete — 빠뜨리면 샌다중괄호를 나갈 때 반납된다
파일 (std::ofstream)close() — 빠뜨리면 내용이 저장 안 될 수 있다중괄호를 나갈 때 닫힌다
잠금 (std::lock_guard)unlock() — 빠뜨리면 프로그램이 멈춘다중괄호를 나갈 때 풀린다
해석: 세 줄이 전부 "안 부르는 쪽이 안전하다"로 끝난다. 이것이 다른 언어를 쓰다 온 사람에게 가장 낯선 대목이다. C++에서는 뒷정리 코드를 안 쓰는 것이 잘 쓴 것이다. 반대로 close()나 unlock()이 코드에 보이면 "왜 직접 부르지?"부터 묻는다. 대개는 필요 없는 줄이다.
이 코드에 close() 나 unlock() 을 직접 부르는 줄이 있으면 알려 줘. 소멸자가 어차피 해 주는 것이면 그 줄을 지우고, 꼭 그 자리에서 불러야 하는 이유가 있으면 지우지 말고 이유를 한 줄로 적어 줘.

⑦ new와 delete의 짝을 사람이 맞추다 보면 언젠가 어긋난다 🔴 사람이 한다

언제 이게 문제가 되나

new로 잡은 것은 delete로 지워야 한다. 규칙은 한 줄이라 쉬워 보인다. 문제는 함수를 빠져나가는 길이 하나가 아니라는 것이다.

AI가 보통 주는 코드 🔴
void tune()
{
  Lidar * p = new Lidar();      // 여기서 잡는다
  if (!p->ok())  { return; }    // ① 여기로 나가면 안 지워진다
  if (busy())    { return; }    // ② 여기로 나가도 안 지워진다
  delete p;                     // ③ 여기까지 와야만 지워진다
}

무엇이 문제인가

나가는 길이 셋인데 delete는 한 줄이다. ①과 ②로 나가면 그대로 샌다. 그리고 이 코드에 나중에 조건을 하나 더 붙이면 새는 길이 또 하나 늘어난다. 사람이 그때마다 delete를 챙겨 넣어야 하는데, 언젠가는 빠뜨린다.

이렇게 말하면 된다

이 코드에서 new 와 delete 를 직접 쓰지 말고 스코프가 정리해 주는 방식으로 바꿔 줘. 함수 중간에 return 이 여러 개 있어도 새지 않아야 해. 바뀌는 부분만 보여 줘.
받은 코드
void tune()
{
  auto p = std::make_unique<Lidar>();   // 여기서 잡는다
  if (!p->ok())  { return; }             // ① 나가면서 반납된다
  if (busy())    { return; }             // ② 나가면서 반납된다
}                                        // ③ 여기서도 반납된다
해석: delete가 사라졌다. 줄이 하나 줄어든 것이 이득이 아니다. 이득은 「나가는 길을 하나 더 만들어도 아무것도 안 고쳐도 된다」는 쪽이다. 코드를 고칠 때마다 사람이 챙겨야 하는 항목이 하나 사라진 것이다.

그냥 변수로 (Lidar lidar;)기본값. 이 중괄호 안에서만 쓸 것이면 이것[요구]
std::make_unique<T>()주인이 하나인데 수명을 중괄호보다 길게 가져가야 할 때[알아보기]

오른쪽 코드에 나온 std::make_unique가 메모리에 RAII를 적용한 도구다. 새로운 발명이 아니라 오늘 본 「중괄호가 곧 수명」을 메모리에 그대로 옮긴 것일 뿐이다. 그래서 RAII가 먼저다. 이것을 모르고 스마트 포인터를 배우면 "포인터인데 이름이 왜 이렇게 기나"에서 멈춘다. 12회에서 제대로 다룬다.

  [SensorGood 소멸자]
2번에서 아무 오류도 안 난다

빌드도 되고 실행도 되고 종료 코드도 정상이다. 줄 하나가 없어진 것이 전부다. 바로 그것이 이 실습에서 확인할 내용이다. 컴파일러가 안 잡아 주는 종류의 실수가 있다는 것을 손으로 겪어 둔다.

🤖 오늘 나온 프롬프트 모음

이럴 때이렇게 말한다
기반 클래스를 받았을 때"상속당하는 클래스의 소멸자에 virtual이 붙어 있는지 확인해 줘. 상속을 안 당하는 클래스에는 붙이지 마."
갈아 끼우는 함수가 있을 때"기반 클래스 함수를 갈아 끼우는 함수 전부에 override를 붙여 줘. 붙였더니 컴파일이 안 되는 곳은 고치지 말고 먼저 알려 줘."
new가 보일 때"new·delete를 직접 쓰지 말고 스코프가 정리해 주는 방식으로 바꿔 줘. 중간에 return이 여러 개여도 안 새야 해."
close()·unlock()이 보일 때"이 close()가 정말 필요한 줄인지 알려 줘. 소멸자가 대신 해 주는 것이면 지워 줘."
클래스 뼈대를 시킬 때"이 클래스를 나중에 상속할 거야. 소멸자는 virtual로, 갈아 끼울 함수는 virtual + 자식 쪽에 override로 만들어 줘."

✅ 오늘의 점검

조금 더 알아두면 시험 범위 아님

왜 소멸자는 자식 → 부모 순서로 불리나

만들 때와 지울 때의 순서가 반대다. 실행 결과가 그것을 그대로 보여 준다. 

[LidarGood 생성] 360칸 확보     ← 부모가 먼저 만들어지고 자식이 채워진다
[LidarGood 소멸자] 360칸 반납    ← 자식이 먼저 정리되고
[SensorGood 소멸자]              ← 부모가 나중에 정리된다

이유는 단순하다. 자식은 부모의 것을 쓸 수 있지만 부모는 자식의 것을 모른다. 부모를 먼저 지우면 자식이 정리하는 도중에 이미 없어진 것을 건드리게 된다. 「나중에 만든 것이 먼저 사라진다」는 규칙은 중괄호 안의 변수들에도 똑같이 적용된다 — 바깥 닫힘이 맨 마지막에 찍힌 이유가 그것이다.

모든 클래스에 virtual 소멸자를 붙이면 안 되나

안 붙이는 것이 맞다. 공짜가 아니기 때문이다.

virtual이 하나라도 붙으면 그 클래스의 객체마다 표를 가리키는 자리가 하나 더 붙는다 (보통 8바이트). float 두 개짜리 작은 객체를 수만 개 만드는 코드라면 이것이 그냥 낭비다.

이런 클래스는가상 소멸자를
다른 클래스가 상속한다붙인다
기반 클래스 손잡이로 잡아서 지울 일이 있다붙인다
혼자 쓰는 작은 자료 묶음이다 (점 좌표 같은 것)안 붙인다

판단 기준 한 줄: "이 클래스를 누가 상속하나?" 답이 "그렇다"면 붙인다.

= default와 = delete — 소멸자 옆에서 자주 보이는 두 표기

가상 소멸자를 붙일 때 몸통이 빌 때가 많다. 그때 이렇게 쓴 코드를 자주 본다. 

class Sensor {
public:
  virtual ~Sensor() = default;   // "기본으로 해 줘" — { } 와 같은 뜻
  virtual float read() = 0;
};

= default는 "컴파일러가 알아서 만들어 주는 기본 동작을 쓰겠다"는 뜻이다. { }라고 쓰는 것과 결과가 같은데, 의도가 코드에 드러난다는 점이 낫다. 반대로 = delete는 "이건 아예 못 쓰게 하라"는 뜻이다. 알아보기만 하면 된다. ROS 2 코드에서 자주 보인다.

다른 언어에서는 이걸 어떻게 하나 — 가비지 컬렉션과의 차이

파이썬이나 자바에는 쓰레기 수집기(garbage collector)가 있다. 안 쓰는 메모리를 나중에 알아서 회수해 준다. 편하지만 두 가지가 다르다.

RAII (C++)쓰레기 수집 (파이썬·자바)
언제 정리되나중괄호를 나가는 그 순간수집기가 도는 때. 언제인지 모른다
파일·잠금도 되나된다. 메모리와 똑같이 처리된다메모리만. 파일은 따로 닫아야 한다
로봇에서정리 시점이 정해져 있다수집기가 도는 동안 잠깐 멈출 수 있다

마지막 줄이 로봇에서 C++을 쓰는 이유 중 하나다. "언제 멈출지 모른다"는 것이 제어 주기를 지켜야 하는 프로그램에서는 문제가 된다.
