확인 명령어 열 개 — 에이전트가 한 일을 내가 보는 법

오늘 답할 질문
  1. 에이전트가 "잘 연결되었습니다"라고 했다. 그 말을 어떻게 확인하나?
  2. 데이터가 안 오는데 어디부터 봐야 하나?
  3. ROS 명령어가 수십 개인데 뭘 외워야 하나?

셋째 질문의 답을 먼저 말한다. 아무것도 외우지 않는다. 명령어는 에이전트가 대신 쳐 준다. 외울 것은 질문 목록이다. 질문을 떠올리지 못하면 에이전트에게 물어볼 수조차 없기 때문이다.

⛔ 확인은 절대 넘기지 않는다

에이전트에게 "잘 됐는지 확인해 줘"라고 하면 "완료했습니다"라는 답이 돌아온다. 그 문장은 정보가 아니다. 화면에 숫자가 올라가는 것을 눈으로 본 사람만 다음 단계에서 무엇이 깨졌는지 안다.

한 장 요약 — 이 열 줄이 학기 내내 쓰인다

무엇을 먼저 볼지: 왼쪽 「내가 알고 싶은 것」 열만 읽는다. 오른쪽은 그때 찾아보면 된다.

내가 알고 싶은 것그때 이걸 친다
1. 내 노드가 살아 있나ros2 node list
2. 어떤 토픽이 있고 타입이 뭔가ros2 topic list -t
3. 값이 정말 흐르나ros2 topic echo /scan
4. 초당 몇 번 오나ros2 topic hz /scan
5. 누가 보내고 누가 받나 (+QoS)ros2 topic info /scan -v
6. 메시지 안에 뭐가 들었나ros2 interface show ...
7. 지금 설정값이 뭔가ros2 param list / get
8. 방금 그 장면을 다시 보고 싶다ros2 bag record / play
9. 연결을 그림으로 보고 싶다rqt_graph
10. 환경 자체가 이상하다ros2 doctor

명령어를 외우지 않는 대신 무엇을 하나 🔴 사람이 한다

ROS 1에서는 rosrun, rosnode, rostopic처럼 명령어가 따로 있었다. ROS 2는 전부 ros2 {무엇을} {어떻게} {옵션} 한 형태로 통일했다. 구조가 규칙적이라 에이전트가 특히 잘 만들어 준다.

해석: 그래서 이 회차의 목표가 바뀐다. 명령어를 치는 능력이 아니라 출력을 읽는 능력을 기른다. 아래 각 절에서 「출력을 이렇게 읽는다」 칸이 진짜 내용이다.

실습하려면 화면이 여럿 필요하다. 터미널을 칸으로 나눠 쓰는 도구를 하나 깔아 둔다. 이것부터 에이전트에게 시켜 본다.

터미널을 상하좌우로 나눠 쓸 수 있는 프로그램을 설치해 줘. sudo가 붙는 명령은 실행하기 전에 나에게 보여 줘. 설치 후 단축키도 알려 줘.

1. 내 노드가 살아 있나 🟢 맡겨도 됨

그때 이걸 친다

$ ros2 node list

출력을 이렇게 읽는다

/teleop_turtle
/turtlesim

여기서 놀라는 대목이 하나 있다. 실행할 때 친 이름은 turtlesim_node였는데 목록에는 /turtlesim으로 나온다. 실행 파일 이름과 노드 이름은 다른 것이기 때문이다.

실행 파일 이름노드 이름
turtlesim_node/turtlesim
turtle_teleop_key/teleop_turtle
해석: 이 구별이 나중에 파라미터를 다룰 때 그대로 온다. ros2 run에는 실행 파일 이름을, ros2 param에는 노드 이름을 쓴다. 같은 걸 넣으면 "그런 노드 없다"는 답이 나온다.
지금 떠 있는 ROS 2 노드 목록을 보여 주고, 각각이 어느 패키지의 어떤 실행 파일인지도 같이 정리해 줘.

2. 어떤 토픽이 있고 타입이 뭔가 🟢 맡겨도 됨

그때 이걸 친다

$ ros2 topic list -t

출력을 이렇게 읽는다

/parameter_events [rcl_interfaces/msg/ParameterEvent]
/rosout [rcl_interfaces/msg/Log]
/scan [sensor_msgs/msg/LaserScan]        ← 라이다
/cmd_vel [geometry_msgs/msg/Twist]       ← 바퀴 명령

-t를 붙이면 대괄호 안에 메시지 타입이 함께 나온다. 이게 중요하다. 코드에서 구독할 때 타입 이름이 한 글자라도 다르면 안 붙기 때문이다.

⚠️ 여기서 제일 많이 나오는 실수

토픽 이름 앞의 빗금(/)이 있고 없고가 다르다. 코드에 "scan"이라고 쓰면 노드 이름공간 안의 토픽이 되어 /robot1/scan이 될 수도 있다. 목록에 보이는 이름과 코드에 쓴 이름을 눈으로 대조한다.

3. 값이 정말 흐르나 🔴 내가 본다

그때 이걸 친다

$ ros2 topic echo /scan --once

출력을 이렇게 읽는다

header:
  stamp: {sec: 1740000000, nanosec: 123456789}
  frame_id: base_scan          ← 어느 좌표계에서 잰 값인가
angle_min: 0.0                 ← 첫 값의 각도
angle_increment: 0.01749       ← 약 1도 (라디안)
range_min: 0.16
range_max: 8.0
ranges: [0.83, 0.84, .inf, 0.86, ... ]   ← 여기를 본다
---
어디를 보나무엇을 확인하나
ranges의 앞부분.inf가 섞여 있는지. 실제 라이다에는 반드시 섞여 있다
range_min·range_max이 값이 거르는 기준이다. 코드에 숫자를 박지 말고 이걸 쓴다
frame_id이 값이 무엇을 기준으로 한 좌표인지. 26회에서 다시 만난다
angle_increment인덱스를 각도로 바꾸는 값. 24회에서 쓴다
해석: --once를 안 붙이면 화면이 끝없이 흘러가서 아무것도 못 읽는다. 값을 읽으려면 --once, 흐르는지만 보려면 그냥 — 목적에 따라 다르다.

4. 초당 몇 번 오나 🔴 밀림 진단

그때 이걸 친다

$ ros2 topic hz /scan

출력을 이렇게 읽는다

average rate: 5.012
  min: 0.196s max: 0.203s std dev: 0.00214s window: 6
본 것무슨 뜻인가
average rate가 사양과 비슷정상. 우리 라이다는 5Hz 이상이 정상값이다
average rate가 사양보다 훨씬 낮음어딘가에서 밀리고 있다. 콜백이 오래 걸리거나 통신이 막혔다
max가 min보다 훨씬 큼가끔 한 번씩 크게 늦는다. 로봇이 그 순간 반응을 놓친다
아무것도 안 나옴토픽 이름이 틀렸거나 QoS가 안 맞다 (22회)

이 명령어가 왜 중요한가: 11회에서 배운 "쓸데없이 복사하지 않는다"가 여기서 숫자로 나타난다. 콜백에서 큰 배열을 통째로 복사하면 이 숫자가 떨어진다. 라즈베리파이는 서버가 아니다 — 여유 자원이 애초에 적다.

/scan 토픽의 주기를 30초 동안 측정해서 평균과 최대 지연을 알려 줘. 사양(5Hz 이상)과 비교해서 정상인지도 판단해 줘.

5. 누가 보내고 누가 받나 🔴 가장 자주 쓰게 된다

그때 이걸 친다

$ ros2 topic info /scan -v

출력을 이렇게 읽는다

Type: sensor_msgs/msg/LaserScan
Publisher count: 1
Subscription count: 0          ← 아무도 안 받고 있다

Node name: turtlebot3_lds
  QoS profile:
    Reliability: BEST_EFFORT   ← 여기를 본다
    Durability: VOLATILE
    History (Depth): KEEP_LAST (5)
⚠️ 이 회차에서 가장 중요한 한 줄

Reliability가 보내는 쪽과 받는 쪽이 다르면 둘은 안 붙는다. 라이다처럼 빠르고 유실돼도 되는 센서는 보통 BEST_EFFORT로 보낸다. 그런데 코드에서 구독을 기본값으로 만들면 RELIABLE이 된다.

증상은 이렇게 나타난다 — 빌드도 되고, 노드도 뜨고, echo로 보면 데이터도 오는데, 내 콜백은 한 번도 안 불린다. 원인이 코드에 안 보이기 때문에 학생이 가장 오래 헤매는 자리다.

고치는 법은 22회에서 다룬다. 지금은 이 화면에서 확인할 수 있다는 것만 기억한다.

6. 메시지 안에 뭐가 들었나 🟢 맡겨도 됨

그때 이걸 친다

$ ros2 interface show sensor_msgs/msg/LaserScan
$ ros2 interface show geometry_msgs/msg/Twist

출력을 이렇게 읽는다

# Twist
Vector3 linear      ← x, y, z
Vector3 angular     ← x, y, z
해석: Twist에는 숫자가 여섯 개 들어 있다. 그런데 바퀴 두 개로 굴러가는 우리 로봇은 그중 둘만 쓴다 — linear.x(앞으로 얼마나)와 angular.z(얼마나 돌지)다. 나머지 넷에 값을 넣어도 조용히 무시된다. 이런 것은 메시지 정의만 봐서는 모르고 로봇 문서를 봐야 안다.
sensor_msgs/msg/LaserScan의 필드를 하나씩 한국어로 설명해 줘. 각 필드를 실제로 어디에 쓰는지도 한 줄씩 붙여 줘.

7. 지금 설정값이 뭔가 🟡 맡기되 확인

$ ros2 param list
$ ros2 param get /turtlesim background_b
$ ros2 param set /turtlesim background_b 0

set이 이 절의 핵심이다. 노드를 끄지 않고, 다시 빌드하지 않고 값을 바꿀 수 있다. 프로젝트에서 조향 이득 같은 값을 파라미터로 빼 두면 로봇을 세우지 않고 튜닝할 수 있다. 평가 당일에 이 차이가 크다.

⚠️ 바꾼 값은 노드를 끄면 사라진다

set으로 바꾼 값은 메모리에만 있다. 좋은 값을 찾았으면 YAML 파일에 적어 둔다(21회). 적어 두지 않으면 다음 날 처음부터 다시 맞춰야 한다.

8. 방금 그 장면을 다시 보고 싶다 🟡 맡기되 확인

$ ros2 bag record /scan /cmd_vel -o cone_run1
$ ros2 bag play cone_run1
해석: 이게 이 열 개 중 가장 과소평가되는 명령어다. 한 번 기록해 두면 로봇 없이도 코드를 고치고 시험할 수 있다. 로봇은 대수가 한정돼 있고 배터리는 닳는다. 기록 파일은 그렇지 않다. 25회 과제(HW7)가 이 파일 위에서 진행된다.

기록할 때 주의: 아무거나 다 기록하면 파일이 금방 커진다. 토픽을 지정해서 기록한다.

9. 연결을 그림으로 보고 싶다 🔴 그림은 사람이 읽는다

$ rqt_graph

노드가 동그라미, 토픽이 화살표로 나온다. 이건 에이전트에게 시키지 않는다. 그림을 보는 것 자체가 목적이기 때문이다.

그림에서 본 것무슨 뜻인가
내 노드가 아예 없다안 떠 있다. 또는 source를 안 했다
노드는 있는데 화살표가 안 닿아 있다토픽 이름이 다르다. 오타일 확률이 높다
화살표는 닿았는데 데이터가 안 온다QoS 문제일 가능성이 크다 → 5번으로 간다

10. 환경 자체가 이상하다 🟢 맡겨도 됨

$ ros2 doctor

설치·네트워크·버전을 한꺼번에 점검한다. 출력이 길어서 읽는 것을 에이전트에게 맡기기 좋다.

ros2 doctor를 실행하고, 경고와 오류만 골라서 각각 무슨 뜻이고 고쳐야 하는 것인지 알려 줘.

막혔을 때 보는 순서 — 이 순서만 기억해 두면 됩니다

무엇을 먼저 볼지: 위에서 아래로 내려간다. 위에서 걸리면 아래는 볼 필요가 없다.

순서확인여기서 걸리면
1ros2 node list — 노드가 떠 있나안 떴다. source했나, 빌드했나
2ros2 topic list — 토픽 이름이 내 코드와 같나오타다. 빗금 확인
3ros2 topic echo — 값이 오나보내는 쪽 문제다
4ros2 topic info -v — QoS가 같나QoS 불일치 (22회)
5ros2 topic hz — 주기가 정상인가내 콜백이 밀리고 있다
해석: 대부분의 질문이 2번이나 4번에서 끝난다. 이 다섯 줄을 순서대로 훑는 습관이 조교 질문의 절반을 없앤다. 에이전트에게 물어볼 때도 이 순서로 물으면 훨씬 정확한 답이 온다.
🧪 실습 — 고장난 시스템 진단하기 (HW5로 이어집니다)

알게 되는 것: 원인을 짚는 순서. 명령어가 아니라 순서가 이 실습의 목표다.

준비물: 배포된 고장난 패키지, 터미널 3칸

절차

  1. 배포된 패키지를 빌드하고 실행한다. 데이터가 안 온다. (5분)
  2. 위 「막혔을 때 보는 순서」를 1번부터 훑는다. (15분)
  3. 어느 줄에서 걸렸는지, 화면의 무엇을 보고 그렇게 판단했는지 적는다. (10분)
  4. 고친 뒤 같은 명령어로 고쳐졌음을 확인한다. (10분)

이렇게 되면 성공: ros2 topic hz에 정상 주기가 찍힌다. 그리고 3번에 적은 근거가 실제 원인과 맞는다.

채점은 고친 결과가 아니라 근거를 본다

에이전트에게 물어봐서 고쳐도 된다. 다만 무엇을 보고 알았는지 못 쓰면 점수가 없다. 고친 사람과 원인을 아는 사람은 다르다.

✅ 오늘의 점검

더 궁금하면 시험 범위 아님

  • ros2 topic pub — 노드를 만들지 않고 토픽을 직접 쏴 볼 수 있다. 로봇 없이 코드를 시험할 때 쓴다.
  • ros2 run rqt_plot rqt_plot — 값이 시간에 따라 어떻게 변하는지 그래프로 본다. 조향값이 흔들리는지 볼 때 유용하다.
