ROS 2 패키지와 노드 (ament_cmake)

오늘 답할 질문
  1. ROS 2 패키지는 8회에서 만든 CMake 프로젝트와 무엇이 같고 무엇이 다른가?
  2. package.xml은 왜 따로 있나? CMakeLists.txt만으로는 안 되나?
  3. 노드는 C++ 코드에서 어떻게 생겼나? 왜 클래스로 만드나?
  4. 빌드는 성공했는데 ros2 run이 못 찾는다. 어디를 보면 되나?

ROS 2의 빌드는 새로운 게 아니다. 8회에서 배운 CMake에 규칙 몇 개가 더 붙은 것이다. add_executable로 실행 파일을 만들고 target_link_libraries로 남의 라이브러리를 붙이는 것 — 8회의 scan_tools/에서 한 일이 오늘도 그대로 나온다. 달라지는 것은 그 앞뒤에 붙는 몇 줄과, cmake를 직접 치는 대신 colcon build를 친다는 것 정도다.

오늘은 ~/ros2_ws/src 안에 turtle_drive라는 패키지를 하나 만든다. 이 패키지는 22회까지 네 회차 동안 자란다. 오늘 거기에 넣는 것은 실행 파일 하나, hello_node다. 로그 한 줄을 찍고 끝나는 프로그램에서 시작해, rclcpp::Node를 상속한 클래스가 되어 ros2 node list에 이름이 뜨는 데까지 간다. 거북이를 움직이는 일(발행·구독·타이머)은 20회 몫이라 오늘은 하지 않는다.

그리고 이 회차의 절반은 안 될 때를 다룬다. ros2 run이 실행 파일을 못 찾는 경우는 대개 세 가지 중 하나이고, 세 가지 모두 실제로 재현해 오류 메시지를 받아 두었다. 메시지를 한 번 봐 두면 나중에 같은 글자를 만났을 때 어디를 볼지 바로 떠오른다.

① 패키지와 ros2 pkg create 🟢 맡긴다

개념 — 패키지(package)

ROS 2에서 코드를 나눠 담는 단위를 패키지(package)라고 한다. 폴더 하나이고, 그 안에 package.xml이 있으면 패키지다. 16회에서 실행해 본 demo_nodes_cpp, 18회의 turtlesim이 모두 패키지였다 — ros2 run turtlesim turtlesim_node의 앞쪽 이름이 패키지, 뒤쪽 이름이 그 안의 실행 파일이다.

그럼 8회의 scan_tools/ 같은 CMake 프로젝트와는 무엇이 다를까? CMake 프로젝트는 혼자 빌드되고 끝이다. 다른 프로젝트가 그것을 찾아 쓰려면 경로를 손으로 알려 줘야 했다. 패키지는 남이 찾을 수 있게 정해진 자리에 설치되고, 자기가 무엇에 기대는지를 적어 둔다. 그 「정해진 자리」가 작업공간의 install/이고, 「적어 둔 것」이 package.xml이다.

🆕 이 명령에서 처음 나오는 것

ros2 pkg create 이름
지금 폴더 안에 이름/ 폴더를 만들고 패키지 뼈대를 채운다. 여기서는 ~/ros2_ws/src/turtle_drive/가 생겼다.
--build-type ament_cmake
이 패키지를 무엇으로 빌드할지 정한다. ament_cmake는 「CMake에 ROS 2용 명령 몇 개를 더한 것」이고 C++ 패키지는 이것을 쓴다. 파이썬 패키지는 ament_python을 쓴다. ament는 ROS 2의 빌드 도구 묶음에 붙은 이름이다(단어 뜻으로 지은 이름이 아니라 고유 이름이다).
--dependencies rclcpp
처음부터 기댈 패키지를 적어 두면 package.xml과 CMakeLists.txt 양쪽에 그 이름을 넣어 준다. rclcpp는 「ROS Client Library for C++」 — C++에서 ROS 2를 쓰게 해 주는 라이브러리다. 오늘 코드의 rclcpp::가 전부 여기서 온다.
⚠️ 패키지 이름은 맨 앞에 — 옵션 순서를 바꾸면 이름이 사라진다

인터넷 예제나 AI가 준 명령에는 패키지 이름을 맨 끝에 붙인 모양이 자주 보인다. 그대로 치면 이렇게 된다. 

$ ros2 pkg create --build-type ament_cmake --dependencies rclcpp turtle_drive

② package.xml 🟡 맡기되 검사

개념 — 패키지 매니페스트(manifest)

이 파일이 왜 필요할까? CMakeLists.txt에도 find_package(rclcpp)가 있으니 의존성은 이미 적혀 있는 셈이다. 차이는 누가 읽느냐다. CMakeLists.txt는 CMake가 빌드하는 순간에만 읽는다. package.xml은 빌드하기 전에 읽힌다 — 작업공간의 패키지 여러 개 중 무엇부터 빌드할지 정하는 colcon, 새 컴퓨터에서 이 패키지에 필요한 것을 깔아 주는 rosdep이 이 파일을 본다. CMake 스크립트는 실행해 봐야 무엇을 찾는지 알 수 있지만, XML은 열어서 읽기만 하면 된다.

이런 「이 묶음이 무엇이고 무엇이 필요한가」를 적은 파일을 매니페스트(manifest)라고 부른다. 형식은 XML이다 — <이름>값</이름>처럼 여는 태그와 닫는 태그 사이에 값을 둔다.

만들어진 파일 읽기

<?xml version="1.0"?>
<?xml-model href="http://download.ros.org/schema/package_format3.xsd" schematypens="http://www.w3.org/2001/XMLSchema"?>
<package format="3">
  <name>turtle_drive</name>
  <version>0.0.0</version>
  <description>TODO: Package description</description>
  <maintainer email="ubuntu@todo.todo">ubuntu</maintainer>
  <license>TODO: License declaration</license>

  <buildtool_depend>ament_cmake</buildtool_depend>

  <depend>rclcpp</depend>

  <test_depend>ament_lint_auto</test_depend>
  <test_depend>ament_lint_common</test_depend>

  <export>
    <build_type>ament_cmake</build_type>
  </export>
</package>

무엇을 먼저 볼지: 아래 표의 「손대나」 열. 손대는 줄은 넷뿐이다.

태그뜻손대나
<name>패키지 이름. ros2 run의 첫 번째 이름이 이것이다안 댄다. 폴더 이름·project()와 같아야 한다
<description> · <maintainer> · <license>무슨 패키지인가 · 누가 관리하나 · 어떤 조건으로 쓰게 하나채운다. TODO가 남아 있으면 남이 받았을 때 누구 것인지 모른다
<buildtool_depend>이 패키지를 빌드하는 도구 (ament_cmake)안 댄다
<depend>빌드할 때도, 실행할 때도 필요한 패키지의존성이 늘면 한 줄씩 더한다 (20회에 두 줄 늘어난다)
<test_depend>코드 검사 도구(lint)를 돌릴 때만 필요한 것그대로 둔다. 오늘은 테스트를 돌리지 않는다
<export><build_type>colcon에게 「이 패키지는 ament_cmake로 빌드하라」고 알린다안 댄다
해석: 이 파일에서 사람이 판단하는 것은 <depend> 줄뿐이다. 나머지는 채우거나 그대로 둔다. <depend>는 <build_depend>(빌드할 때 필요)와 <exec_depend>(실행할 때 필요)를 한 줄로 합친 것이고, 대부분의 경우 이것 하나로 충분하다.

채우는 세 칸은 7단계까지 미뤄 두었다가 v3에서 한 번에 채운다. 지금 채워도 되지만, TODO가 남은 채로도 빌드는 된다는 것을 먼저 봐 두는 편이 좋다. 그래서 검사 목록에 들어간다(⑪절).

③ ament_cmake의 CMakeLists.txt 🟡 맡기되 검사

개념 — 8회 CMake 위에 더해진 명령

ament_cmake는 CMake를 대신하는 도구가 아니다. CMake 그대로이고, ament_으로 시작하는 명령 몇 개가 더해진 것이다. 그래서 파일을 열면 8회에서 본 줄과 처음 보는 줄이 섞여 있다. 만들어진 파일 전체다. 

cmake_minimum_required(VERSION 3.8)
project(turtle_drive)

if(CMAKE_COMPILER_IS_GNUCXX OR CMAKE_CXX_COMPILER_ID MATCHES "Clang")
  add_compile_options(-Wall -Wextra -Wpedantic)
endif()

# find dependencies
find_package(ament_cmake REQUIRED)
find_package(rclcpp REQUIRED)

if(BUILD_TESTING)
  find_package(ament_lint_auto REQUIRED)
  # the following line skips the linter which checks for copyrights
  # comment the line when a copyright and license is added to all source files
  set(ament_cmake_copyright_FOUND TRUE)
  # the following line skips cpplint (only works in a git repo)
  # comment the line when this package is in a git repo and when
  # a copyright and license is added to all source files
  set(ament_cmake_cpplint_FOUND TRUE)
  ament_lint_auto_find_test_dependencies()
endif()

ament_package()
줄8회에 있었나무엇을 하나
cmake_minimum_required · project있었다그대로다. project()의 이름이 곧 패키지 이름이고, 아래 ${PROJECT_NAME}이 이 값이 된다
add_compile_options(-Wall -Wextra -Wpedantic)11회에서 비슷한 줄을 봤다경고를 켠다. 이 줄은 타깃을 지정하지 않는다 — 8회 기준으로는 낡은 모양이지만 도구가 만들어 주는 기본값이라 그대로 둔다
find_package(rclcpp REQUIRED)8회 「조금 더」에 예고만 있었다설치된 패키지를 찾아 그 타깃을 쓸 수 있게 불러온다. REQUIRED는 못 찾으면 거기서 멈추라는 뜻
find_package(ament_cmake REQUIRED)없었다ament_package() 같은 ament 명령을 쓸 수 있게 불러온다
if(BUILD_TESTING) … endif()없었다코드 검사(lint)를 켤 때만 도는 묶음. 오늘은 신경 쓰지 않아도 된다
ament_package()없었다이 패키지를 ROS 2에 등록한다 — package.xml을 설치 폴더에 복사하고, 「이 패키지가 여기 있다」는 표시를 남긴다. 맨 마지막 줄이어야 한다
해석: 빠진 것이 보인다 — add_executable이 없다. 아직 소스가 없으니 만들 실행 파일도 없다. 이 상태로도 빌드는 되지만, 실행할 것이 없다. 
$ cd ~/ros2_ws
$ colcon build --packages-select turtle_drive
Starting >>> turtle_drive
Finished <<< turtle_drive [1.01s]

Summary: 1 package finished [1.09s]
$ source install/setup.bash
$ ros2 pkg executables turtle_drive
$ ros2 run turtle_drive hello_node
No executable found

ros2 pkg executables가 아무것도 찍지 않았다 — 이 패키지에는 실행 파일이 없다. No executable found라는 글자를 기억해 두면 좋다. ⑨절에서 다른 이유로 한 번 더 만난다. colcon build와 source가 무엇을 하는지는 ⑧절에서 그림으로 정리한다. 지금은 「작업공간 최상위에서 빌드하고, 그 결과를 source로 불러온다」까지만 보면 된다.

개념 — ROS 2 프로그램의 시작과 끝

ROS 2를 쓰는 C++ 프로그램도 그냥 main이 있는 C++ 프로그램이다. 다만 ROS 2의 통신을 쓰려면 시작할 때 준비를 하고, 끝날 때 정리를 해야 한다. 준비가 rclcpp::init, 정리가 rclcpp::shutdown이다. 11회의 RAII에서 「얻은 것은 돌려준다」를 봤는데, 그 짝이 여기서는 함수 두 개로 나와 있다. 

int main(int argc, char ** argv)
{
  rclcpp::init(argc, argv);   // 준비
  // … 일을 한다 …
  rclcpp::shutdown();         // 정리
  return 0;
}

그리고 화면에 무언가를 찍을 때는 std::cout 대신 ROS 2의 로그를 쓴다. 로그는 화면에도 찍히지만 /rosout이라는 토픽으로도 나가서, 다른 터미널이나 도구(22회의 rqt)에서도 볼 수 있다. 누가 언제 찍었는지가 줄마다 붙는다.

예제에 적용 — src/hello_node.cpp를 만든다

⑤ target_link_libraries와 ament_target_dependencies 🟡 맡기되 검사

개념 — 의존성을 타깃에 붙이는 두 가지 방법

④절에서 rclcpp를 붙인 줄은 8회의 target_link_libraries였다. 그런데 ros2 pkg create에 실행 파일까지 만들어 달라고 하면(--node-name hello_node) 도구는 다른 줄을 넣는다. 실제로 만들어진 줄이다. 

add_executable(hello_node src/hello_node.cpp)
target_include_directories(hello_node PUBLIC
  $<BUILD_INTERFACE:${CMAKE_CURRENT_SOURCE_DIR}/include>
  $<INSTALL_INTERFACE:include/${PROJECT_NAME}>)
target_compile_features(hello_node PUBLIC c_std_99 cxx_std_17)  # Require C99 and C++17
ament_target_dependencies(
  hello_node
  "rclcpp"
)

install(TARGETS hello_node
  DESTINATION lib/${PROJECT_NAME})

ament_target_dependencies(hello_node "rclcpp")가 ④절의 target_link_libraries(hello_node PRIVATE rclcpp::rclcpp)와 같은 일을 하는 줄이다. ament가 따로 만든 명령으로, 패키지 이름만 적으면 그 패키지의 헤더 경로와 라이브러리를 찾아 붙여 준다. CMake의 타깃 방식이 지금처럼 자리 잡기 전에 만들어져, 오랫동안 ROS 2 예제의 표준 모양이었다.

해석: 둘 다 지금 Jazzy에서 빌드되고, 결과도 같다. 이 자료는 8회와 같은 줄인 target_link_libraries를 쓴다 — 새로 외울 것이 하나 줄고, 다음 배포판으로 옮겨 가도 그대로 쓸 수 있기 때문이다. 받은 코드에 ament_target_dependencies가 있다고 틀린 것은 아니다. 지금 인터넷 예제와 AI 답의 대부분이 이 모양이라 읽을 줄 알아야 하고, 고칠지 말지는 패키지 안에서 한 가지로 맞추느냐가 기준이 된다.

🆕 이 파일에서 처음 나오는 것

$<BUILD_INTERFACE:…> · $<INSTALL_INTERFACE:…>
「빌드할 때는 이 경로, 설치한 뒤에는 저 경로」를 한 줄에 적는 CMake 문법(generator expression)이다. 다른 패키지가 이 패키지의 헤더를 가져다 쓸 때 필요하다. hello_node는 헤더를 내놓지 않으므로 오늘 우리 파일에는 넣지 않았다. 읽을 줄만 알면 된다.
target_compile_features(hello_node PUBLIC cxx_std_17)
8회의 set(CMAKE_CXX_STANDARD 17)을 타깃 하나에 거는 모양이다. 우리 파일에는 없지만 Jazzy의 컴파일러(g++ 13)는 기본이 C++17이라 빌드에 차이가 없다.
이 CMakeLists.txt 에서 ament_target_dependencies 를 쓰는 줄을 전부 target_link_libraries 로 바꿔 줘. 실행 파일 타깃은 PRIVATE 로 하고, 메시지 패키지는 ${패키지_TARGETS} 모양으로 붙여 줘. 바꾼 뒤 colcon build --packages-select 로 빌드해서 경고 없이 끝나는지 보여 줘.

⑥ rclcpp::Node 상속과 rclcpp::spin (v2) 🟡 맡기되 검사

개념 — 노드는 rclcpp::Node를 상속한 클래스다

17회에서 노드는 「ROS 2 그래프에 이름을 올리고 통신에 참여하는 단위」였다. C++ 코드에서는 그것이 rclcpp::Node 타입의 객체다. 이 객체가 만들어지는 순간 그래프에 이름이 올라가고, 없어지는 순간 내려간다.

왜 rclcpp::Node를 그대로 쓰지 않고 상속할까? 노드가 할 일은 노드마다 다르기 때문이다. 20회에서 wall_stop은 발행자·구독자·타이머를 갖고, 21회에서는 파라미터도 갖는다. 그런 것들은 노드가 살아 있는 동안 계속 있어야 하니 멤버 변수가 되고, 9회의 클래스가 정확히 그 일을 한다. 이름 짓기·로거·통신 같은 공통 기능은 rclcpp::Node에서 물려받고, 우리 노드만의 상태와 동작을 얹는다 — 10회에서 기반 클래스·파생 클래스로 본 그 구조다. 

class 노드이름 : public rclcpp::Node
{
public:
  노드이름()
  : Node("그래프에 올라갈 이름")   // 기반 클래스 생성자에 이름을 넘긴다
  {
    // 처음 한 번 할 일
  }
};

그리고 노드를 만들기만 하면 main이 곧바로 끝나 버린다. v1처럼 말이다. 노드가 계속 살아서 일을 하게 하려면 main이 거기서 기다려야 한다. 그 일을 하는 함수가 rclcpp::spin이다. spin은 Ctrl+C로 끝내라는 신호가 올 때까지 돌아오지 않는다.

예제에 적용 — v1에는 노드가 없다

④절 끝에서 ros2 node list가 비어 있었다. 고칠 것은 둘이다. 노드를 만드는 것과, 노드가 살아 있는 동안 기다리는 것. CMakeLists.txt와 package.xml은 그대로 둔다 — rclcpp 하나만 쓰는 것은 변함이 없다.

#include <memory>

#include "rclcpp/rclcpp.hpp"

class HelloNode : public rclcpp::Node
{
public:
  HelloNode()
  : Node("hello_node")           // 기반 클래스 생성자에 노드 이름을 넘긴다
  {
    RCLCPP_INFO(this->get_logger(), "노드가 만들어졌습니다");
  }
};

int main(int argc, char ** argv)
{
  rclcpp::init(argc, argv);
  auto node = std::make_shared<HelloNode>();
  rclcpp::spin(node);            // Ctrl+C 를 누를 때까지 여기서 기다린다
  rclcpp::shutdown();
  return 0;
}

🆕 이 코드에서 처음 나오는 것

: Node("hello_node")
9회의 멤버 초기화 리스트 자리에서 기반 클래스의 생성자를 부른다. 넘긴 문자열이 그래프에 올라가는 노드 이름이다. 클래스 이름(HelloNode)과 노드 이름(hello_node)은 따로다 — ros2 node list에 보이는 것은 뒤의 것이다.
this->get_logger()
rclcpp::Node에서 물려받은 멤버 함수. 노드 이름이 붙은 로거를 돌려준다. v1의 rclcpp::get_logger("hello_node")를 대신한다 — 이름을 두 번 적지 않아도 된다.
std::make_shared<HelloNode>()
11회의 그것이다. HelloNode 객체를 만들고 shared_ptr로 돌려준다. rclcpp의 함수들이 노드를 shared_ptr로 받기 때문에 노드는 거의 언제나 이렇게 만든다.
rclcpp::spin(node)
노드를 붙잡고 들어오는 일을 처리하며 기다린다. 오늘은 처리할 일이 없어 그냥 기다리기만 한다. 20회에서 타이머·구독 콜백이 생기면 그 콜백들이 전부 이 spin 안에서 불린다. Ctrl+C가 오면 돌아온다.

개념 — spin 앞과 뒤

v2를 Ctrl+C로 끝냈을 때 spin이 돌아온 뒤에도 main에는 줄이 남아 있었다 — rclcpp::shutdown()과 return 0;. 그리고 main이 끝나면 지역 변수 node가 사라지면서 HelloNode의 소멸자가 불린다(11회, shared_ptr의 참조 횟수가 0이 되는 순간). 이 순서는 눈에 보이지 않는다. 로그를 몇 줄 넣으면 보인다.

20회 이후 노드가 커지면 「멈출 때 바퀴를 세운다」 같은 정리 일이 생긴다. 그것을 어디에 둘지 정하려면 이 순서를 알고 있어야 한다.

개념 — colcon은 CMake를 패키지마다 대신 불러 준다

8회에서는 cmake -S . -B build와 cmake --build build를 손으로 쳤다. 프로젝트가 하나였으니 그것으로 충분했다. 작업공간에는 패키지가 여럿 들어간다. 22회쯤 되면 우리 패키지 하나에도 실행 파일이 넷이고, 남이 만든 패키지를 소스로 받아 넣기도 한다. 그때 무엇부터 빌드하고, 결과를 어디에 모을지를 맡는 도구가 colcon(collective construction — 「여럿을 함께 짓는다」에서 따온 이름)이다.

colcon은 지금 폴더 아래에서 package.xml이 있는 폴더를 전부 찾고, 패키지마다 CMake 설정·빌드·설치를 차례로 돌린다. 결과는 colcon을 친 그 폴더 바로 아래 세 폴더에 쌓인다.

무엇이 문제인가

줄무엇이 문제인가얼마나 급한가
include_directories(include)8회 ⑤절의 그 줄이다. 누구에게 거는지가 없어 이 파일의 모든 타깃에 걸린다. 지금은 include/가 비어 있어 아무 일도 안 하는 줄이기도 하다지운다
set(CMAKE_CXX_STANDARD 14)C++14로 낮춘다. 14회의 std::optional·구조적 바인딩은 C++17이라 그 코드를 넣는 순간 컴파일 오류가 난다. Jazzy는 C++17 기준이다지운다
ament_target_dependencies⑤절. Jazzy에서는 되지만 다음 배포판에서 사라질 예정이다패키지 안에서 한 가지로 맞춘다
add_compile_options(-Wall …)가 없다경고가 꺼져 있다. 형식 문자열과 값이 안 맞는 RCLCPP_INFO 같은 실수를 컴파일러가 알려 주지 않는다넣는다
cmake_minimum_required(VERSION 3.5)오래된 기준이지만 빌드에는 문제가 없다그대로 둬도 된다
해석: 다섯 줄 가운데 오늘 당장 결과를 바꾸는 것은 없다. 그래서 「빌드되니 됐다」로 넘어가기 쉽다. 바뀌는 것은 다음 회차다 — 파일이 커지고, C++17 문법을 넣고, 의존성이 늘어날 때 이 줄들이 하나씩 걸린다.
이 ROS 2 패키지의 CMakeLists.txt 를 ros2 pkg create(Jazzy)가 만드는 모양에 맞춰 정리해 줘. include_directories 는 지우고, C++ 표준을 14로 낮추는 줄도 지우고, 경고 옵션(-Wall -Wextra -Wpedantic)은 넣어 줘. 의존성은 target_link_libraries(… PRIVATE rclcpp::rclcpp) 로 붙이고, ament_package() 는 맨 끝에 둬. 무엇을 왜 바꿨는지 한 줄씩 적어 줘.

패키지를 새로 만들 때"~/ros2_ws/src 에서 ros2 pkg create 로 ament_cmake 패키지를 만들어 줘. 패키지 이름을 명령 맨 앞에 쓰고, 의존성은 rclcpp 하나만. 만든 뒤 package.xml 의 TODO 세 칸이 무엇인지 알려 줘."
실행 파일을 더할 때"src/이름.cpp 를 실행 파일로 더해 줘. add_executable, target_link_libraries(… PRIVATE rclcpp::rclcpp), install(TARGETS … DESTINATION lib/${PROJECT_NAME}) 세 줄을 ament_package() 위에 넣어 줘."
옛 방식 CMake를 받았을 때"이 CMakeLists.txt 에서 include_directories, C++14 설정, ament_target_dependencies 를 찾아 오늘 방식으로 바꿔 줘. 바꾼 이유를 한 줄씩."
의존성을 더할 때"새 의존성을 package.xml 의 <depend> 와 CMakeLists.txt 의 find_package·target_link_libraries 양쪽에 넣어 줘. 넣은 뒤 colcon info 로 package.xml 쪽이 반영됐는지 보여 줘."
ros2 run이 안 될 때"이 오류가 source 를 안 한 것인지, install 이 빠진 것인지, 다른 폴더에서 빌드한 것인지 먼저 판단하고 근거가 되는 명령 하나를 돌려 줘."
노드 뼈대가 필요할 때"rclcpp::Node 를 상속한 클래스로 노드를 만들어 줘. 노드 이름은 생성자의 멤버 초기화 리스트에서 넘기고, main 은 init → make_shared → spin → shutdown 순서로."

✅ 오늘의 점검

조금 더 알아두면 시험 범위 아님

colcon build --symlink-install — 인터넷 예제에 자주 붙는 옵션

install()은 파일을 build/에서 install/로 복사한다. --symlink-install을 붙이면 복사 대신 바로가기(심볼릭 링크)를 만든다. 그러면 21회의 launch 파일·YAML 파일처럼 컴파일이 필요 없는 파일은 src/에서 고치기만 해도 다시 빌드하지 않고 바로 반영된다.

C++ 실행 파일에는 차이가 없다 — 어차피 소스를 고치면 다시 컴파일해야 한다. 그래서 오늘은 붙이지 않았다. 받은 명령에 이 옵션이 붙어 있으면 「설치를 복사 대신 링크로 한다」고 읽으면 된다.

작업공간을 지우고 다시 만들 때 나오는 WARNING … doesn't exist

source install/setup.bash를 한 터미널에서 ~/ros2_ws를 통째로 지우고 다시 빌드하면 이런 줄이 나온다. 검증하다가 실제로 받은 것이다. 

[0.147s] WARNING:colcon.colcon_ros.prefix_path.ament:The path '/home/ubuntu/ros2_ws/install/turtle_drive' in the environment variable AMENT_PREFIX_PATH doesn't exist

터미널의 AMENT_PREFIX_PATH에는 지워진 폴더가 아직 적혀 있는데 실제 폴더가 없어서 colcon이 알려 주는 것이다. 빌드에는 영향이 없다. 새 터미널을 열면 사라진다.

ros2 pkg create --node-name — 실행 파일까지 한 번에 만들기

--node-name hello_node를 붙이면 src/hello_node.cpp와 그것을 빌드·설치하는 줄까지 만들어 준다. ⑤절의 ament_target_dependencies 판이 그 결과다. 만들어지는 소스는 노드가 아니라 printf("hello world …") 한 줄짜리 main이다. 이름은 node인데 노드는 없는 셈이라, 오늘은 쓰지 않고 손으로 더했다.

파이썬 패키지(ament_python)는 어떻게 다른가

--build-type ament_python으로 만들면 CMakeLists.txt 대신 setup.py·setup.cfg가 생기고, 실행 파일 등록은 setup.py의 entry_points에서 한다. package.xml은 똑같이 있다 — colcon·rosdep이 읽는 쪽은 언어와 상관이 없기 때문이다. 15회에서 본 「노드는 언어가 달라도 붙는다」가 여기서도 보인다. 이 과목은 C++만 쓴다.

21회에 install()이 한 번 더 나온다

오늘의 install(TARGETS …)은 빌드 결과물을 옮긴다. 21회에는 launch 파일과 파라미터 YAML 파일처럼 빌드하지 않는 파일을 옮기는 install(DIRECTORY launch config DESTINATION share/${PROJECT_NAME})이 나온다. 실행 파일은 lib/, 나머지 파일은 share/로 간다는 것만 기억해 두면 그때 덜 헷갈린다.
