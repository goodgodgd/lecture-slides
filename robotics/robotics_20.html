오늘 답할 질문
  1. 내 노드가 /turtle1/cmd_vel에 속도 명령을 보내려면 코드에 무엇이 있어야 하나?
  2. 「0.1초마다 한 번」을 코드로는 어떻게 적나? while과 sleep으로 적으면 무엇이 안 되나?
  3. 받은 메시지는 콜백에서 어떤 모양으로 받아 두나? 왜 ConstSharedPtr인가?
  4. 달리는 중에 내 노드를 Ctrl+C로 끊으면 거북이는 서나, 마지막 속도로 계속 가나?
  5. AI가 준 노드 코드가 빌드도 되고 실행도 되는데 거북이가 벽에 부딪힌다. 무엇부터 보면 되나?

19회에 만든 hello_node는 그래프에 이름만 올렸을 뿐 어느 화살표에도 이어져 있지 않았다. 오늘은 같은 패키지 turtle_drive에 실행 파일을 하나 더 넣는다. 이름은 wall_stop — 거북이를 앞으로 몰다가 앞에 벽이 가까워지면 세우는 노드다. 7회에 만든 「정면 장애물 판정기」를 기억하는 사람도 있을 것이다. 그때는 숫자 배열을 보고 판정만 했고, 오늘은 판정한 결과로 실제로 거북이를 세운다. 기말 프로젝트의 「콘 앞에서 선다」가 정확히 이 모양이다. 거북이의 자세가 라이다 값으로 바뀔 뿐이다.

노드는 세 단계로 자란다. v1은 0.1초마다 「앞으로 가라」를 보내기만 한다(발행자·타이머). v2는 거북이의 자세를 받아 들고 있는다(구독자). v3는 받은 자세로 벽까지 거리를 재서 가까우면 「서라」를 보낸다. 19회 끝에서 예고한 대로, 오늘 쓰는 콜백은 전부 rclcpp::spin 안에서 불린다. 이것이 왜 중요한지는 ⑩절에서 AI가 준 코드가 보여 준다.

그리고 이 회차의 몸통은 ⑩절이다. 「벽 앞에서 서는 노드를 만들어 줘」라고 하면 돌아오는 그럴듯한 코드를 하나 놓고, 11·12·13회에서 쌓은 검사 목록으로 한 줄씩 훑는다. 그 코드는 빌드되고 실행되는데, 거북이는 벽에 부딪히고, Ctrl+C를 누르면 Segmentation fault가 난다. 왜 그런지를 ①~⑨절에서 배운 것으로 짚을 수 있으면 오늘의 목표에 닿은 것이다.

② 콜백(callback)과 rclcpp::spin 🔴 사람이 한다

개념 — 함수를 넘겨 두면 때가 됐을 때 불러 준다

「0.1초마다 명령을 보낸다」, 「자세가 오면 받아 둔다」 — 이것을 어떻게 적을까? 2부까지의 프로그램은 위에서 아래로 한 줄씩 내려가며 일을 했다. 그런데 메시지는 언제 올지 내가 정하지 못한다. 기다렸다가 오면 처리해야 한다.

그래서 ROS 2는 거꾸로 묻는다. 「이 일이 생기면 무엇을 할지 함수로 미리 넘겨 달라. 때가 되면 내가 부르겠다.」 이렇게 넘겨 두었다가 나중에 불리는 함수를 콜백(callback, 「나중에 다시 불러 준다」)이라고 한다. 14회에서 「저장해 뒀다가 나중에 부르는 람다」를 봤는데, 그것이 바로 콜백이다. 그리고 때가 됐는지 살피다가 콜백을 부르는 일을 하는 것이 19회의 rclcpp::spin이다.

무엇이 생기면누가 불리나오늘 만드는 것
정해 둔 시간이 지났다타이머 콜백on_timer() — 0.1초마다. 판단하고 속도 명령을 보낸다
구독한 토픽에 메시지가 왔다구독 콜백on_pose(msg) — 초당 62.5번(18회 hz). 받은 자세를 들고 있는다
int main(int argc, char ** argv)
{
  rclcpp::init(argc, argv);
  auto node = std::make_shared<WallStop>();   // 생성자에서 발행자·구독자·타이머를 만들고 콜백을 넘긴다
  rclcpp::spin(node);                          // 여기서 기다리다가 일이 생길 때마다 콜백을 부른다
  rclcpp::shutdown();
  return 0;
}
해석: 규칙은 둘이다. 첫째, 콜백은 spin 안에서만 불린다. 메시지가 컴퓨터에 도착해도 spin이 돌지 않으면 아무도 그 콜백을 부르지 않는다. 둘째, 기본 rclcpp::spin은 콜백을 한 번에 하나씩 부른다. 한 콜백이 오래 걸리면 다른 콜백이 그만큼 기다린다 — 그래서 콜백은 짧게 쓴다. 이 기다림이 실제로 얼마나 되는지는 22회에서 시간을 재어 본다.

19회 v3의 로그에서 「spin 에 들어갑니다」와 「signal_handler」 사이가 3초쯤 비어 있었다. 그때는 부를 콜백이 없어서 그냥 기다리기만 했다. 오늘은 그 빈 구간에서 타이머 콜백이 0.1초마다, 구독 콜백이 0.016초마다 불린다.

③ 발행자(publisher) — create_publisher와 publish 🟡 맡기되 검사

개념 — 토픽 하나에 보내는 창구

17회에서 토픽은 「발행자가 보내고 구독자가 받는, 이름 붙은 데이터 흐름」이었다. 코드에서 발행자는 그 흐름에 메시지를 넣는 객체다. 토픽 이름 하나와 메시지 타입 하나로 만들고, 만든 뒤에는 그 타입의 메시지만 넣을 수 있다. 18회 ros2 topic pub이 터미널에서 하던 일을 코드가 하는 것이다. 

// 만들 때 — 노드의 멤버 함수로 만든다. 꺾쇠 안이 메시지 타입, 괄호 안이 토픽 이름과 큐 깊이
cmd_pub_ = this->create_publisher<geometry_msgs::msg::Twist>("/turtle1/cmd_vel", 10);

// 보낼 때 — 메시지 객체를 만들어 칸을 채우고 넘긴다
geometry_msgs::msg::Twist cmd;
cmd.linear.x = 1.0;
cmd_pub_->publish(cmd);

발행자는 노드가 살아 있는 동안 계속 있어야 한다. 그래서 생성자의 지역 변수가 아니라 클래스의 멤버 변수로 들고 있는다. 19회 v3에서 인사말을 멤버로 옮기며 「20회에서 발행자가 이 자리에 들어간다」고 한 것이 이것이다. 생성자 안의 지역 변수에 두면 생성자가 끝나는 순간 발행자가 사라지고, 토픽에서도 빠진다.

④ 타이머(timer) — create_wall_timer (v1) 🟡 맡기되 검사

개념 — 주기마다 콜백을 부르는 객체

발행자는 만들었는데 언제 publish를 부를까? 생성자에서 한 번 부르고 끝내면 안 될까? 18회에서 topic pub --once로 한 번 보냈을 때 거북이가 짧은 호를 그리고 멈췄다. turtlesim은 속도 명령이 1초 넘게 안 오면 거북이를 세운다. 거북이를 계속 가게 하려면 명령을 계속, 일정한 간격으로 보내야 한다.

「일정한 간격으로」를 2부 방식으로 적으면 while 반복 안에 sleep을 넣는 모양이 된다. 그런데 ②절의 규칙을 떠올려 보면 문제가 보인다. while이 main을 붙잡고 있으면 spin에 들어가지 못하고, 그러면 구독 콜백이 불릴 자리가 없다. 13회의 원칙 「이미 있는 것을 먼저 찾는다」를 여기에 적용하면 답이 나온다 — 주기마다 콜백을 불러 주는 것은 ROS 2에 이미 있다. 그것이 타이머다. 

// 주기와 콜백을 넘겨 만든다. 이 객체가 살아 있는 동안 spin 이 주기마다 콜백을 부른다
timer_ = this->create_wall_timer(100ms, [this]() { on_timer(); });
while + sleep_forcreate_wall_timer
주기는 누가 지키나내 반복문spin
그동안 구독 콜백은안 불린다 (반복문 안에서 따로 불러 주지 않는 한)사이사이에 불린다
Ctrl+C를 누르면반복 조건에 rclcpp::ok()가 있어야 끝난다spin이 돌아온다
주기를 바꾸려면반복문 안을 고친다숫자 하나(100ms)를 고친다
해석: 둘째 줄이 결정적이다. while 방식으로도 발행은 된다. 그래서 v1만 놓고 보면 차이가 안 보인다. 차이는 구독이 더해지는 v2에서 드러나고, ⑩절의 받은 코드가 정확히 이 자리에서 무너진다.

// 20회 벽 앞 정지 — v1 (1단계: create_publisher · create_wall_timer — 거북이가 직진한다)
#include <chrono>
#include <memory>

#include "rclcpp/rclcpp.hpp"
#include "geometry_msgs/msg/twist.hpp"

using namespace std::chrono_literals;

class WallStop : public rclcpp::Node
{
public:
  WallStop()
  : Node("wall_stop")
  {
    cmd_pub_ = this->create_publisher<geometry_msgs::msg::Twist>("/turtle1/cmd_vel", 10);
    timer_ = this->create_wall_timer(100ms, [this]() { on_timer(); });
    RCLCPP_INFO(this->get_logger(), "0.1초마다 /turtle1/cmd_vel 에 직진 명령을 보냅니다");
  }

private:
  // 타이머가 0.1초마다 부른다
  void on_timer()
  {
    geometry_msgs::msg::Twist cmd;   // 여섯 칸이 전부 0 으로 시작한다
    cmd.linear.x = 1.0;              // 앞으로 1 m/s
    cmd_pub_->publish(cmd);
  }

  rclcpp::Publisher<geometry_msgs::msg::Twist>::SharedPtr cmd_pub_;
  rclcpp::TimerBase::SharedPtr timer_;
};

int main(int argc, char ** argv)
{
  rclcpp::init(argc, argv);
  auto node = std::make_shared<WallStop>();
  rclcpp::spin(node);            // 타이머 콜백은 이 안에서 불린다
  rclcpp::shutdown();
  return 0;
}

🆕 이 코드에서 처음 나오는 것

주기(14회의 100ms 표기)마다 콜백을 부르는 타이머를 만든다. 이름의 wall은 벽이 아니라 벽시계(wall clock), 곧 실제 흐르는 시간이라는 뜻이다. 오늘 노드 이름의 「벽」과는 상관이 없다. 여기서는 0.1초마다 on_timer()를 부르게 했다.

14회의 람다와 [this] 캡처다. 14회 표에서 「저장해 뒀다가 나중에 부르는 람다는 가리키던 것이 먼저 사라질 수 있으니 조심」이라고 했는데, 여기서는 괜찮다. 이 람다를 들고 있는 타이머가 이 노드의 멤버라서, 노드(this)보다 먼저 사라질 수 없기 때문이다.

⑥ 구독자(subscription)와 ConstSharedPtr (v2) 🔴 사람이 한다

개념 — 메시지가 올 때마다 불리는 콜백

벽 앞에서 서려면 먼저 거북이가 어디 있는지 알아야 한다. turtlesim은 그것을 /turtle1/pose로 초당 62.5번 내보내고 있다. 그 토픽을 받는 객체가 구독자다. 발행자처럼 토픽 이름과 타입으로 만들고, 여기에 메시지가 오면 부를 콜백을 하나 더 넘긴다. 

pose_sub_ = this->create_subscription<turtlesim::msg::Pose>(
  "/turtle1/pose", 10,
  [this](turtlesim::msg::Pose::ConstSharedPtr msg) { on_pose(msg); });

그럼 콜백은 메시지를 어떤 모양으로 받을까? rclcpp는 몇 가지 모양을 다 받아 준다. 그래서 받은 코드마다 모양이 다르다. 12회에서 「읽기만 할 인자는 const &로 받는다」를 배웠고, 11회에서 shared_ptr를 배웠다. 그 둘로 아래 표를 읽을 수 있다.

콜백 인자의 모양콜백마다 메시지 복사받은 메시지를 고칠 수 있나멤버에 들고 있으려면
turtlesim::msg::Pose msg (값 전달)한 번 (12회의 값 전달)사본은 고칠 수 있다사본을 한 번 더 복사
const turtlesim::msg::Pose & msg없다없다복사해야 한다 — 콜백이 끝나면 참조가 가리키던 것을 쓸 수 없다
turtlesim::msg::Pose::SharedPtr msg없다있다포인터만 들고 있으면 된다
turtlesim::msg::Pose::ConstSharedPtr msg없다없다포인터만 들고 있으면 된다
해석: 넷째 줄만 세 칸이 다 좋다. ConstSharedPtr는 std::shared_ptr<const turtlesim::msg::Pose>의 타입 별칭이다 — 복사 없이(포인터로), 고치지 못하게(const), 그리고 11회의 shared_ptr라서 포인터를 멤버에 복사해 두면 메시지가 그대로 살아 있다(참조 횟수가 하나 는다). 오늘처럼 「최신 값을 들고 있다가 타이머에서 쓴다」면 이 모양이 가장 자연스럽다.

Pose는 float 다섯 개(20바이트)라 값으로 받아도 복사 비용이 눈에 띄지 않는다. 그래서 「빌드되고 돌아가니 됐다」로 넘어가기 쉽다. 그런데 24회의 LaserScan에는 거리 값이 360개 들어 있고, 거리 하나가 float 4바이트이니 ranges만 1,440바이트다. 그것을 초당 다섯 번, 노드마다 복사하게 된다. 12회에서 복사 횟수를 세어 본 그 이야기가 메시지에서 그대로 일어난다. 콜백 인자는 처음부터 ConstSharedPtr로 받는 습관을 들여 두면 메시지가 커져도 고칠 것이 없다.

예제에 적용 — 받은 자세를 멤버에 들고 있는다

구독 콜백(초당 62.5번)과 타이머 콜백(초당 10번)은 부르는 박자가 다르다. 그래서 구독 콜백에서 판단까지 하지 않는다. 구독 콜백은 받은 것을 멤버에 넣어 두기만 하고, 판단과 명령은 타이머 콜백이 그 순간의 최신 자세로 한다. 타이머 사이에 온 자세 대여섯 개 중 앞의 것들은 덮어써져 버려지는데, 속도 명령을 정하는 데는 최신 하나면 되므로 그것이 맞다.

하나 더 정할 것이 있다. 노드가 뜬 직후에는 아직 자세를 한 번도 못 받은 순간이 있다. 그때 판단하면 무엇을 기준으로 판단하는 것일까? 멤버를 ConstSharedPtr로 두면 처음에는 비어 있는(nullptr) 포인터라서, 「아직 모른다」를 if (!pose_) 한 줄로 가를 수 있다. 14회 std::optional이 「값이 없을 수도 있다」를 타입으로 드러냈던 것과 같은 생각이다.

⑧ 정면 장애물 판정 — 앞 벽까지 거리 (v3) 🔴 사람이 한다

개념 — 바라보는 방향으로 곧장 갔을 때 남은 거리

「벽에 가까우면 선다」를 어떻게 판정할까? 가장 먼저 떠오르는 것은 「x가 10보다 크면 선다」다. 지금 거북이는 오른쪽으로만 가니 이것으로도 선다. 그런데 거북이가 왼쪽을 보고 오른쪽 벽 가까이에 있으면 어떨까? 벽에서 멀어지는 중인데도 선다. 반대로 위쪽 벽을 향해 가면 x는 그대로라 서지 않는다. 로봇이 신경 써야 하는 것은 가장 가까운 벽이 아니라 앞에 있는 벽이다. 프로젝트에서도 옆의 콘이 아니라 앞의 콘에서 선다.

그래서 지금 바라보는 방향(theta)으로 곧장 가면 벽까지 몇 m 남았나를 잰다. 방향의 x 성분은 cos θ, y 성분은 sin θ다. 오른쪽 벽(x = 11.0889)까지는 x 방향으로 11.0889 − x가 남았고, 1 m 갈 때마다 x 쪽으로 cos θ만큼 다가가므로 (11.0889 − x) / cos θ m를 가야 닿는다. 네 벽에 대해 이것을 구하고(그 벽 쪽으로 가고 있을 때만), 가장 작은 값이 앞 벽까지의 거리다.

숫자를 넣어 본다x, y, θ앞 벽까지
태어난 자리, 오른쪽을 본다5.54, 5.54, 0cos 0 = 1 → (11.09 − 5.54) / 1 = 5.54 m (오른쪽 벽)
v3가 선 자리10.14, 5.54, 0(11.09 − 10.14) / 1 = 0.95 m
같은 자리에서 왼쪽을 본다10.14, 5.54, πcos π = −1 → (0 − 10.14) / (−1) = 10.14 m (왼쪽 벽) — 서지 않는다
해석: 셋째 줄이 「x > 10이면 선다」와 갈리는 자리다. 같은 위치인데 바라보는 방향에 따라 판정이 바뀐다. 이것이 「정면」 장애물 판정이다.

예제에 적용 — on_timer가 판단한다

v2의 on_timer는 자세를 찍기만 했다. 이제 그 자세로 앞 벽까지 거리를 구하고, 정해 둔 여유(wall_margin_, 1 m)보다 가까우면 0인 Twist를 보낸다. 0인 Twist가 곧 「서라」다 — ④절에서 본 대로 메시지를 만들면 여섯 칸이 전부 0이니, linear.x를 채우지 않고 보내면 된다. 속도·여유·창 크기는 숫자를 코드 곳곳에 흩지 않고 9회의 기본 멤버 초기화자로 한자리에 모은다. 21회에 이 셋 중 둘이 파라미터로 바뀐다. 「섭니다」 로그는 서는 순간에 한 번만 찍도록 stopped_로 앞 상태를 기억한다 — 안 그러면 0.1초마다 같은 줄이 찍힌다.

🆕 이 코드에서 처음 나오는 것

std::cos(θ) · std::sin(θ)
<cmath>의 삼각함수. 각도는 라디안으로 받는다 — Pose의 theta가 라디안이라 그대로 넣었다. 바라보는 방향을 x 성분·y 성분으로 나누는 데 썼다. 좌표와 각도는 25회에서 제대로 다룬다.
std::min(a, b)
<algorithm>에 있는, 두 값 중 작은 것을 돌려주는 함수. 13회의 min_element가 범위에서 가장 작은 값을 찾았다면 이것은 두 값만 비교한다. 여기서는 벽 네 개 중 가장 가까운 앞 벽을 고르는 데 썼다.
std::numeric_limits<double>::infinity()
<limits>가 주는 「무한대」 값. 어떤 거리와 std::min을 해도 그 거리가 이긴다. 그래서 「아직 찾은 벽이 없다」의 출발값으로 썼다. 13회에서 본 라이다의 inf가 바로 이 값이다.
1e-6
0.000001. cos θ가 정확히 0인 방향(바로 위·아래)이면 그 벽 쪽으로는 영영 닿지 않으니 나누지 않는다. 실수는 정확히 0이 되기 어려워 「거의 0」을 이 값으로 갈랐다.

class WallStop : public rclcpp::Node
{
public:
  WallStop()
  : Node("wall_stop")
  {
    cmd_pub_ = this->create_publisher<geometry_msgs::msg::Twist>("/turtle1/cmd_vel", 10);
    pose_sub_ = this->create_subscription<turtlesim::msg::Pose>(
      "/turtle1/pose", 10,
      [this](turtlesim::msg::Pose::ConstSharedPtr msg) { on_pose(msg); });
    timer_ = this->create_wall_timer(100ms, [this]() { on_timer(); });

  void on_pose(turtlesim::msg::Pose::ConstSharedPtr msg)
  {
    pose_ = msg;
  }

  // 타이머가 0.1초마다 부른다 — 판단하고 명령을 보낸다
  void on_timer()
  {
    if (!pose_) {                    // 아직 자세를 한 번도 못 받았다
      return;
    }
    const double front = front_distance(*pose_);
    const bool near_wall = front < wall_margin_;

      RCLCPP_INFO(this->get_logger(), "앞 벽까지 %.2f m — 섭니다 (x = %.2f, y = %.2f)",

    if (s < -1e-6) { d = std::min(d, (0.0 - p.y) / s); }           // 아래쪽 벽
    return d;
  }

  const double speed_ = 1.0;          // 앞으로 가는 속도 (m/s)
  const double wall_margin_ = 1.0;    // 벽 앞 이만큼에서 선다 (m)
  const double world_size_ = 11.0889; // turtlesim 창 한 변의 길이 (m)
  bool stopped_ = false;

  rclcpp::Publisher<geometry_msgs::msg::Twist>::SharedPtr cmd_pub_;
  rclcpp::Subscription<turtlesim::msg::Pose>::SharedPtr pose_sub_;
  rclcpp::TimerBase::SharedPtr timer_;
  turtlesim::msg::Pose::ConstSharedPtr pose_;   // 마지막으로 받은 자세 (처음에는 비어 있다)
};

⚠️ 「끊으면 선다」는 turtlesim의 성질이지 모든 로봇의 성질이 아니다

turtlesim은 마침 타임아웃이 있어서 1초 뒤에 섰다. 모든 로봇의 구동 노드가 이렇게 만들어져 있다는 보장은 없다. 타임아웃이 없는 구동 노드라면 마지막 명령대로 계속 가고, 타임아웃이 있더라도 그 1초 동안 1 m/s 로봇은 1 m를 더 간다. 그래서 프로젝트 노드에는 내 노드 쪽에서도 「센서 값이 일정 시간 안 오면 선다」를 넣는다 — 27회의 「타임아웃 정지」가 그것이다. 실물 터틀봇이 명령이 끊겼을 때 어떻게 하는지는 로봇 앞에서 직접 확인해 볼 자리다(28회).

v3는 이 규칙에 기대지 않는다. 벽 앞에서는 0인 명령을 스스로 보내므로 그 순간에 선다. ⑧절 표의 「서 있을 때도 0인 명령을 계속 보낸다」가 그 뜻이다. 남는 구멍은 달리는 도중에 노드가 끝나는 경우뿐이고, 그때는 받는 쪽의 타임아웃에 맡겨진다. 이 구멍을 어떻게 막을지는 여러분이 실습에서 직접 보고 판단할 거리다.

#include <chrono>
#include <thread>

#include "rclcpp/rclcpp.hpp"
#include "geometry_msgs/msg/twist.hpp"
#include "turtlesim/msg/pose.hpp"

using namespace std::chrono_literals;

rclcpp::Publisher<geometry_msgs::msg::Twist>::SharedPtr cmd_pub;
turtlesim::msg::Pose current_pose;

void pose_callback(const turtlesim::msg::Pose msg)
{
  current_pose = msg;
}

int main(int argc, char ** argv)
{
  rclcpp::init(argc, argv);
  auto node = rclcpp::Node::make_shared("wall_stop");

  cmd_pub = node->create_publisher<geometry_msgs::msg::Twist>("/turtle1/cmd_vel", 1000);
  auto pose_sub = node->create_subscription<turtlesim::msg::Pose>(
    "/turtle1/pose", 1000, pose_callback);

  RCLCPP_INFO(node->get_logger(), "wall_stop node started");

  while (rclcpp::ok()) {
    geometry_msgs::msg::Twist cmd;
    if (current_pose.x < 10.0) {
      cmd.linear.x = 1.0;
    } else {
      cmd.linear.x = 0.0;
      RCLCPP_INFO(node->get_logger(), "Wall detected! Stopping.");
    }
    cmd_pub->publish(cmd);
    std::this_thread::sleep_for(100ms);
  }

  rclcpp::shutdown();
  return 0;
}

이렇게 말하면 된다

「코드 좀 개선해 줘」나 「효율적으로 고쳐 줘」로는 위 일곱 줄이 다 고쳐져 오지 않는 경우가 많다. 고칠 자리를 짚어서 말한다. AI가 만든 C++ 코드를 조사한 한 연구는 C++ 함수 50개를 요청 방식만 달리해 다시 짜게 했다. 아무 말 없이 받은 코드의 효율 점수가 0.294였고, 「효율적으로」라는 일반적인 요구로는 0.342, 무엇이 문제인지 범주를 짚어서 요구했을 때 0.385까지 올라갔다(만점 1.0). 차이를 만든 것은 무엇이 잘못됐는지 아는 것이었다.

이 wall_stop.cpp 를 아래 기준으로 고쳐 줘. 고치기 전에 기준마다 지금 코드의 어느 줄이 어긋나는지 먼저 표로 보여 줘. ① rclcpp::Node 를 상속한 WallStop 클래스로 만들고, 발행자·구독자·타이머·마지막 자세는 전부 멤버로 둬(전역 변수 금지). ② while + sleep_for 대신 create_wall_timer(100ms, …) 를 쓰고 main 은 init → make_shared → spin → shutdown. ③ 구독 콜백 인자는 turtlesim::msg::Pose::ConstSharedPtr 로 받고, 콜백에서는 포인터를 멤버에 저장만 해. ④ 자세를 아직 못 받았으면 타이머 콜백에서 아무것도 보내지 마. ⑤ 판정은 x 대신 「지금 theta 방향으로 갔을 때 앞 벽까지 거리」로 하고, 1.0 m 보다 가까우면 0 인 Twist 를 보내. 속도와 여유 거리는 이름 붙은 멤버로. ⑥ 큐 깊이는 10. 빌드는 ~/ros2_ws 에서 colcon build --packages-select turtle_drive 로 하고, 실행 결과는 내가 직접 볼게.

받은 결과는 ⑧절의 v3와 나란히 놓고 일곱 줄을 다시 훑는다. 모양이 조금 달라도 된다(예: 람다 대신 std::bind — 「조금 더 알아두면」). 마지막 확인은 여러분이 합니다 — 거북이가 벽 앞에서 서는지, hz가 10인지, Ctrl+C 때 Segmentation fault가 없는지.

turtle_drive/src/wall_stop.cpp
#include <chrono>
#include <thread>

#include "rclcpp/rclcpp.hpp"
#include "geometry_msgs/msg/twist.hpp"
#include "turtlesim/msg/pose.hpp"

using namespace std::chrono_literals;

rclcpp::Publisher<geometry_msgs::msg::Twist>::SharedPtr cmd_pub;
turtlesim::msg::Pose current_pose;

void pose_callback(const turtlesim::msg::Pose msg)
{
  current_pose = msg;
}

int main(int argc, char ** argv)
{
  rclcpp::init(argc, argv);
  auto node = rclcpp::Node::make_shared("wall_stop");

  cmd_pub = node->create_publisher<geometry_msgs::msg::Twist>("/turtle1/cmd_vel", 1000);
  auto pose_sub = node->create_subscription<turtlesim::msg::Pose>(
    "/turtle1/pose", 1000, pose_callback);

  RCLCPP_INFO(node->get_logger(), "wall_stop node started");

  while (rclcpp::ok()) {
    geometry_msgs::msg::Twist cmd;
    if (current_pose.x < 10.0) {
      cmd.linear.x = 1.0;
    } else {
      cmd.linear.x = 0.0;
      RCLCPP_INFO(node->get_logger(), "Wall detected! Stopping.");
    }
    cmd_pub->publish(cmd);
    std::this_thread::sleep_for(100ms);
  }

  rclcpp::shutdown();
  return 0;
}

turtlesim::msg::Pose g_pose;      // 마지막으로 받은 자세

{

  while (rclcpp::ok()) {
    rclcpp::spin_some(node);
    if (g_received) {
      const float nearest = std::min(std::min(g_pose.x, 11.0889f - g_pose.x),
                                     std::min(g_pose.y, 11.0889f - g_pose.y));
      std::cout << "가장 가까운 벽까지 " << nearest << " m" << std::endl;
    }
    std::this_thread::sleep_for(500ms);
  }
  rclcpp::shutdown();
  return 0;
}

🆕 이 코드에서 처음 나오는 것

rclcpp::spin_some(node)
지금까지 도착해 있는 일만 처리하고 바로 돌아온다. spin이 「끝날 때까지 기다리며 처리」라면 이것은 「밀린 것만 한 번 처리」다. 그래서 while 안에서 부르면 콜백이 불리기는 한다 — 대신 주기를 지키고 끝낼 때를 정하는 일을 내 반복문이 떠맡는다. 이 코드가 ⑩절의 받은 코드와 달리 돌아가는 이유가 이 한 줄이다.

조금 더 알아두면 시험 범위 아님

std::bind — 람다 대신 받는 코드에 자주 보이는 모양

인터넷 예제와 AI 답에는 콜백을 람다 대신 std::bind로 넘기는 모양이 아주 많다. v3를 이 모양으로 바꿔 빌드·실행해 보니 똑같이 0.94 m에서 섰다. 

#include <functional>
// …
pose_sub_ = this->create_subscription<turtlesim::msg::Pose>(
  "/turtle1/pose", 10,
  std::bind(&WallStop::on_pose, this, std::placeholders::_1));
timer_ = this->create_wall_timer(100ms, std::bind(&WallStop::on_timer, this));

「WallStop::on_pose를 this 객체에 대해 부르는 함수를 만들어라. 첫 번째 인자(_1)는 나중에 들어오는 것을 넘겨라」라고 읽는다. 하는 일은 [this](… msg) { on_pose(msg); }와 같다. 이 과목은 14회에 배운 람다로 쓰지만, 받은 코드에 std::bind가 있다고 틀린 것은 아니다.

왜 AI는 while 반복을 자주 쓰나 — ROS 1의 버릇

ROS 1 시절의 기본 예제(talker)는 ros::Rate loop_rate(10); while (ros::ok()) { …; ros::spinOnce(); loop_rate.sleep(); } 모양이었다. 반복문 안에서 spinOnce(오늘 연습문제의 spin_some에 해당)로 콜백을 처리하고, Rate로 주기를 맞췄다. 이 모양의 예제가 오랫동안 인터넷에 쌓였고, ROS 2로 옮기면서 spinOnce만 빠뜨린 것이 ⑩절의 받은 코드다. ROS 2의 기본 예제는 타이머와 spin으로 짜여 있다. 받은 코드에 Rate나 while (rclcpp::ok())가 보이면 ROS 1 버릇이 섞였을 수 있다고 읽으면 된다(17회 「ROS 1 방식이 섞여 있으면」).

create_wall_timer와 create_timer

오늘 쓴 create_wall_timer는 이름대로 벽시계, 실제 흐르는 시간을 따른다. create_timer는 노드의 ROS 시간을 따른다. 평소에는 둘이 같지만, 22회의 ros2 bag을 기록된 시각대로 재생하거나 시뮬레이터가 시간을 느리게 돌릴 때는 ROS 시간이 실제 시간과 달라진다. 그때는 ROS 시간을 따르는 쪽이 맞다. 지금은 turtlesim이 실제 시간으로 돌므로 어느 쪽이든 같다.

콜백 안에서 바로 발행하는 노드

받은 메시지를 조금 바꿔 다른 토픽으로 바로 넘기는 노드(단위를 바꾸거나, 값을 걸러 내거나)는 타이머 없이 구독 콜백 안에서 publish한다. 그러면 받는 박자 그대로 내보낸다. ⑧절 표 첫 줄의 「안 쓸 때」가 이 경우다. 거북이 자세를 받아 앞 벽까지 거리만 계산해 다른 토픽으로 내보내는 노드라면 이 모양이 자연스럽다.

노드 하나에 콜백이 여럿일 때 — 한 번에 하나씩

오늘 노드에는 콜백이 둘(타이머·구독)이다. 기본 rclcpp::spin은 이것을 차례로 하나씩 부른다. 그래서 두 콜백이 같은 멤버 pose_를 읽고 써도 동시에 건드리는 일이 없다. 콜백을 여러 스레드에서 동시에 부르게 하는 방법(멀티스레드 실행기)도 있는데, 그때는 공유하는 멤버를 지키는 장치가 따로 필요하다. 이 과목의 프로젝트는 기본 spin으로 충분하다.
