상속·다형성과 RAII — 뒷정리를 사람이 하지 않는다

오늘 답할 질문
  1. ROS 2 예제 첫 줄의 class MyNode : public rclcpp::Node — 이 콜론은 무슨 뜻인가?
  2. virtual이 있는 함수와 없는 함수는 무엇을 보고 어느 것을 부를지 정하나?
  3. 소멸자에 virtual을 안 붙였을 뿐인데 왜 메모리가 새나? 그런데 왜 아무 오류도 안 나나?
  4. C++ 코드에는 왜 delete도 close()도 거의 안 보이나?

오늘 배울 것은 둘이다. 앞의 넷은 상속과 다형성이고, 뒤의 셋은 RAII다. 성격이 달라 보이지만 한 줄로 이어진다. 둘 다 「객체가 사라질 때 무슨 일이 일어나는가」의 이야기다. 9회에서 소멸자가 자동으로 불린다는 것을 봤다. 오늘은 그것이 안 불리는 경우(⑤)와, 그것을 믿고 뒷정리를 맡기는 방법(⑥~⑧)을 본다.

오늘은 용어 여덟 개를 다룬다. 절마다 먼저 그 문법이 무엇이고 왜 생겼는지를 설명하고, 그다음에 센서 둘의 값을 읽는 작은 프로그램에 그것을 적용한다. 프로그램은 if 문으로 먼저 짜 두고, 절이 넘어갈 때마다 문법 하나씩으로 고쳐 간다.

무엇을 만드나

센서가 둘이다. 라이다는 거리 360개를 들고 있고 정면(0번) 값을 돌려준다. 초음파는 거리 하나를 돌려준다. 밖에서 하고 싶은 일은 하나다 — 「값을 읽어라.」 센서 종류가 무엇인지는 알고 싶지 않다. 이 작은 바람이 오늘 문법 넷을 차례로 끌어낸다.

읽는 법

  • 먼저 9회까지 배운 것만으로 짠다. 센서마다 클래스 하나, 종류는 번호로 따진다. 이대로도 돌아간다.
  • ②절부터는 절마다 「개념」이 먼저 온다 — 그 문법이 무엇이고 어떤 문제를 풀려고 생겼는지. 그다음 「예제에 적용」에서 지금 프로그램의 어디가 불편한지를 보고, 그 문법으로 고친다.
  • 고치는 자리는 고치기 전(붉은 테두리)과 고친 뒤(푸른 테두리)를 따로 놓는다. 더하기만 하는 단계는 더한 뒤의 모양만 보인다.
  • 그 아래 📄 「전체 코드」 상자를 누르면 그 단계의 main.cpp 전체가 나온다. 첫 줄 주석에 버전(v1, v2, …)이 있다. 어느 버전을 펼쳐도 그대로 빌드되고 돌아간다.
  • 컴파일 오류를 보이는 자리는 한 곳만 일부러 고장 낸 변형 파일이다. 그것도 전체를 상자에 뒀다.
  • 「실제로 나온 출력」에는 그 절이 새로 찍는 줄만 보인다. 전체 출력은 실습 「성공 화면」에 한 번 있다.
  • 빌드는 CMake다. 파일이 main.cpp 하나라 CMakeLists.txt는 끝까지 안 바뀐다.

② 상속 — 공통인 것을 위에 두고 물려받는다 🟡 맡기되 검사

개념 — 기반 클래스와 파생 클래스

상속(inheritance)은 한 클래스가 다른 클래스의 멤버를 전부 물려받아 시작하는 것이다. 물려주는 쪽을 기반 클래스(base class), 물려받는 쪽을 파생 클래스(derived class)라고 한다. 파생 클래스는 물려받은 것에 자기 멤버를 더하거나, 물려받은 멤버 함수를 자기 것으로 다시 정의할 수 있다. 

class Sensor { ... };                    // 기반 클래스 — 모든 센서에 공통인 것
class Lidar : public Sensor { ... };     // 파생 클래스 — 「Lidar 는 Sensor 다」. Sensor 의 멤버를 전부 갖고 시작한다

클래스 이름 뒤의 : public Sensor가 상속이다. public은 「물려받은 멤버의 접근 권한을 그대로 둔다」는 뜻이고, 이 강의에서는 늘 public이다.

상속이 주는 것이 하나 더 있다. 파생 클래스 객체는 기반 클래스 타입의 자리에 들어갈 수 있다. Sensor &로 받는 함수에 Lidar 객체를 넘겨도 되고 Sonar 객체를 넘겨도 된다 — 둘 다 Sensor이기 때문이다. 이것이 「종류를 묻지 않는 함수」를 만드는 열쇠다.

예제에 적용 — 「모든 센서는 read()를 갖는다」를 클래스 하나로 적는다

Lidar와 Sonar 위에 Sensor를 두고, read()를 거기에도 둔다. 그러면 read_any는 Sensor & 하나만 받으면 되고 if가 사라진다. 아직 아무 센서도 아닌 Sensor의 read()는 -1을 돌려주게 했다.

③ 가상 함수와 다형성 — 실제 객체의 함수가 불리게 한다 🟡 맡기되 검사

개념 — 정적 타입과 동적 타입

read_any(Sensor & s) 안에서 s의 타입은 둘로 나뉜다. 참조를 선언한 타입 Sensor가 정적 타입(static type)이고, 실제로 들어 있는 객체의 타입 Lidar가 동적 타입(dynamic type)이다. 상속 덕에 이 둘이 다를 수 있다.

s.read()를 부를 때 어느 타입의 read()를 부를지가 문제다. virtual이 없는 멤버 함수는 정적 타입을 보고 컴파일할 때 정한다 — 그래서 v2에서 Sensor::read()가 불렸다. 기반 클래스에서 함수 앞에 virtual을 붙이면 가상 함수(virtual function)가 되고, 동적 타입을 보고 실행할 때 정한다. 기반 클래스 참조 하나로 여러 파생 클래스의 함수를 골라 부르는 이 성질을 다형성(polymorphism)이라고 한다.

무엇을 먼저 볼지: 가운데 열이 「무엇을 보고 정하나」다.

기반 클래스의 함수가무엇을 보고 정하나실제로 불리는 것언제 정해지나
virtual이 없다정적 타입 (참조·포인터의 타입)Sensor::read컴파일할 때
virtual이 있다동적 타입 (실제 객체의 타입)Lidar::read실행할 때

가상 함수 뒤에 = 0을 붙이면 순수 가상 함수(pure virtual function)다. 「기반 클래스에는 내용이 없고, 파생 클래스가 반드시 채운다」는 뜻이다. 순수 가상 함수가 하나라도 남아 있는 클래스를 추상 클래스(abstract class)라고 하고, 추상 클래스로는 객체를 만들 수 없다. Sensor처럼 「종류가 정해지지 않은 것」은 객체가 있을 이유가 없으니, 이쪽이 -1을 돌려주는 것보다 정확하다.

④ override — 재정의하려는 의도를 컴파일러에게 적어 둔다 🟡 맡기되 검사

개념 — 재정의는 이름·인자·const가 정확히 같아야 성립한다

파생 클래스가 기반 클래스의 가상 함수를 자기 것으로 다시 정의하는 것을 재정의(override)라고 한다. 재정의가 성립하려면 이름, 인자 목록, const 여부가 기반 클래스의 것과 정확히 같아야 한다. 하나라도 다르면 재정의가 아니라 그 이름의 새 함수를 하나 더 만든 것이 되고, 컴파일러는 그것을 잘못으로 보지 않는다.

override는 파생 클래스 쪽 함수의 인자 목록 뒤에 붙이는 지정자(specifier)다. 「이 함수는 기반 클래스의 가상 함수를 재정의하는 것이다」라고 선언하는 것이고, 동작은 바꾸지 않는다. 하는 일은 하나다 — 그런 가상 함수가 위에 없으면 컴파일을 멈춘다. 

float read() override { ... }   // 「위에 virtual float read() 가 있어야 한다」 — 없으면 컴파일 오류

예제에 적용 — 파생 클래스의 read()에 붙인다

4단계 (v4) — override를 붙인다

고치기 전 (v3)
  float read() { return buf_.at(0); }     // Lidar
  float read() { return dist_; }          // Sonar
고친 뒤 (v4)
  float read() override { return buf_.at(0); }     // Lidar
  float read() override { return dist_; }          // Sonar

개념 — 소멸자도 멤버 함수라서 ③절의 규칙이 그대로 적용된다

9회에서 소멸자는 객체가 사라질 때 자동으로 불리는 멤버 함수라고 했다. 멤버 함수이므로 ③절의 규칙이 그대로 적용된다 — virtual이 없으면 정적 타입의 소멸자가, 있으면 동적 타입의 소멸자가 불린다.

문제가 되는 상황은 하나다. 기반 클래스 포인터(정적 타입 Sensor)가 파생 클래스 객체(동적 타입 Lidar)를 잡고 있다가 지울 때. 소멸자가 virtual이 아니면 Sensor의 소멸자만 불리고 Lidar의 소멸자는 불리지 않는다. Lidar가 들고 있던 원소 360개는 돌아오지 않는다. 오류도 크래시도 없다.

그래서 규칙은 한 줄이다. 가상 함수가 하나라도 있는 클래스의 소멸자는 virtual로 만든다. 가상 함수가 있다는 것은 기반 클래스 참조나 포인터로 다룰 클래스라는 뜻이고, 그러면 언젠가 그 포인터로 지우게 되기 때문이다. 파생 클래스의 소멸자는 따로 virtual을 안 적어도 가상 함수가 된다 — 기반 클래스에서 물려받는다.

예제에 적용 — 생성자·소멸자가 말을 하게 하고, 기반 클래스 포인터로 잡아 본다

소멸자가 불리는지 눈으로 보려면 생성자와 소멸자가 화면에 한 줄씩 찍게 하면 된다. 세 클래스에 소멸자를 넣는데, Sensor의 소멸자에는 일부러 virtual을 안 붙였다 — AI가 기반 클래스를 만들어 줄 때 가장 흔한 모양이 이것이다. 그리고 main에 「정적 타입은 Sensor, 동적 타입은 Lidar」인 블록을 하나 더한다.

⑥ RAII — 자원의 수명을 객체의 수명에 묶는다 🟡 맡기되 검사

개념 — 얻은 것은 소멸자가 돌려준다

메모리, 열어 둔 파일, 잠근 자물쇠처럼 쓰고 나면 반드시 돌려줘야 하는 것을 자원(resource)이라고 한다. 자원의 어려움은 얻는 쪽이 아니라 돌려주는 쪽에 있다 — 돌려주는 줄을 빠뜨리면 새고, 함수를 빠져나가는 길이 여럿이면 길마다 챙겨야 한다.

C++의 답은 자원을 객체 안에 넣는 것이다. 생성자에서 자원을 얻고, 소멸자에서 돌려준다. 9회 ③절에서 본 대로 소멸자는 객체가 스코프를 벗어날 때 자동으로 불리므로 — return으로 나가든 오류로 튀어나가든 — 자원은 객체가 사라지는 순간 반드시 돌아온다. 이 설계 방식을 RAII라고 한다. Resource Acquisition Is Initialization(자원 획득이 곧 초기화)의 약자인데 이름은 잊어도 된다. 기억할 것은 「스코프가 곧 수명이다」 한 줄이다.

앞 절까지 계속 본 것이 이미 RAII다. Lidar는 생성자에서 원소 360개를 얻고 소멸자에서 반납했고, 아무도 반납하라고 시키지 않았다. std::vector와 std::string도 같은 방식으로 만들어져 있다.

예제에 적용 — 중괄호를 겹쳐서 수명을 눈으로 본다

⑦ 파일도 잠금도 같은 원리다 — std::ofstream · std::lock_guard 🟡 맡기되 검사

개념 — 표준 라이브러리의 자원 객체는 이미 RAII로 만들어져 있다

우리가 만든 Lidar만 그런 것이 아니다. 표준 라이브러리에서 자원을 다루는 클래스는 전부 RAII로 만들어져 있다. 파일을 쓰는 std::ofstream은 생성자에서 파일을 열고 소멸자에서 닫는다. 자물쇠를 잠그는 std::lock_guard는 생성자에서 잠그고 소멸자에서 푼다. 그래서 close()나 unlock()을 직접 부르는 줄이 없는 것이 정상이다.

무엇을 먼저 볼지: 가운데 「사람이 부르면」 열을 본다. 셋 다 부를 필요가 없다.

무엇을 잡나사람이 부르면안 부르면
메모리 (std::vector·unique_ptr)delete — 빠뜨리면 샌다중괄호를 나갈 때 반납된다
파일 (std::ofstream)close() — 빠뜨리면 내용이 저장 안 될 수 있다중괄호를 나갈 때 닫힌다
잠금 (std::lock_guard)unlock() — 빠뜨리면 프로그램이 멈춘다중괄호를 나갈 때 풀린다

개념 — 동적 할당과 그 짝

new Lidar()는 스코프와 무관하게 살아 있는 객체를 만들어 그 주소(포인터)를 돌려준다. 이것을 동적 할당(dynamic allocation)이라고 한다. 스코프를 벗어나도 안 사라지므로 사람이 delete로 지워야 한다. 규칙은 한 줄이라 쉬워 보인다. 문제는 함수를 빠져나가는 길이 하나가 아니라는 것이다. return이 셋이면 delete도 셋이어야 하고, 나중에 return을 하나 더 넣으면 delete도 하나 더 넣어야 한다. 언젠가는 빠뜨린다.

C++의 답은 ⑥절과 같다 — 포인터를 객체 안에 넣는다. ⑤절에서 본 std::unique_ptr가 그 객체다. 생성자에서 주소를 받아 두고 소멸자에서 delete한다. 그러면 함수를 어느 길로 나가든 스코프를 벗어나는 순간 지워진다. std::make_unique<Lidar>()는 new Lidar()와 unique_ptr를 한 줄로 합친 것이다. RAII를 메모리에 적용한 것이 스마트 포인터이고, 12회에서 따로 다룬다.

// 10회 연습문제 — 배터리·온도 기록기. 오늘 배운 것을 하나도 안 쓴 코드
#include <fstream>
#include <iostream>
#include <string>

class Battery
{
public:
  Battery() : volt_(11.8f) { std::cout << "  [Battery 생성]\n"; }
  ~Battery() { std::cout << "  [Battery 소멸자]\n"; }
  float read() { return volt_; }
private:
  float volt_;
};

class Thermo
{
public:
  Thermo() : celsius_(41.5f) { std::cout << "  [Thermo 생성]\n"; }
  ~Thermo() { std::cout << "  [Thermo 소멸자]\n"; }
  float read() { return celsius_; }
private:
  float celsius_;
};

// 종류를 밖에서 따진다
float read_kind(int kind, Battery & b, Thermo & t)
{
  if (kind == 0) { return b.read(); }
  else if (kind == 1) { return t.read(); }
  return -1.0f;
}

// 한 줄을 파일에 남긴다. dry_run 이면 아무것도 안 쓰고 나간다
bool log_once(int kind, bool dry_run)
{
  Battery * b = new Battery();
  Thermo * t = new Thermo();
  std::ofstream f("health_log.txt", std::ios::app);
  if (dry_run) { return false; }               // 여기로 나가면 b, t 가 안 지워진다
  f << "kind " << kind << " = " << read_kind(kind, *b, *t) << "\n";
  f.close();
  delete b;
  delete t;
  return true;
}

int main()
{
  std::ofstream("health_log.txt");             // 파일을 비운다
  std::cout << "① 배터리\n";  log_once(0, false);
  std::cout << "② 온도\n";    log_once(1, false);
  std::cout << "③ 연습 실행\n"; log_once(0, true);

  std::ifstream in("health_log.txt");
  std::string line;
  while (std::getline(in, line)) { std::cout << "  파일: " << line << "\n"; }
  return 0;
}

할 일

이 코드를 오늘 프로그램이 v1에서 v9로 간 것과 같은 길로 고친다. 파일에 남는 두 줄은 같아야 하고, ③에서 소멸자 줄이 나와야 한다. 직접 쳐도 되고 에이전트에게 시켜도 된다 — 단, 받은 코드에서 아래 항목이 전부 됐는지는 사람이 확인한다.

고칠 것오늘 어디서 했나확인하는 법
기반 클래스 Sensor를 두고 Battery·Thermo가 상속한다. read()는 순수 가상 함수② ③read_kind와 kind 번호가 없어진다. Sensor & 하나로 받는다
파생 클래스의 read()에 override④이름을 일부러 틀리면 빌드가 막힌다
Sensor의 소멸자를 virtual로⑤unique_ptr<Sensor>로 잡은 객체가 사라질 때 파생 클래스 소멸자 줄이 찍힌다
new/delete를 없앤다 — 그냥 변수로 만들거나 make_unique⑧파일에 new·delete가 없다. ③에서 소멸자 줄이 나온다
f.close()를 지운다⑦지워도 파일 내용이 같다
이 코드를 오늘 배운 방식으로 고쳐 줘. Battery와 Thermo가 상속하는 기반 클래스 Sensor를 만들고 read()는 순수 가상 함수로, 파생 쪽에는 override를, 기반 클래스 소멸자는 virtual로 해 줘. new/delete와 close()는 없애고 스코프가 정리하게 해 줘. 파일에 남는 두 줄은 지금과 같아야 하고, 한 항목 고칠 때마다 빌드해서 확인해 줘.

정답은 하나가 아니다. 위 표의 「확인하는 법」이 전부 통과하면 된 것이다. 수업 시간에 몇 사람의 결과를 같이 본다.

🤖 오늘 나온 프롬프트 모음 🟢 맡긴다

이럴 때이렇게 말한다
if로 종류를 따지는 코드가 보일 때"기반 클래스 하나를 만들고 종류마다 상속하는 구조로 바꿔 줘. 공통 함수는 순수 가상 함수로 해 줘."
기반 클래스를 받았을 때"상속당하는 클래스의 소멸자에 virtual이 붙어 있는지 확인해 줘. 상속을 안 당하는 클래스에는 붙이지 마."
재정의하는 함수가 있을 때"기반 클래스의 가상 함수를 재정의하는 함수 전부에 override를 붙여 줘. 붙였더니 컴파일이 안 되는 곳은 고치지 말고 먼저 알려 줘."
new가 보일 때"new·delete를 직접 쓰지 말고 스코프가 정리해 주는 방식으로 바꿔 줘. 중간에 return이 여러 개여도 안 새야 해."
close()·unlock()이 보일 때"이 close()가 정말 필요한 줄인지 알려 줘. 소멸자가 대신 해 주는 것이면 지워 줘."
클래스 뼈대를 시킬 때"이 클래스를 나중에 상속할 거야. 소멸자는 virtual로, 재정의할 함수는 virtual + 파생 쪽에 override로 만들어 줘."

✅ 오늘의 점검

조금 더 알아두면 시험 범위 아님

왜 소멸자는 파생 → 기반 순서로 불리나

만들 때와 지울 때의 순서가 반대다. 실행 결과가 그것을 그대로 보여 준다.

[Lidar 생성] 원소 360개 확보     ← 기반이 먼저 만들어지고 파생이 채워진다
[Lidar 소멸자] 원소 360개 반납    ← 파생이 먼저 정리되고
[Sensor 소멸자]              ← 기반이 나중에 정리된다

파생 클래스는 기반 클래스의 것을 쓸 수 있지만 기반 클래스는 파생 클래스의 것을 모른다. 기반을 먼저 지우면 파생이 정리하는 도중에 이미 없어진 것을 건드리게 된다. 「나중에 만든 것이 먼저 사라진다」는 규칙은 중괄호 안의 변수들에도 똑같이 적용된다.

모든 클래스에 virtual 소멸자를 붙이면 안 되나

안 붙이는 것이 맞다. 공짜가 아니기 때문이다. virtual이 하나라도 붙으면 그 클래스의 객체마다 가상 함수 표를 가리키는 자리가 하나 더 붙는다(보통 8바이트). float 두 개짜리 작은 객체를 수만 개 만드는 코드라면 낭비다.

판단 기준 한 줄: 「이 클래스를 누가 상속하나?」 답이 「그렇다」면 붙인다.

= default · = delete · noexcept — 소멸자 옆에서 자주 보이는 표기 
class Sensor {
public:
  virtual ~Sensor() = default;   // "기본으로 해 줘" — { } 와 같은 뜻
  virtual float read() = 0;
};

= default는 「컴파일러가 알아서 만들어 주는 기본 동작을 쓰겠다」는 뜻이다. { }라고 쓰는 것과 결과가 같은데 의도가 코드에 드러난다. = delete는 반대로 「이건 아예 못 쓰게 하라」는 뜻이다. ~Lidar() noexcept의 noexcept는 「이 함수는 오류를 위로 던지지 않는다」는 약속인데, 소멸자에는 적지 않아도 이미 붙어 있다. 셋 다 알아보기만 하면 된다. ROS 2 코드에서 자주 보인다.
