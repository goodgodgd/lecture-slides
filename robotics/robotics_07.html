코드를 읽기 위한 최소 장비

오늘 답할 질문
  1. ROS 2 예제를 열면 보이는 ::, ->, &, <>는 각각 무엇인가?
  2. 옛날 방식으로 짠 C++ 코드와 요즘 코드는 무엇이 다르고, 왜 바꾸나?
  3. 함수에 값을 넘겼는데 고친 것이 원본에 반영되지 않는다면 무엇을 빠뜨린 것인가?
  4. AI가 준 C++ 코드를 보고 "여기가 이상하다"고 말하려면 최소한 무엇을 알아야 하나?

오늘은 문법 수업이 아니라 읽기 연습이다. 이 강의는 학생이 C++ 코드를 처음부터 짜기를 요구하지 않는다. 코드는 에이전트가 짠다. 학생이 하는 일은 받은 코드를 읽고 판단하는 것이다.

그런데 읽으려면 최소한의 장비가 필요하다. const std::vector<float> & ranges라는 한 조각에 기호가 넷 들어 있는데, 그중 하나라도 모르면 학생은 그 줄에서 읽기를 멈춘다. 멈추면 그 아래 스무 줄이 통째로 안 읽힌다.

그래서 오늘은 기호 여덟 개만 다룬다. 다만 하나씩 늘어놓지는 않는다. 라이다 값으로 「멈출까 갈까」를 정하는 작은 프로그램 하나를 옛날 방식으로 먼저 짜 놓고, 기호를 하나씩 적용해 고쳐 간다. 기호마다 「이걸 안 쓰면 무엇이 불편한가」가 먼저 나오고 그다음에 기호가 나온다. 깊은 이야기는 그 기호가 실제로 문제를 일으키는 회차에서 다시 한다.

한 장 요약 — 학기가 끝나도 이 표만 남으면 된다

① 이 화면 한 장에 오늘 배울 기호가 전부 들어 있다 🟢 맡긴다

아래는 VS Code에 C++ 파일 하나를 열어 둔 화면이다. 따로 고른 화면이 아니라 이 과목에서 흔히 만나게 될 모양이다. 오늘 배울 여덟 개 중 일곱 개가 이 한 화면 안에 있다.

이 화면이 안 읽히는 이유는 문법이 어려워서가 아니다. 기호가 셋씩 붙어 나오기 때문이다. const std::string & frame은 사실 세 조각을 이어 붙인 것이다 — "안 바꾼다"(const) + "표준 문자열"(std::string) + "원본을 가리킨다"(&). 조각으로 끊어 읽는 법을 익히면 그 줄이 읽힌다. 오늘 하는 일이 그것이다.

② 오늘 만들 것 — 정면 장애물 판정기, 옛날 방식으로 먼저 🟡 맡기되 검사

무엇을 만드나

라이다가 잰 정면 거리 값 몇 개를 받아 가장 가까운 장애물까지의 거리를 찾고, 그것이 정지 거리보다 가까우면 STOP, 아니면 GO를 찍는 프로그램이다. 27회의 콘 트랙 주행에서 로봇이 실제로 하는 판단을 가장 작게 줄인 것이다. 라이다는 벽이 너무 멀거나 빛이 안 돌아오면 「측정 실패」를 보내는데, 그 값이 INFINITY(무한대)다. 6회 측정 코드에도 이 값이 있었다. 이것을 건너뛰는 것까지가 오늘 프로그램의 전부다.

읽는 법

  • 먼저 이 프로그램을 오늘 배울 기호를 하나도 안 쓰고, 옛날 C 방식 그대로 짠다. 이대로도 돌아간다.
  • 절이 하나 넘어갈 때마다 「이 방식의 무엇이 불편한가」가 먼저 나오고, 기호 하나로 그 자리를 고친다. 본문에는 새로 넣는 줄(초록 바탕)과 지우는 줄(붉은 취소선)만 보인다.
  • 그 아래 📄 「전체 코드」 상자를 누르면 그 단계까지의 파일 전체가 나온다. 어느 단계를 펼쳐도 그대로 빌드되고 돌아간다. 오른쪽 위 「복사」로 통째로 가져갈 수 있다.
  • 「실제로 나온 출력」은 그 단계의 프로그램이 찍은 것 전부다. 출력이 안 변하는 단계가 많은데, 그것도 배울 점이다.

1단계 — 옛날 방식 그대로

C에서 하던 대로 짰다. 값은 배열에, 화면 출력은 printf로, 무한대 판정은 isfinite로. 오늘 배울 기호는 하나도 없다. 그런데도 멀쩡히 돌아간다는 것을 먼저 본다. 

// 7회 — 정면 장애물 판정기. 1단계: 옛날 방식 그대로
#include <stdio.h>     // printf
#include <math.h>      // isfinite, INFINITY

int main()
{
  // 라이다가 잰 정면 8방향 거리 (m). INFINITY 는 측정 실패
  float ranges[8] = {1.20f, 0.83f, INFINITY, 0.65f, 0.71f, INFINITY, 2.40f, 3.10f};
  float stop_dist = 0.7f;                  // 이보다 가까우면 멈춘다

  float best = 1e9f;                       // 아직 아무것도 못 봤다는 뜻으로 큰 값
  for (int i = 0; i < 8; i++) {
    if (!isfinite(ranges[i])) continue;    // 측정 실패는 건너뛴다
    if (ranges[i] < best) best = ranges[i];
  }
  printf("가장 가까운 장애물 %.2f m\n", best);
  if (best < stop_dist) printf("STOP\n");
  else                  printf("GO\n");
  return 0;
}

🆕 이 코드에서 처음 나오는 것

float ranges[8] = { ... };
실수 8칸짜리 배열이다. 칸 수를 코드에 박아 넣는다. 여기서는 라이다 정면 8방향의 거리를 담았다. ranges[i]가 i번째 칸이고 첫 칸은 0번이다.
1e9f
10억을 실수로 적은 것이다(1×10⁹). 여기서는 "아직 아무 값도 못 봤다"는 뜻의 출발값으로 썼다. 어떤 실제 거리든 이것보다는 작다.
continue;
반복문에서 이번 바퀴의 나머지를 건너뛰고 다음 바퀴로 간다. 여기서는 측정 실패 값을 최솟값 후보에서 빼는 데 썼다.

빌드는 CMake 로 한다 — 네 줄이면 된다

6회에서 g++ 한 줄로 빌드했다. 오늘부터는 같은 폴더에 CMakeLists.txt를 하나 두고 빌드한다. 파일이 하나뿐인 지금은 g++과 차이가 없지만, 8회에서 파일이 둘이 되는 순간 이 네 줄이 일을 대신한다. 지금은 내용을 이해하지 않아도 된다. 그대로 복사해 두고, 9회에서 한 줄씩 읽는다. 

cmake_minimum_required(VERSION 3.16)
project(scan_guard CXX)
set(CMAKE_CXX_STANDARD 17)
add_executable(scan_guard main.cpp)

CMakeLists.txt
「무엇을 어떻게 빌드하나」를 적어 두는 파일이다. 이름은 이 철자 그대로여야 한다. 여기서는 main.cpp 하나로 scan_guard라는 실행 파일을 만들라고 적었다.
add_executable(scan_guard main.cpp)
네 줄 중 실제로 일하는 줄이다. 앞은 실행 파일 이름, 뒤는 소스 파일. 소스가 늘면 뒤에 이어 적는다.
cmake -S . -B build
이 폴더(.)의 CMakeLists.txt를 읽어 build/ 폴더에 빌드 준비를 한다. 처음 한 번만 친다.
cmake --build build
준비된 build/에서 실제로 컴파일한다. 코드를 고칠 때마다 이것만 다시 친다.

③ #include는 선언을 붙이고, ::는 소속을 밝힌다 🟢 맡긴다

무엇이 불편한가 — %.2f 한 글자를 잘못 적으면

printf는 값의 타입마다 %d·%f 같은 서식을 사람이 골라 적어야 한다. 실수를 %d(정수용)로 찍으면 어떻게 될까. 1단계 코드에서 그 한 글자만 바꿔 돌려 봤다. 

$ g++ -std=c++17 -O2 -o scan_guard main.cpp
main.cpp:16:31: warning: format ‘%d’ expects argument of type ‘int’, but argument 2 has type ‘double’ [-Wformat=]
   16 |   printf("가장 가까운 장애물 %d m\n", best);   // %d 는 정수용이다
$ ./scan_guard
가장 가까운 장애물 1557695728 m
STOP
해석: 경고만 내고 컴파일은 되고, 실행도 되고, 엉뚱한 숫자가 찍힌다. 로봇이 15억 미터 앞에 장애물이 있다고 믿는 셈이다. 다행히 판정은 best로 하니 STOP은 맞게 나왔지만, 이런 종류의 실수는 실행해 봐야 안다.

2단계 — printf를 std::cout으로

C++에는 타입을 보고 알아서 찍는 출력 도구가 따로 있다. std::cout이다. 서식 글자가 없으니 잘못 적을 자리도 없다. 이것을 쓰려면 파일 맨 위에서 그 도구의 선언을 가져다 붙여야 한다. 그 줄이 #include다. 무한대 판정도 C++ 쪽 이름 std::isfinite로 바꾼다. 

#include <stdio.h>     // printf
#include <math.h>      // isfinite, INFINITY
#include <cmath>       // std::isfinite, INFINITY
#include <iostream>    // std::cout
  // … 배열과 반복문은 그대로 …
    if (!isfinite(ranges[i])) continue;    // 측정 실패는 건너뛴다
    if (!std::isfinite(ranges[i])) continue;    // 측정 실패는 건너뛴다
  // …
  printf("가장 가까운 장애물 %.2f m\n", best);
  if (best < stop_dist) printf("STOP\n");
  else                  printf("GO\n");
  std::cout << "가장 가까운 장애물 " << best << " m\n";
  if (best < stop_dist) std::cout << "STOP\n";
  else                  std::cout << "GO\n";

🆕 이 코드에서 처음 나오는 것

#include <iostream>
꺾쇠 안의 이름을 가진 파일(헤더)을 이 자리에 통째로 붙여 넣으라는 지시다. 그 안에 std::cout의 선언이 있다. 이 줄이 없으면 컴파일러는 cout이라는 이름을 모른다. <stdio.h>·<math.h>는 C 시절의 이름이고, C++에서는 <cmath>처럼 앞에 c를 붙이고 .h를 뗀 이름을 쓴다.
std::cout << 값 << 값;
화면에 찍는다. 화살표 두 개(<<)를 계속 이어 붙이면 왼쪽부터 순서대로 찍힌다. best가 실수라는 것을 컴파일러가 알고 있으니 서식을 적지 않는다. "\n"은 줄바꿈이다.
std::
앞에 붙은 std가 소속이다 — "C++ 표준 라이브러리에 있는 그것". cout도 isfinite도 표준이 준 것이라 std::를 붙여 부른다.

3단계에서 std::vector<float>::size_type을 두 번 적었다. 사람이 이 이름을 매번 정확히 적는 것은 무리다. 조금 다른 타입을 적으면 컴파일은 되는데 그 자리에서 조용히 값이 바뀌거나 복사가 한 번 일어난다. 그리고 반복문의 번호 i는 사실 쓸모가 없다 — 값을 하나씩 보고 싶을 뿐, 몇 번째인지는 관심이 없다.

🆕 이 코드에서 처음 나오는 것

for (auto & x : r)
같은 &다. 그릇에서 값을 복사해 꺼내지 않고 그 칸 자체를 x라고 부른다. 그래서 x = 8.0f가 그릇의 칸을 바꾼다. 이 &가 없으면 함수 안에서도 사본만 고친다.

⚠️ 고쳐야 할 때만 티가 난다 — 읽기만 하는 함수에서는 티가 안 난다

fill_missing은 원본을 고쳐야 하는 함수라 &가 빠진 것이 출력에 드러났다. 그런데 다음 절의 nearest처럼 읽기만 하는 함수는 &가 있든 없든 출력이 글자 하나 안 다르다.

다른 것은 눈에 안 보이는 곳에서 일어난다. &가 없으면 부를 때마다 값 360개를 통째로 하나 더 만들고, 다 쓰면 버린다. 그래서 이 실수는 테스트로 안 잡힌다. 사람이 코드를 읽어야만 잡힌다. 6회에서 본 「AI 코드의 복사 오버헤드 1.39배」가 바로 이 자리다. 11회에서 시간을 재면서 다시 본다.

void report(const lidar::Scan * s, float stop_dist)
{
  if (s == nullptr) {
    std::cout << "아직 스캔이 없다\n";
    return;

  const float best = nearest(s->ranges);   // -> — 가리키는 곳에 가서 칸을 꺼낸다
  std::cout << "[" << s->frame << "] 가장 가까운 장애물 " << best << " m\n";
  if (best < stop_dist) std::cout << "STOP\n";
  else                  std::cout << "GO\n";
}

int main()
{
  const float stop_dist = 0.7f;
  const lidar::Scan * latest = nullptr;    // 아직 아무 스캔도 안 가리킨다
  report(latest, stop_dist);               // 스캔이 오기 전

nullptr
"아직 아무 자리도 안 정했다"는 값이다. 자리를 담는 변수는 이 상태가 될 수 있고, 그래서 쓰기 전에 == nullptr로 먼저 본다. return;은 함수를 그 자리에서 끝낸다 — 돌려줄 값이 없는 함수라 뒤에 아무것도 안 적는다.
s->ranges · s->frame
"그 자리에 가서 칸을 꺼내라"는 뜻이다. ⑧절의 scan.ranges와 하는 일이 같다. 왼쪽에 물건이 있으면 점, 물건이 있는 자리가 있으면 화살표다.
&scan
⑥절의 &와 다른 뜻이다. 변수 앞에 붙으면 "그 변수가 있는 자리(주소)를 달라"는 뜻이다. 타입 뒤에 붙었을 때만 「참조」다. 붙은 자리를 봐야 뜻이 갈린다.

// 측정 실패(inf)를 센서 최대 사거리 8 m 로 바꿔 넣는다
void fill_missing(std::vector<float> & r)      // & — 원본을 받는다. 고쳐야 하니까
{
  for (auto & x : r) {
    if (!std::isfinite(x)) x = 8.0f;

옛날 코드에서는 0이나 NULL을 썼다. 지금도 컴파일된다. 그런데 0은 숫자인지 빈 자리인지 코드만 봐서는 알 수 없다. AI가 준 코드에 NULL이 보이면 오래된 코드를 흉내낸 것이다. nullptr로 바꿔 달라고 하면 된다.

⑩ #include가 파일을 둘로 나눈다 — 그리고 AI가 거기서 하는 실수 🔴 사람이 한다

그래서 파일이 두 개로 나뉜다

③절에서 #include는 다른 파일의 내용을 그 자리에 붙여 넣는 것이라고 했다. 표준 라이브러리만 그렇게 가져오는 것이 아니다. 우리가 만든 것도 그렇게 가져온다. 여기서 C++이 파이썬과 크게 다른 점이 하나 나온다 — "무엇이 있는지"(선언)와 "어떻게 하는지"(정의)를 다른 파일에 나눠 적는다.

🆕 여기서 처음 나오는 것

#include "이름.hpp"
따옴표로 감싸면 내 프로젝트 안에서 먼저 찾는다. 꺾쇠 <>는 시스템에 깔린 것을 찾는다. 내가 만든 헤더를 가져올 때 이 모양을 쓴다. 8회의 예제가 이것이다.
#ifndef / #define / #endif
헤더 파일 맨 위아래를 감싸는 세 줄이다. 아래 코드에 나온다. "같은 헤더가 두 번 들어와도 한 번만 읽히게" 만드는 장치다. 지금은 헤더 파일에 늘 붙어 다니는 세 줄이라는 것만 알아 두면 된다.

제대로 다루는 곳: 8회(헤더와 소스 나누기 — 포함 보호)

무엇을 먼저 볼지: 왼쪽 열이 헤더, 오른쪽이 소스다. 헤더 쪽이 짧아야 정상이다.

헤더 (.hpp) — 무엇이 있는지소스 (.cpp) — 어떻게 하는지
클래스에 무슨 함수가 있는지그 함수가 실제로 무엇을 하는지
함수 이름과 인자 모양, 그리고 세미콜론중괄호 안의 코드 전부
쓰는 쪽이 읽는다빌드할 때만 쓰인다
고치면 이걸 쓰는 파일이 전부 다시 컴파일된다고쳐도 이 파일만 다시 컴파일된다
해석: 마지막 줄이 나누는 진짜 이유다. 파이썬은 파일을 고치면 그 파일만 다시 읽으면 되지만, C++은 헤더 하나를 고치면 그것을 읽는 파일 전부를 다시 컴파일해야 한다. 그래서 헤더는 가볍게 유지한다. 아래 AI 실수가 정확히 이 지점을 어긴다.

실수 1 — 헤더에 함수의 내용까지 적는다

AI에게 "헤더 파일을 만들어 줘"라고 하면 중괄호 안의 코드까지 헤더에 넣는 일이 흔하다. 파일 하나짜리 프로그램에서는 잘 돌기 때문에 알아채기 어렵다.

AI가 보통 주는 코드 🔴
// bad.hpp — 헤더에 함수의 「내용」까지 들어갔다

#define BAD_HPP_
float front(const float * r) { return r[0]; }   // 선언이 아니라 정의다
#endif

무엇이 문제인가

이 헤더를 소스 파일 두 개가 각각 #include하면 같은 함수가 두 벌 만들어진다. 그리고 빌드 마지막 단계에서 터진다. 아래는 실제로 그렇게 해서 나온 오류다.

📝 연습문제 — 옛날 방식 코드를 오늘 배운 것으로 고쳐 본다 🟡 맡기되 검사

아래는 「왼쪽과 오른쪽 중 어느 쪽이 더 비어 있나」를 정하는 프로그램이다. 값 8개 중 앞의 넷이 왼쪽, 뒤의 넷이 오른쪽 방향의 거리다. 오늘 프로그램의 1단계처럼 옛날 방식으로만 짰다. 이대로도 돌아간다. 

// 7회 연습문제 — 어느 쪽으로 돌까. 옛날 방식으로 짠 코드
#include <stdio.h>
#include <math.h>

// 앞의 절반은 왼쪽, 뒤의 절반은 오른쪽 방향의 거리다
float side_min(float r[], int from, int to)
{
  float best = 1e9f;
  for (int i = from; i < to; i++) {
    if (!isfinite(r[i])) continue;
    if (r[i] < best) best = r[i];
  }
  return best;
}

int main()
{
  float ranges[8] = {0.42f, 0.55f, INFINITY, 0.90f, 1.80f, 2.10f, INFINITY, 1.65f};
  float left  = side_min(ranges, 0, 4);
  float right = side_min(ranges, 4, 8);
  printf("왼쪽 %.2f m, 오른쪽 %.2f m\n", left, right);
  if (left > right) printf("LEFT\n");
  else              printf("RIGHT\n");
  return 0;
}

RIGHT

  return best;
}

int main()
{
  float ranges[8] = {0.42f, 0.55f, INFINITY, 0.90f, 1.80f, 2.10f, INFINITY, 1.65f};
  float left  = side_min(ranges, 0, 4);
  float right = side_min(ranges, 4, 8);
  printf("왼쪽 %.2f m, 오른쪽 %.2f m\n", left, right);
  if (left > right) printf("LEFT\n");
  else              printf("RIGHT\n");
  return 0;
}

할 일

이 코드를 오늘 프로그램이 1단계에서 8단계로 간 것과 같은 길로 고친다. 출력은 끝까지 같아야 한다(좌표계 이름이 앞에 붙는 것은 괜찮다). 한 번에 다 고치지 말고, 한 항목을 고칠 때마다 빌드해서 돌려 본다. 직접 쳐도 되고 에이전트에게 시켜도 된다 — 단, 받은 코드에서 아래 항목이 전부 됐는지는 사람이 확인한다.

고칠 것오늘 어디서 했나확인하는 법
printf → std::cout, <stdio.h>·<math.h> → C++ 이름③파일에 printf·.h가 남아 있지 않다
float[8] → std::vector<float>. 4와 8을 코드에 박지 않는다④값을 하나 더 넣어도 절반 계산이 저절로 맞는다 (size() / 2)
타입 이름이 긴 자리는 auto⑤size_type이라는 글자가 없다
측정 실패를 한 번만 손질하는 fill_missing(… & r)을 두고, side_min에서 isfinite를 뺀다⑥side_min 안에 continue가 없다. fill_missing 인자에 &가 있다
읽기만 하는 side_min은 const &로 받는다. 결과도 const⑦side_min 안에서 r에 대입하는 줄을 넣으면 컴파일이 막힌다
좌표계 이름과 거리 값을 lidar::Scan으로 묶는다⑧출력 앞에 [base_scan]이 붙는다
이 C 스타일 코드를 C++17로 고쳐 줘. 배열은 std::vector<float>로, printf는 std::cout으로, 측정 실패(inf)는 fill_missing 함수가 참조로 받아 8 m로 채우게 하고, side_min은 const 참조로 받게 해 줘. 좌표계 이름과 거리 값은 lidar::Scan 구조체로 묶어 줘. 출력은 지금과 같아야 하고, 한 항목 고칠 때마다 빌드가 되는지 확인해 줘.

다 했으면 아래 상자와 견줘 본다. 같을 필요는 없다. 위 표의 「확인하는 법」이 전부 통과하면 된 것이다.

연습문제 — 고친 한 가지 답 (다 해 본 뒤에 연다)

빌드해서 돌리는 법: cmake --build build && ./build/scan_guard

main.cpp
// 7회 연습문제 — 어느 쪽으로 돌까. 오늘 배운 것으로 고친 한 가지 답
#include <cmath>
#include <iostream>
#include <string>
#include <vector>

namespace lidar {
  struct Scan {
    std::string frame;
    std::vector<float> ranges;
  };
}

// 측정 실패(inf)를 센서 최대 사거리 8 m 로 바꿔 넣는다
void fill_missing(std::vector<float> & r)
{
  for (auto & x : r) {
    if (!std::isfinite(x)) x = 8.0f;
  }
}

// from 번째부터 to 번째 앞까지의 최솟값. 읽기만 한다
float side_min(const std::vector<float> & r, std::size_t from, std::size_t to)
{
  float best = 1e9f;
  for (auto i = from; i < to; ++i) {
    if (r.at(i) < best) best = r.at(i);
  }
  return best;
}

int main()
{
  lidar::Scan scan{"base_scan", {0.42f, 0.55f, INFINITY, 0.90f, 1.80f, 2.10f, INFINITY, 1.65f}};
  fill_missing(scan.ranges);

  const auto half = scan.ranges.size() / 2;
  const float left  = side_min(scan.ranges, 0, half);
  const float right = side_min(scan.ranges, half, scan.ranges.size());
  std::cout << "[" << scan.frame << "] 왼쪽 " << left << " m, 오른쪽 " << right << " m\n";
  if (left > right) std::cout << "LEFT\n";
  else              std::cout << "RIGHT\n";
  return 0;
}

✅ 오늘의 점검

조금 더 알아두면 시험 범위 아님

using과 using namespace std; — 자주 보이지만 조심할 것

std::를 매번 적기 귀찮아서 생략하게 해 주는 문법이 있다. 두 가지 모양이다. 

using std::cout;          // ① 이 이름 하나만 std:: 없이 쓰겠다
using namespace std;      // ② std 안의 이름을 전부 std:: 없이 쓰겠다

①은 괜찮고 ②는 조심해야 한다. ②를 쓰면 표준 라이브러리의 모든 이름이 그냥 굴러다니게 되고, 내가 만든 이름과 부딪치면 어느 것이 불렸는지 알 수 없는 상황이 생긴다. count·distance·data처럼 흔한 이름이 표준에도 있다.

특히 헤더 파일에서는 둘 다 쓰지 않는다. 헤더를 읽는 모든 파일에 그 생략이 딸려 들어가기 때문이다. AI가 준 헤더 맨 위에 using namespace std;가 보이면 지워 달라고 하면 된다.

using에는 긴 타입에 짧은 별명을 붙이는 용법도 있다. ROS 2 코드에서 자주 보게 된다. 

using LaserScan = sensor_msgs::msg::LaserScan;   // 별명을 붙였다
중괄호로 초기화하는 모양 — Scan scan{"base_scan", {0.83f, 0.85f}}

⑧절의 lidar::Scan scan{...}이 이 모양이다. 중괄호 안에 값을 순서대로 나열하면 그대로 채워진다. 바깥 중괄호가 Scan을 채우고, 안쪽 중괄호가 ranges를 채운다.

옛날에는 소괄호 ()만 있었는데 C++11부터 중괄호도 쓸 수 있게 됐다. 중괄호 쪽에 이득이 하나 있다 — 값이 잘려 나가는 변환을 막아 준다. int x{3.14};는 소수점이 잘리므로 컴파일러가 거부한다. int x(3.14);는 아무 말 없이 3이 된다.

그래서 값을 채울 때는 중괄호가 조금 더 안전하다. 다만 std::vector에서는 v(5)(칸 5개)와 v{5}(값 5 하나)가 다른 뜻이 되니 그릇을 만들 때는 소괄호와 중괄호를 헷갈리지 않게 쓴다. 6회의 ranges(N)과 오늘의 ranges{1.20f, ...}가 그 둘이다.

auto가 참조와 const를 안 물려받는다는 것

auto는 오른쪽의 타입을 그대로 가져오지 않는다. const와 &는 떼어 버리고 알맹이만 가져온다. ⑥절의 for (auto & x : r)에서 &를 직접 적어야 했던 이유가 이것이다. 

const std::vector<float> & r = scan.ranges;

auto        a = r;   // 복사본이 생긴다   (const 와 & 가 떨어졌다)
const auto & b = r;   // 복사가 없다      (직접 적어 줘야 한다)

그래서 ROS 2 코드에는 const auto &가 세트로 붙어 다닌다. auto만 쓰면 복사가 조용히 한 번 일어난다. 6회에서 본 「AI 코드의 복사 오버헤드 1.39배」 중 상당수가 이 모양이다.

규칙은 더 있지만 이 강의에서 외울 필요는 없다. 기억할 것은 하나다 — 읽기만 할 거면 const auto &라고 통째로 적는다. 11회에서 이 차이를 시간으로 재 본다.
