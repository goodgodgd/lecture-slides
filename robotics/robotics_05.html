로봇공학 · 5회 · 1부 환경과 도구

Git — 열흘 만에 만든 도구

오늘 답할 질문
  1. 왜 파일 이름 뒤에 _최종_진짜최종을 붙이면 안 되나?
  2. GitHub에 올리려는데 비밀번호를 받지 않는다. 그러면 무엇으로 올리나?
  3. add와 commit은 무엇이 다른가? 왜 두 단계인가?
  4. 커밋 하나에 무엇까지 담아야 하나? 크기는 어떻게 정하나?
  5. 에이전트가 커밋도 대신 해 줄 수 있다. 그러면 내가 할 일은 무엇이 남나?

git 명령어를 정리한 자료가 하나 있다. 815줄이고 되돌리기·이동·비교 명령어의 계보까지 다룬다. 그 자료를 다 읽어도 정작 사고가 나는 자리는 안 나온다. 사고는 언제나 같은 두 곳에서 난다 — 커밋 하나에 관계없는 것이 섞여 들어가는 것, 그리고 왜 그렇게 고쳤는지가 아무 데도 안 적혀 있는 것이다.

명령어는 오늘도 에이전트가 대신 친다. "지금 변경사항 커밋해 줘"라고 하면 해 준다. 그런데 「무엇을 한 덩어리로 볼 것인가」와 「왜 이렇게 했는가」는 에이전트가 정해 줄 수 없다.

오늘 자료는 저장소를 하나 만들어 끝까지 이어 간다. GitHub에서 저장소를 만들고, 내 컴퓨터로 받아 오고, 파일을 고쳐 다시 올린다. 중간을 건너뛰면 뒤에서 저장소가 없다.

한 장 요약 — 명령어는 여섯 개, 판단은 두 개

무엇을 먼저 볼지: 왼쪽 「내가 알고 싶은 것」 열만 읽는다. 아래 두 줄이 오늘의 중심이다.

내가 알고 싶은 것 / 하고 싶은 것그때 이걸 친다수준
서버에 있는 저장소를 내 컴퓨터로 받아 온다git clone 주소[알아보기]
지금 무엇이 바뀌어 있나git status[요구]
이번 커밋에 이것만 담겠다git add 파일[판단]
여기까지를 한 덩어리로 굳힌다git commit -m "..."[판단]
내 것을 서버로 올린다git push[알아보기]
서버에 올라온 것을 받아 온다git pull[알아보기]
커밋 하나에 무엇까지 담나 🔴사람이 정한다. 명령어가 아니다[판단]
왜 이렇게 고쳤는지 남긴다 🔴커밋 메시지. 사람이 쓴다[요구]
해석: 위 여섯 줄은 전부 에이전트가 대신 쳐 줄 수 있다. 아래 두 줄은 대신 해 줄 수 없다. 코드를 보면 무엇이 바뀌었는지는 알 수 있지만 왜 그렇게 했는지는 코드 어디에도 안 적혀 있기 때문이다.

아래 출력은 전부 실제로 실행해서 얻은 것이다. 돌린 곳: 컨테이너(우분투 24.04.4 LTS, git 2.43.0). 경로가 /home/ubuntu/…로 찍히는 것은 그 컴퓨터의 계정 이름이 ubuntu이기 때문이다.

화가 나서 만든 도구가 열흘 만에 세계 표준이 됐다 (15분 · 건너뛰어도 됩니다)

① 2002년 — 수천 명이 고치는 프로젝트에 쓸 도구가 없었다

리눅스 커널은 전 세계 수천 명이 동시에 고치는 프로젝트다. 당시 무료로 쓸 수 있던 버전 관리 도구들은 그 규모를 감당하지 못했다. 리누스 토르발스(Linus Torvalds)는 비트키퍼(BitKeeper)라는 상용 도구를 쓰기로 한다. 만든 회사가 커널 개발자에게는 공짜로 쓰게 해 줬다. 조건이 하나 붙었다 — 경쟁 도구를 만들지 말 것.

② 2005년 — 조건이 깨지고, 하루아침에 도구가 사라졌다

커널 개발자 앤드루 트리젤(Andrew Tridgell)이 비트키퍼와 통신하는 도구를 직접 만들었다. 회사는 곧바로 무료 라이선스를 거둬들였다. 수천 명이 매일 쓰던 프로젝트가 버전 관리 도구를 통째로 잃었다. 대안을 찾을 시간이 없었고, 마음에 드는 대안도 없었다.

③ 여기가 재미있다 — 나흘 만에 자기 자신을 관리하기 시작했다

토르발스는 2005년 4월 3일 새 도구를 짜기 시작했다. 4월 7일, 그 도구는 자기 자신의 소스 코드를 그 도구로 관리하기 시작했다. 나흘째다. 그리고 열흘 만에 리눅스 커널 전체를 이 도구로 관리하기 시작한다.

이름은 git이라고 붙였다. 영국 속어로 "멍청이"라는 뜻이다. 본인이 붙인 설명은 이랬다.

"나는 자기중심적인 인간이라 내 프로젝트에 내 이름을 붙인다. 처음엔 리눅스, 이번엔 git."
— 리누스 토르발스

세계에서 가장 많이 쓰이는 개발 도구의 이름이 자기 비하 농담이다. 그리고 그 농담을 20년째 아무도 못 바꾸고 있다.

④ 그래서 지금 우리 손에 남은 것

그 열흘의 목표는 딱 두 가지였다 — 빠를 것, 그리고 망가진 데이터를 즉시 알아챌 것. git의 명령어가 이상하고 예쁘지 않은 이유가 이것이다. 속도와 무결성 말고 나머지를 포기하고 만든 도구다.

⑤ 숫자로 확인한다

무엇숫자어디서 확인했나
첫 줄부터 자기 자신을 관리하기까지4일 (4월 3일 → 4월 7일)기록으로 남은 날짜
리눅스 커널 관리를 넘겨받기까지열흘기록으로 남은 날짜
1.0.0 판이 나오기까지같은 해 12월 21일 (약 8개월)배포 기록
저장소를 만들어 첫 커밋까지 필요한 명령세 줄우리가 직접 돌려 봤다 (아래)

마지막 줄은 오늘 쓸 컨테이너에서 실제로 재 본 것이다. 정말 세 줄이면 끝난다.

$ git init -b main
$ git add .gitignore src/main.cpp
$ git commit -m "콘 트랙 주행 노드 뼈대 추가"
[main (root-commit) 17e94e4] 콘 트랙 주행 노드 뼈대 추가
 2 files changed, 5 insertions(+)

2 files changed, 5 insertions(+) — 이 한 줄이 그 커밋에 들어간 전부다. 이런 한 줄이 남는다는 것이 git이 20년간 안 밀려난 이유다. 나중에 누가 무엇을 왜 넣었는지 되짚을 수 있다.

① _최종_진짜최종은 게을러서 생긴 게 아니다 🔴 사람이 한다

파일 이름 뒤에 판 번호를 붙이는 습관은 필요해서 생긴 것이다. 되돌릴 수 있어야 하니까 지우지 못하고, 어느 것이 최신인지는 이름에 적을 수밖에 없다. 문제는 이 방식이 안 되는 게 아니라, 세 가지를 못 한다는 것이다.

무엇을 먼저 볼지: 오른쪽 열이다. 왼쪽은 이미 겪어 본 것이다.

이름으로 판 관리를 할 때못 하는 것git이 그 자리에 놓는 것
v0.4와 v0.5가 있다 무엇이 달라졌는지 파일을 열어 비교하지 않으면 모른다 커밋마다 바뀐 줄만 따로 남는다
왜 v0.5를 만들었는지 아무 데도 안 적혀 있다. 만든 사람 머릿속에만 있다 커밋 메시지 · PR 설명
둘이 동시에 같은 파일을 고쳤다 한 사람 것이 통째로 덮인다. 덮인 줄도 모른다 브랜치 · 병합 · 충돌 표시
해석: 셋째 줄이 팀 프로젝트에서 가장 크게 터진다. 덮어쓴 사람도 덮인 사람도 그 순간에는 모른다. 며칠 뒤 "내가 고친 게 없어졌다"로 발견된다. git은 이 상황에서 덮지 않고 멈춘 다음 사람에게 물어본다. 이 강의에서 git을 쓰는 첫 번째 이유가 이것이다.

② 준비 — GitHub 가입 · 저장소 만들기 · 토큰 ⛔ 사람이 직접

git은 내 컴퓨터 안에서만 돌아가는 도구다. 그것만으로도 판 관리는 된다. 그런데 노트북이 고장 나면 같이 사라지고, 다른 컴퓨터에서 이어서 할 수도 없다. 그래서 인터넷에 사본을 하나 둔다. 그 자리를 빌려주는 곳이 GitHub이다.

2-1. 가입하고 저장소를 하나 만든다

순서무엇을 하나내가 확인하는 것 ✅
①github.com에서 가입한다로그인한 화면이 나오나
②초록색 New 버튼 → 저장소 이름 sch-robotics이름 칸에 초록색 체크가 뜨나
③Add a README file을 꼭 켠다체크 상자가 켜져 있나
④Create repository저장소 화면에 README.md 한 줄이 보이나
⚠️ ③의 README 체크를 빼지 않는다

이걸 켜면 GitHub이 커밋 하나가 들어 있는 저장소를 만들어 준다. 끄면 완전히 빈 저장소가 되는데, 빈 저장소는 받아 와도 아무것도 없어서 다음 절부터가 성립하지 않는다.

2-2. 토큰을 만든다 — 비밀번호로는 올릴 수 없다

GitHub은 2021년부터 계정 비밀번호로 올리는 것을 막았다. 대신 토큰(token)이라는 긴 글자를 만들어 그것을 비밀번호 자리에 넣는다. 지금 만들어 두지 않으면 ⑦절에서 반드시 막힌다.

순서어디를 누르나
①오른쪽 위 내 사진 → Settings
②왼쪽 목록 맨 아래 Developer settings
③Personal access tokens → Tokens (classic)
④Generate new token (classic)
⑤이름(Note)은 wsl-robotics, 기간(Expiration)은 학기 끝 이후로
⑥권한(Scopes)에서 repo 하나만 켠다
⑦Generate token → 나온 글자를 복사해 둔다
⛔ 토큰은 그 화면을 떠나면 다시 볼 수 없다

만든 직후 한 번만 보여 준다. 창을 닫으면 GitHub도 그 글자를 다시 알려 주지 않는다. 잃어버리면 지우고 새로 만드는 수밖에 없다.

토큰은 비밀번호와 같다. 남에게 보여 주지 않고, 소스 코드나 과제 보고서에 붙여 넣지 않는다. 실수로 GitHub에 올리면 지워도 커밋 기록에 남는다 — ⑨절에서 다시 이야기한다.

⛔ 에이전트에게도 토큰을 화면에 찍게 하지 않는다. 이렇게 말한다.

GitHub에 push 하려는데 인증에서 막혔어. 지금 내 환경에서 가장 간단한 방법으로 인증을 설정해 줘. 토큰을 화면에 그대로 찍지는 마. 설정이 끝나면 내가 확인할 명령 한 줄을 알려 줘.

2-3. git이 깔려 있는지 본다

WSL 우분투에는 보통 이미 들어 있다. 4회에서 배운 대로 확인부터 한다.

$ git --version
git version 2.43.0

숫자가 한 줄 나오면 된다. command not found(4회 ④절의 127)가 나오면 깔면 된다. 

$ sudo apt install git

③ git config — 누가 고쳤는지 남긴다 🟢 맡긴다

무엇이 궁금한가

git은 변경마다 누가 했는지를 같이 적는다. 그래서 이름과 메일을 한 번 등록해 둬야 첫 커밋이 된다. 안 하면 커밋할 때 오류가 난다.

그때 이걸 친다

$ git config --global user.name "Hong Gildong"
$ git config --global user.email "gildong@example.com"
$ git config --global init.defaultBranch main
$ git config --global --list
user.name=Hong Gildong
user.email=gildong@example.com
init.defaultbranch=main

🆕 이 출력에서 처음 나오는 것

--global
이 컴퓨터의 모든 저장소에 적용한다는 뜻이다. 빼면 지금 저장소에만 적용된다. 한 번만 해 두면 된다.
user.name · user.email
커밋에 함께 적히는 만든 사람이다. GitHub 계정과 같은 메일을 쓰면 웹 화면에서 내 사진이 같이 뜬다.
init.defaultBranch main
새 저장소를 만들 때 첫 브랜치 이름을 main으로 한다. 안 정하면 master가 되어 GitHub과 이름이 어긋난다.
해석: 이름과 메일은 확인용이지 인증용이 아니다. 아무 이름이나 적어도 커밋은 된다. 서버에 올릴 자격을 확인하는 것은 ②절의 토큰이다. 둘을 헷갈리면 "이름 적었는데 왜 push가 막히지"에서 시간을 쓴다.

④ git clone — 원격 저장소를 내 컴퓨터로 🟢 맡긴다

무엇이 궁금한가

②절에서 만든 저장소는 GitHub 서버에 있다. 이걸 원격(remote) 저장소라고 한다. 실제 작업은 내 컴퓨터에서 하므로 사본을 하나 받아 와야 한다. 받아 온 쪽을 로컬(local) 저장소라고 한다.

그때 이걸 친다

주소는 GitHub 저장소 화면의 초록색 Code 버튼 → HTTPS에서 복사한다.

$ cd ~/robotics
$ git clone https://github.com/내계정/sch-robotics.git
Cloning into 'sch-robotics'...
done.
$ cd sch-robotics
$ ls -a
.
..
.git
README.md
해석: ls -a에 .git이라는 숨은 폴더가 보인다(4회 ②절). 이 폴더 하나가 저장소의 전부다. 지금까지의 모든 기록이 여기 들어 있다. 이걸 지우면 그냥 파일 뭉치가 되고, 이걸 복사해 가면 저장소가 통째로 따라간다.

🆕 이 출력에서 처음 나오는 것

git clone 주소
원격 저장소를 통째로 내려받아 폴더로 만든다. 기록까지 전부 따라오고, origin이라는 이름도 자동으로 붙는다.
origin
원격 저장소에 붙은 별명이다. 규칙이 아니라 관례인데 거의 모두가 이 이름을 쓴다. 매번 긴 주소를 안 쓰려고 붙였다.
.git
점으로 시작하니 평소에는 안 보이는 폴더다(4회 ②절 ls -a). 여기를 직접 열어 볼 일은 없다.

⑤ git status — 지금 무엇이 바뀌어 있나 [요구]

무엇이 궁금한가

무언가를 하기 전에 언제나 이것부터 본다. 받아 온 직후에는 아무것도 안 바뀌었을 테니, 「깨끗한 상태」가 어떻게 보이는지부터 눈에 넣는다.

그때 이걸 친다

$ git status
On branch main
Your branch is up to date with 'origin/main'.

nothing to commit, working tree clean

세 군데를 본다. 첫 줄 On branch main은 지금 어느 갈래에 서 있는가, 둘째 줄은 서버 사본과 견줘 앞섰나 뒤졌나, 마지막 줄은 고친 것이 있나이다.

이제 4회에서 배운 echo >로 파일을 하나 만들고 다시 친다.

$ echo "print('hello robotics')" > hello.py
$ git status
On branch main
Your branch is up to date with 'origin/main'.

Untracked files:
  (use "git add <file>..." to include in what will be committed)
	hello.py

nothing added to commit but untracked files present (use "git add" to track)
해석: Untracked files 아래에 hello.py가 생겼다. 「git이 아직 모르는 파일」이라는 뜻이다. 파일을 만들었다고 git이 자동으로 챙기지 않는다. 내가 담아 줘야 한다 — 다음 절이다. 그리고 git은 늘 다음에 칠 명령을 괄호 안에 알려 준다. 읽는 습관을 들인다.

⑥ git add와 git commit — 고르고, 굳힌다 🔴 사람이 판단

무엇이 궁금한가

왜 두 단계인가? 「고친 것」과 「이번에 기록할 것」이 같지 않기 때문이다. 파일 다섯 개를 고쳤어도 그중 둘만 한 덩어리로 묶고 싶을 때가 있다. add가 고르는 명령이고 commit이 굳히는 명령이다.

그때 이걸 친다

$ git add hello.py
$ git status
On branch main
Your branch is up to date with 'origin/main'.

Changes to be committed:
  (use "git restore --staged <file>..." to unstage)
	new file:   hello.py

같은 파일이 다른 칸으로 옮겨 갔다. Untracked files에 있던 것이 Changes to be committed로 올라왔다. 이 칸에 있는 것만 다음 커밋에 들어간다. 

$ git commit -m "첫 프로그램 hello.py 추가"
[main 12d2d74] 첫 프로그램 hello.py 추가
 1 file changed, 1 insertion(+)
 create mode 100644 hello.py
$ git log --oneline
12d2d74 첫 프로그램 hello.py 추가
3f5f807 Initial commit

🆕 이 출력에서 처음 나오는 것

git add 파일
저장하는 명령이 아니라 고르는 명령이다. git add .이라고 치면 바뀐 것 전부를 고른다 — 편하지만 무엇이 딸려 들어가는지 안 보게 된다.
git commit -m "메시지"
고른 것을 한 덩어리로 굳히고 이름을 붙인다. -m이 없으면 편집기가 열리므로 그냥 -m으로 적는 것이 낫다.
12d2d74 (해시)
커밋마다 자동으로 붙는 번호표다. 학생마다 다르게 나온다. 이걸로 나중에 그 시점으로 돌아갈 수 있다.
git log --oneline
커밋을 한 줄씩 최신부터 보여 준다. Initial commit은 ②절에서 GitHub이 README를 만들며 넣어 둔 것이다.
해석: 1 file changed, 1 insertion(+) — 이 한 줄이 그 커밋에 들어간 전부다. 나중에 누가 무엇을 왜 넣었는지 되짚을 수 있다는 것이 git이 20년간 안 밀려난 이유다.

⑦ git push — 토큰을 쓰는 자리 🟡 맡기되 검사

무엇이 궁금한가

지금까지 굳힌 것은 전부 내 노트북 안에만 있다. git log에는 보이지만 GitHub 웹 화면에는 아직 없다. 올려야 사본이 생긴다.

그때 이걸 친다

$ git push origin main
Username for 'https://github.com': 내계정
Password for 'https://내계정@github.com': ← 여기에 ②절의 토큰을 붙여 넣는다

To https://github.com/내계정/sch-robotics.git
   3f5f807..12d2d74  main -> main
⚠️ Password라고 쓰여 있지만 계정 비밀번호가 아니다

②절에서 만든 토큰을 붙여 넣는다. 계정 비밀번호를 넣으면 이렇게 막힌다. 

remote: Support for password authentication was removed on August 13, 2021.
fatal: Authentication failed for 'https://github.com/…'

그리고 붙여 넣어도 화면에 아무 글자도 안 보인다. 비밀번호 칸이라 원래 그렇다. 안 쳐진 줄 알고 여러 번 붙여 넣지 않는다. 한 번 붙이고 엔터를 친다.

올라간 뒤에는 GitHub 웹 화면을 새로 고쳐서 hello.py가 보이는지 눈으로 본다. 명령이 오류 없이 끝난 것과 서버에 제대로 올라간 것은 다른 이야기다.

🆕 이 출력에서 처음 나오는 것

git push origin main
내 main의 커밋을 origin(서버)의 main으로 올린다. clone으로 받아 온 저장소는 짝이 이미 맺어져 있어 그냥 git push만 쳐도 된다.
3f5f807..12d2d74
어디서 어디까지 올라갔는지를 해시로 보여 준다. 이 줄이 나오면 올라간 것이다.
git pull
반대 방향이다. 서버에 올라온 것을 내 폴더로 받아 오고 파일까지 바꾼다. 다른 컴퓨터에서 작업했거나 웹에서 고쳤을 때 쓴다. 일을 시작하기 전에 git pull부터 하는 습관이 중요하다.
⛔ git push --force는 시키지 않는다

--force는 서버에 있던 기록을 내 것으로 덮어 버린다. 그 사이에 올라와 있던 커밋이 있으면 그대로 사라진다.

에이전트는 push가 거부되면 --force를 붙여 다시 시도하는 흐름을 자연스럽게 제안한다. 거부된 이유(대개 pull을 안 한 것)를 먼저 확인하는 것이 사람이 할 일이다. 3회의 승인 모드에서 이 명령을 확인 후 실행으로 둔 이유가 이것이다.

⑧ 파일의 상태와 저장소의 세 자리 🔴 사람이 한다

여기까지 여섯 개를 쳐 봤다. 이제 그 명령들이 무엇을 옮긴 것인지 정리한다. 자리가 셋이라는 것만 알면 여섯 개 명령이 전부 제자리를 찾는다.

자리무엇이 있나여기로 보내는 명령
작업트리 (내 폴더)지금 내가 편집기로 보고 있는 파일 그대로—
인덱스 (담는 바구니)이번 커밋에 담기로 고른 것만git add
저장소 (기록)굳어서 이름이 붙은 덩어리들git commit
원격 저장소 (GitHub)남과 같이 보는 사본git push / 받을 때 git pull
해석: 인덱스가 이 표의 핵심이다. 이 자리가 없으면 "고친 것 전부"가 곧 "커밋 하나"가 되어 버린다. 고치는 단위와 기록하는 단위를 따로 정할 수 있게 하려고 가운데에 바구니를 하나 둔 것이다. git add는 저장하는 명령이 아니라 고르는 명령이다.

파일 쪽에서 보면 상태가 넷이다. ⑤⑥절에서 git status가 찍어 준 이름 그대로다.

상태언제 이 상태가 되나git status에서 보이는 말
Untracked파일을 새로 만들었고 아직 add 안 했다Untracked files
Stagedgit add를 했다Changes to be committed
Modified추적 중인 파일을 고쳤고 아직 add 안 했다Changes not staged for commit
Unmodified커밋한 뒤 아무것도 안 고쳤다working tree clean

무엇이 달라졌는지 줄 단위로 본다 — git diff

이미 추적 중인 파일을 고치면 어느 줄이 달라졌는지까지 볼 수 있다.

$ echo "print('one more')" >> hello.py
$ git diff
diff --git a/hello.py b/hello.py
index b555dab..f2106c4 100644
--- a/hello.py
+++ b/hello.py
@@ -1 +1,2 @@
 print('hello robotics')
+print('one more')

맨 아래 두 줄만 보면 된다. 앞에 +가 붙은 줄이 새로 들어간 것이고, -가 붙으면 지워진 것이다. 아무 표시 없는 줄은 그대로다. 커밋하기 전에 이걸 한 번 보는 것이 실수를 가장 많이 막아 준다.

⑨ .gitignore — 올리지 않을 것을 적어 둔다 🟢 맡긴다

무엇이 궁금한가

소스를 빌드하면 결과물 폴더가 생긴다. 이건 소스에서 언제든 다시 만들 수 있는 것이라 올릴 이유가 없다. 그런데 git status는 그것도 꼬박꼬박 알려 준다.

그때 이걸 친다

$ mkdir -p build && echo "binary" > build/out
$ git status --short
?? build/

$ echo "build/" > .gitignore
$ git status --short
?? .gitignore
해석: build/가 목록에서 사라졌다. 이것이 .gitignore가 하는 일의 전부다 — 지우는 것이 아니라 git이 못 본 척하게 한다. 파일은 내 컴퓨터에 그대로 있다. 그리고 .gitignore 자신은 올려야 하는 파일이라 목록에 새로 나타났다.

🆕 이 출력에서 처음 나오는 것

git status --short
같은 내용을 한 줄씩 짧게 보여 준다. ??는 Untracked라는 뜻이다. 익숙해지면 이쪽이 빠르다.
.gitignore
이름이 정확히 이것이어야 한다. 한 줄에 하나씩 무시할 것을 적는다. build/처럼 빗금으로 끝내면 폴더 통째로다.
⚠️ 이미 올라간 뒤에 .gitignore에 적으면 안 사라진다

.gitignore는 아직 git이 모르는 파일에만 효력이 있다. 한 번 커밋에 들어간 파일은 그 뒤에 규칙을 적어도 계속 따라다닌다. 그래서 저장소를 받자마자 .gitignore부터 만든다. 순서가 중요하다.

이미 올려 버렸다면 이렇게 시킨다.

실수로 커밋된 build/ 폴더를 저장소에서만 빼 줘. 내 컴퓨터의 파일은 지우지 말고, .gitignore에도 추가해 줘. 실행할 명령을 먼저 보여 줘.

"내 컴퓨터의 파일은 지우지 말고"를 빼면 진짜로 지워질 수 있다. 되돌릴 수 없는 일 앞에는 언제나 조건을 붙인다(4회 ⑨절).

⛔ 토큰·비밀번호가 들어간 파일은 처음부터 올리지 않는다

한 번 커밋에 들어가면 다음 커밋에서 지워도 그 커밋 안에는 그대로 남는다. GitHub에 올라갔다면 누구든 기록을 뒤져 볼 수 있다. ②절의 토큰을 파일에 적어 두는 습관을 들이지 않는다.

⑩ 커밋 하나의 크기는 명령어가 아니라 사람이 정한다 🔴 사람이 한다

여기부터가 오늘의 본론이다. 앞의 명령 여섯 개는 에이전트가 다 쳐 준다. 이 절만은 대신해 줄 수 없다.

무엇이 궁금한가

지금 .gitignore를 새로 만들었고 hello.py에 줄도 하나 더 넣었다. 둘 다 안 담긴 상태다. git add . 한 번이면 편한데, 그래도 되나? 

$ git add .gitignore
$ git commit -m "빌드 결과는 올리지 않는다"
$ git add hello.py
$ git commit -m "출력 한 줄 추가"
$ git log --oneline
1c813b9 출력 한 줄 추가
d081e4d 빌드 결과는 올리지 않는다
12d2d74 첫 프로그램 hello.py 추가
3f5f807 Initial commit
해석: 두 가지는 목적이 다르므로 커밋도 둘이다. 한 덩어리로 묶었다면 메시지가 "gitignore 추가하고 출력도 바꿈"이 됐을 것이다. 「~하고」가 들어가면 한 덩어리가 아니라는 신호다.
이렇게 쓰지 않는다이렇게 쓴다왜
수정, ㅇㅇ, asdf조향 계산 함수 추가목록을 훑을 때 이 줄만 읽는다
main.cpp 수정출력 문구를 v2 로 바꿈파일 이름은 이미 기록에 있다. 무엇을 했는지를 쓴다
조향 추가하고 문구도 바꿈커밋을 둘로 나눈다「~하고」가 들어가면 한 덩어리가 아니다

영어로 쓸 필요는 없다. 중요한 것은 언어가 아니라 목록을 훑었을 때 무엇을 한 커밋인지 읽히는가이다.

에이전트에게 시키면 🤖

지금 변경사항을 논리적으로 나눠서 커밋해 줘. 메시지는 무엇을 왜 바꿨는지 한국어로 써 줘. 커밋하기 전에 어떻게 나눌지 안을 먼저 보여 줘.

"나눌 안을 먼저 보여 줘"가 이 프롬프트의 값어치다. 나누는 기준은 사람이 정한다. 에이전트는 그 기준대로 손을 움직여 줄 뿐이다.

🧪 실습 — 저장소 하나를 처음부터 끝까지 (35분)

알게 되는 것: 만들기 → 받아 오기 → 고치기 → 올리기 한 바퀴가 도는 감각. 명령어를 외우는 것이 목적이 아니라 어느 자리에서 무엇을 판단해야 하는지를 몸에 넣는 것이다.

준비물: WSL 터미널 하나, 웹 브라우저, GitHub 계정. 로봇도 ROS도 필요 없다.

절차

  1. GitHub에서 저장소를 만든다. (5분)
    이름은 sch-robotics. Add a README file을 켠다. 만든 뒤 초록색 Code 버튼에서 HTTPS 주소를 복사한다.
  2. 토큰을 만든다. (5분)
    ②절의 일곱 단계를 따른다. 권한은 repo 하나만 켠다. 나온 글자를 안전한 곳에 복사해 둔다. 이 창을 닫으면 다시 못 본다.
  3. 이름과 메일을 등록하고 받아 온다. (5분) 
    git config --global user.name "이름"
git config --global user.email "메일"
cd ~/robotics
git clone 복사한주소
cd sch-robotics
git status
    nothing to commit, working tree clean이 보이면 제대로 받아진 것이다.
  4. 파일을 만들고 상태가 바뀌는 것을 본다. (5분)
    echo "print('hello robotics')" > hello.py 뒤 git status → Untracked. git add hello.py 뒤 다시 git status → Changes to be committed. 같은 파일이 칸을 옮겨 가는 것을 눈으로 본다.
  5. 커밋하고 올린다. (7분)
    git commit -m "첫 프로그램 hello.py 추가" 뒤 git push origin main. 비밀번호 자리에 ②의 토큰을 붙여 넣는다. 화면에 글자가 안 보이는 것이 정상이다. GitHub 웹 화면을 새로 고쳐 hello.py가 보이는지 눈으로 확인한다.
  6. .gitignore를 만들고 커밋을 둘로 나눈다. (8분)
    mkdir -p build && echo "binary" > build/out 뒤 git status --short로 ?? build/를 확인한다. echo "build/" > .gitignore를 하고 목록에서 사라지는 것을 본다. 이어서 hello.py에 >>로 한 줄을 더한 뒤, git add를 한 파일씩 하고 각각 커밋한다. 끝나면 git log --oneline으로 커밋 두 개가 각각 한 줄씩 보이는지 본다.

이렇게 되면 성공이다.
① GitHub 웹 화면에 hello.py와 .gitignore가 보이고 build는 없다.
② git log --oneline에 내가 만든 커밋이 각각 한 줄씩 보인다.
③ 커밋 메시지가 서로 다른 일을 말하고 있다. ③이 안 되면 6단계를 다시 한다.

5단계에서 Authentication failed가 나오면 여기를 본다

비밀번호 문제가 아니다. GitHub은 계정 비밀번호로는 push를 받지 않는다. ②절에서 만든 토큰을 넣어야 한다. 토큰을 잃어버렸으면 지우고 새로 만든다.

이 대목은 에이전트에게 통째로 맡겨도 되는 자리다 — 아래 문장을 그대로 쓴다.

GitHub에 push 하려는데 인증에서 막혔어. 지금 내 환경에서 가장 간단한 방법으로 인증을 설정해 줘. 토큰을 화면에 그대로 찍지는 마. 설정이 끝나면 내가 확인할 명령 한 줄을 알려 줘.

이럴 때이렇게 말한다
인증에서 막혔을 때"가장 간단한 방법으로 인증을 설정해 줘. 토큰을 화면에 찍지는 마."
커밋을 시킬 때"논리적으로 나눠서 커밋해 줘. 나눌 안을 먼저 보여 줘."
올리면 안 될 것이 섞였을 때"저장소에서만 빼 줘. 내 컴퓨터의 파일은 지우지 말고."
push가 거부됐을 때"거부된 이유를 먼저 알려 줘. --force는 쓰지 마."
무엇이 바뀌었는지 볼 때"git diff로 바뀐 줄만 보여 줘."

✅ 오늘의 점검

조금 더 알아두면 시험 범위 아님

브랜치 — 갈라놓고 일하는 자리

혼자 쓸 때는 main 하나로 충분하다. 그런데 여럿이 같은 파일을 동시에 고치면 한 사람 것이 통째로 덮인다. 브랜치는 그 사고를 막는 칸막이다. 

$ git switch -c feature/intro   # 새 갈래를 만들고 그리로 옮긴다
Switched to a new branch 'feature/intro'
$ git branch                    # 지금 어디 서 있나
* feature/intro
  main

*가 붙은 줄이 지금 서 있는 갈래다. 여기서 커밋하면 main은 건드려지지 않는다. 다 되면 main으로 돌아가 git merge feature/intro로 합친다.

이 과목에서는 프로젝트를 팀으로 할 때 다시 다룬다.

Pull Request — 합치기 전에 봐 달라고 하는 자리

GitHub에서 브랜치를 올리면 「합쳐 주세요」라고 요청하는 화면을 만들 수 있다. 그게 Pull Request(PR)다. 합치기 전에 남이 볼 기회를 만드는 것이 목적이다.

설명을 다섯 줄로 쓴다 — 무엇을 / 왜 / 어떻게 확인했나 / 안 한 것 / 봐 줬으면 하는 곳. 세 번째 줄만은 사람이 채운다. 나머지 네 줄은 커밋 기록만 봐도 초안이 나오지만, 「어떻게 확인했나」를 에이전트가 채우면 그건 확인이 아니라 소설이다. 에이전트는 내가 화면에서 무엇을 봤는지 모른다.

실수했을 때 되돌리는 법 — 이름만 알아 둔다
이럴 때이걸 찾아본다
아직 add 안 한 변경을 버리고 싶다git restore 파일
add한 것을 바구니에서 빼고 싶다git restore --staged 파일
방금 한 커밋의 메시지를 고치고 싶다git commit --amend
실수로 커밋된 파일을 저장소에서만 빼고 싶다git rm --cached 파일

외우지 않는다. 이런 것이 있다는 것만 알아 두고 그때 에이전트에게 물으면 된다. 다만 되돌리는 명령은 되돌릴 수 없는 경우가 많으므로 "실행 전에 무엇이 어떻게 되는지 먼저 보여 줘"를 꼭 붙인다.
