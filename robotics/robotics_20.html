오늘 답할 질문
  1. 내 노드가 /turtle1/cmd_vel에 속도 명령을 보내려면 코드에 무엇이 있어야 하나?
  2. 「0.5초마다 한 번」을 코드로는 어떻게 적나? while과 sleep으로 적으면 무엇이 안 되나?
  3. 받은 메시지는 콜백에서 어떤 모양으로 받아 두나? 왜 ConstSharedPtr인가?
  4. 달리는 중에 내 노드를 Ctrl+C로 끊으면 거북이는 서나, 마지막 속도로 계속 가나?
  5. AI가 준 노드 코드가 빌드된다. 그래도 무엇을 확인하면 되나?

19회에 만든 hello_node는 그래프에 이름만 올렸을 뿐 어느 화살표에도 이어져 있지 않았다. 오늘은 같은 패키지 turtle_drive에 실행 파일을 하나 더 넣는다. 이름은 패키지와 같은 turtle_drive — 거북이를 무작위로 돌아다니게 하다가, 벽에 가까워지면 중앙 쪽으로 돌려세워 다시 출발시키는 노드다. 이 노드는 21·22회에서도 계속 자란다. 오늘이 그 첫 두 단계다.

노드는 두 단계로 자란다. v1은 0.5초마다 무작위 속도를 보내기만 한다(발행자·타이머). 거북이는 아무 데로나 가다가 결국 벽에 부딪힌다. v2는 거북이의 자세를 받아서(구독자), 정해 둔 범위를 벗어나면 중앙을 볼 때까지 제자리에서 돌고 다시 출발한다. 두 단계 모두 「함수를 넘겨 두면 때가 됐을 때 불러 주는」 콜백으로 움직이고, 그 콜백을 부르는 것은 19회의 rclcpp::spin이다.

마지막 ⑥절에서는 다 만든 노드에서 확인할 것 — 두 파일의 의존성, Ctrl+C 때 거북이, 받은 노드 코드에서 볼 일곱 줄 — 을 짧게 짚는다.

② 발행자(publisher) — create_publisher와 publish 🟡 맡기되 검사

개념 — 토픽 하나에 보내는 창구

17회에서 토픽은 「발행자가 보내고 구독자가 받는, 이름 붙은 데이터 흐름」이었다. 코드에서 발행자는 그 흐름에 메시지를 넣는 객체다. 토픽 이름 하나와 메시지 타입 하나로 만들고, 만든 뒤에는 그 타입의 메시지만 넣을 수 있다. 18회 ros2 topic pub이 터미널에서 하던 일을 코드가 하는 것이다. 

// 만들 때 — 노드의 멤버 함수로 만든다. 꺾쇠 안이 메시지 타입, 괄호 안이 토픽 이름과 큐 깊이
cmd_pub_ = this->create_publisher<geometry_msgs::msg::Twist>("/turtle1/cmd_vel", 10);

// 보낼 때 — 메시지 객체를 만들어 칸을 채우고 넘긴다
geometry_msgs::msg::Twist cmd;
cmd.linear.x = 1.0;
cmd_pub_->publish(cmd);

발행자는 노드가 살아 있는 동안 계속 있어야 한다. 그래서 생성자의 지역 변수가 아니라 클래스의 멤버 변수로 들고 있는다. 19회 v3에서 인사말을 멤버로 옮기며 「20회에서 발행자가 이 자리에 들어간다」고 한 것이 이것이다. 생성자 안의 지역 변수에 두면 생성자가 끝나는 순간 발행자가 사라지고, 토픽에서도 빠진다.

③ 타이머(timer)와 콜백(callback) — create_wall_timer · rclcpp::spin (v1) 🟡 맡기되 검사

개념 — 주기마다 부르는 함수, 그것을 부르는 spin

발행자는 만들었는데 언제 publish를 부를까? 생성자에서 한 번 부르고 끝내면 안 될까? 18회에서 topic pub --once로 한 번 보냈을 때 거북이가 짧은 호를 그리고 멈췄다. turtlesim은 속도 명령이 1초 넘게 안 오면 거북이를 세운다. 거북이를 계속 가게 하려면 명령을 계속, 일정한 간격으로 보내야 한다.

「일정한 간격으로」를 2부 방식으로 적으면 while 반복 안에 sleep을 넣는 모양이 된다. 이것도 발행은 된다. 그런데 오늘 노드는 보내기만 하지 않는다 — v2에서는 거북이의 자세를 받아야 한다. 자세는 언제 올지 내가 정하지 못한다. while이 main을 붙잡고 있으면 그 사이에 온 메시지를 처리할 자리가 없다.

그래서 ROS 2는 거꾸로 묻는다. 「주기마다, 또는 메시지가 오면 무엇을 할지 함수로 미리 넘겨 달라. 때가 되면 내가 부르겠다.」 이렇게 넘겨 두었다가 나중에 불리는 함수를 콜백(callback, 「나중에 다시 불러 준다」)이라고 한다. 14회에서 「저장해 뒀다가 나중에 부르는 람다」를 봤는데, 그것이 바로 콜백이다. 주기마다 콜백을 불러 주는 객체가 타이머이고, 때가 됐는지 살피다가 콜백을 부르는 일을 하는 것이 19회의 rclcpp::spin이다. 

// 주기와 콜백을 넘겨 만든다. 이 객체가 살아 있는 동안 spin 이 주기마다 콜백을 부른다
timer_ = this->create_wall_timer(500ms, [this]() { on_timer(); });

int main(int argc, char ** argv)
{
  rclcpp::init(argc, argv);
  auto node = std::make_shared<TurtleDrive>();   // 생성자에서 발행자·타이머를 만들고 콜백을 넘긴다
  rclcpp::spin(node);                            // 여기서 기다리다가 때가 될 때마다 콜백을 부른다
  rclcpp::shutdown();
  return 0;
}

주기를 바꾸려면반복문 안을 고친다숫자 하나(500ms)를 고친다
해석: 규칙은 둘이다. 첫째, 콜백은 spin 안에서만 불린다. 메시지가 컴퓨터에 도착해도 spin이 돌지 않으면 아무도 그 콜백을 부르지 않는다. 둘째, 기본 rclcpp::spin은 콜백을 한 번에 하나씩 부른다. 한 콜백이 오래 걸리면 다른 콜백이 그만큼 기다린다 — 그래서 콜백은 짧게 쓴다. 이 기다림이 실제로 얼마나 되는지는 22회에서 시간을 재어 본다. v1만 놓고 보면 while과 차이가 안 보인다. 차이는 구독이 더해지는 v2에서 드러난다. ⑥절 검사 목록의 첫 줄이 이 자리다.

19회 v3의 로그에서 「spin 에 들어갑니다」와 「signal_handler」 사이가 3초쯤 비어 있었다. 그때는 부를 콜백이 없어서 그냥 기다리기만 했다. 오늘은 그 빈 구간에서 타이머 콜백이 0.5초마다 불린다. v2에서는 여기에 구독 콜백이 0.016초마다 더해진다.

예제에 적용 — src/turtle_drive.cpp를 새로 만든다

19회 패키지에 실행 파일을 하나 더한다. 소스 이름은 실행 파일 이름과 같게 turtle_drive.cpp로 짓는다. 클래스 이름은 TurtleDrive, 노드 이름은 turtle_drive다. 타이머 콜백 on_timer()는 부를 때마다 앞으로 가는 속도와 도는 속도를 무작위로 하나씩 골라 보낸다. 그러면 거북이가 이리저리 돌아다닌다. 주기를 0.5초로 둔 것은 위에서 본 turtlesim의 1초 규칙 때문이다 — 1초보다 자주 보내야 거북이가 중간에 서지 않는다.

Twist를 쓰므로 의존성 geometry_msgs가 하나 늘고, 19회 ②·③절에서 본 대로 package.xml과 CMakeLists.txt 양쪽에 넣는다. hello_node는 그대로 둔다.

1단계 (v1) — 발행자와 타이머

turtle_drive/src/turtle_drive.cpp (새 파일)
// 20회 turtle_drive — v1 (1단계: create_publisher · create_wall_timer — 무작위로 돌아다닌다)
#include <chrono>
#include <memory>
#include <random>

#include "rclcpp/rclcpp.hpp"
#include "geometry_msgs/msg/twist.hpp"

using namespace std::chrono_literals;

class TurtleDrive : public rclcpp::Node
{
public:
  TurtleDrive()
  : Node("turtle_drive")
  {
    cmd_pub_ = this->create_publisher<geometry_msgs::msg::Twist>("/turtle1/cmd_vel", 10);
    timer_ = this->create_wall_timer(500ms, [this]() { on_timer(); });
    RCLCPP_INFO(this->get_logger(), "0.5초마다 /turtle1/cmd_vel 에 무작위 속도를 보냅니다");
  }

private:
  // 타이머가 0.5초마다 부른다
  void on_timer()
  {
    geometry_msgs::msg::Twist cmd;               // 여섯 칸이 전부 0 으로 시작한다
    cmd.linear.x = random_between(0.2, 1.2);     // 앞으로 0.2 ~ 1.2 m/s
    cmd.angular.z = random_between(-1.0, 1.0);   // 왼쪽(+)·오른쪽(-)으로 최대 1 rad/s
    RCLCPP_INFO(this->get_logger(), "linear.x = %.2f, angular.z = %.2f", cmd.linear.x, cmd.angular.z);
    cmd_pub_->publish(cmd);
  }

  // lo 와 hi 사이의 실수 하나를 고르게 뽑는다
  double random_between(double lo, double hi)
  {
    std::uniform_real_distribution<double> dist(lo, hi);
    return dist(gen_);
  }

  std::mt19937 gen_{std::random_device{}()};   // 난수 생성기 — 실행할 때마다 다른 씨앗으로 시작한다
  rclcpp::Publisher<geometry_msgs::msg::Twist>::SharedPtr cmd_pub_;
  rclcpp::TimerBase::SharedPtr timer_;
};

int main(int argc, char ** argv)
{
  rclcpp::init(argc, argv);
  auto node = std::make_shared<TurtleDrive>();
  rclcpp::spin(node);            // 타이머 콜백은 이 안에서 불린다
  rclcpp::shutdown();
  return 0;
}

🆕 이 코드에서 처음 나오는 것

this->create_wall_timer(500ms, 콜백)
주기(14회의 500ms 표기)마다 콜백을 부르는 타이머를 만든다. 이름의 wall은 벽이 아니라 벽시계(wall clock), 곧 실제 흐르는 시간이라는 뜻이다. 여기서는 0.5초마다 on_timer()를 부르게 했다.
[this]() { on_timer(); }
14회의 람다와 [this] 캡처다. 14회 표에서 「저장해 뒀다가 나중에 부르는 람다는 가리키던 것이 먼저 사라질 수 있으니 조심」이라고 했는데, 여기서는 괜찮다. 이 람다를 들고 있는 타이머가 이 노드의 멤버라서, 노드(this)보다 먼저 사라질 수 없기 때문이다.
rclcpp::TimerBase::SharedPtr
타이머를 들고 있는 멤버의 타입. 발행자와 같은 이유로 멤버여야 한다 — 이 객체가 사라지면 타이머도 멈춘다.
geometry_msgs::msg::Twist cmd; · cmd.angular.z
메시지도 그냥 C++ 구조체다. 만들면 숫자 칸이 전부 0으로 채워진다. 17회에서 본 여섯 칸 중 둘만 채웠다 — linear.x는 앞으로 가는 속도(m/s), angular.z는 제자리에서 도는 속도(rad/s)다. angular.z가 양수면 왼쪽(반시계 방향), 음수면 오른쪽으로 돈다. 둘을 함께 주면 거북이가 곡선을 그린다.
std::mt19937 · std::random_device · std::uniform_real_distribution
<random>의 난수 도구 셋. mt19937은 난수를 만들어 내는 생성기, random_device는 그 생성기의 출발값(씨앗)을 컴퓨터에서 얻어 오는 장치, uniform_real_distribution(lo, hi)는 생성기가 낸 수를 「lo와 hi 사이에 고르게 퍼진 실수」로 바꾸는 분포다. 씨앗이 매번 달라서 실행할 때마다 다른 길로 간다. 생성기는 멤버로 하나만 두고 계속 쓴다 — 부를 때마다 새로 만들면 비슷한 수가 되풀이되기 쉽다.

개념 — 메시지가 올 때마다 불리는 콜백

벽에 부딪히기 전에 돌아서려면 먼저 거북이가 어디 있는지 알아야 한다. turtlesim은 그것을 /turtle1/pose로 초당 62.5번 내보내고 있다. 그 토픽을 받는 객체가 구독자다. 발행자처럼 토픽 이름과 타입으로 만들고, 여기에 메시지가 오면 부를 콜백을 하나 더 넘긴다. 타이머 콜백이 「때가 되면」 불렸다면, 구독 콜백은 「메시지가 오면」 불린다. 부르는 쪽은 똑같이 spin이다. 

pose_sub_ = this->create_subscription<turtlesim::msg::Pose>(
  "/turtle1/pose", 10,
  [this](turtlesim::msg::Pose::ConstSharedPtr msg) { on_pose(msg); });

그럼 콜백은 메시지를 어떤 모양으로 받을까? rclcpp는 몇 가지 모양을 다 받아 준다. 그래서 받은 코드마다 모양이 다르다. 12회에서 「읽기만 할 인자는 const &로 받는다」를 배웠고, 11회에서 shared_ptr를 배웠다. 그 둘로 아래 표를 읽을 수 있다.

콜백 인자의 모양콜백마다 메시지 복사받은 메시지를 고칠 수 있나멤버에 들고 있으려면
turtlesim::msg::Pose msg (값 전달)한 번 (12회의 값 전달)사본은 고칠 수 있다사본을 한 번 더 복사
const turtlesim::msg::Pose & msg없다없다복사해야 한다 — 콜백이 끝나면 참조가 가리키던 것을 쓸 수 없다
turtlesim::msg::Pose::SharedPtr msg없다있다포인터만 들고 있으면 된다
turtlesim::msg::Pose::ConstSharedPtr msg없다없다포인터만 들고 있으면 된다
해석: 넷째 줄만 세 칸이 다 좋다. ConstSharedPtr는 std::shared_ptr<const turtlesim::msg::Pose>의 타입 별칭이다 — 복사 없이(포인터로), 고치지 못하게(const), 그리고 11회의 shared_ptr라서 포인터를 멤버에 복사해 두면 메시지가 그대로 살아 있다(참조 횟수가 하나 는다). 오늘처럼 「최신 값을 들고 있다가 타이머에서 쓴다」면 이 모양이 가장 자연스럽다.

Pose는 float 다섯 개(20바이트)라 값으로 받아도 복사 비용이 눈에 띄지 않는다. 그래서 「빌드되고 돌아가니 됐다」로 넘어가기 쉽다. 그런데 24회의 LaserScan에는 거리 값이 360개 들어 있고, 거리 하나가 float 4바이트이니 ranges만 1,440바이트다. 그것을 초당 다섯 번, 노드마다 복사하게 된다. 12회에서 복사 횟수를 세어 본 그 이야기가 메시지에서 그대로 일어난다. 콜백 인자는 처음부터 ConstSharedPtr로 받는 습관을 들여 두면 메시지가 커져도 고칠 것이 없다.

개념 — 중앙을 보고 있나: 두 방향 사이의 각

범위를 벗어났을 때 「중앙 쪽으로 돌아선다」는 것은 무엇을 재면 될까? 거북이가 바라보는 방향과 거북이에서 중앙으로 가는 방향, 두 방향 사이의 각이다. 이 각이 0이면 중앙을 똑바로 보고 있고, 180°면 중앙을 등지고 있다.

두 방향 사이의 각은 수학 시간에 배운 내적(dot product)으로 구한다. 두 벡터 a, b에 대해 a · b = |a| |b| cos φ이므로, cos φ = (a · b) / (|a| |b|)를 계산해 cos를 거꾸로 풀면(arccos) 각 φ가 나온다.

벡터성분길이
바라보는 방향 h(cos θ, sin θ) — Pose의 theta로 만든다1
중앙으로 가는 방향 d(5.5 − x, 5.5 − y) — 중앙 좌표에서 거북이 좌표를 뺀다√(dx² + dy²)

예를 들어 거북이가 오른쪽 벽 가까이 (10.5, 5.5)에 있으면 d = (−5, 0), 곧 중앙은 왼쪽에 있다. 바라보는 방향만 바꿔 가며 각을 구해 보면 이렇다.

해석: 범위 밖에서 이 각이 크면 제자리에서 돌고, 작아지면(오늘은 20° 안) 다시 출발한다. 「벽까지 몇 m 남았나」를 벽 네 개에 대해 따로 계산할 필요가 없다 — 범위 밖인지는 x·y를 1과 10에 비교하면 되고, 어느 쪽으로 갈지는 이 각 하나가 정한다.

예제에 적용 — 받은 자세는 들고만 있고, 타이머가 판단한다

구독 콜백(초당 62.5번)과 타이머 콜백(초당 2번)은 부르는 박자가 다르다. 그래서 구독 콜백에서 판단까지 하지 않는다. 구독 콜백은 받은 것을 멤버에 넣어 두기만 하고, 판단과 명령은 타이머 콜백이 그 순간의 최신 자세로 한다. 타이머 사이에 온 자세 서른 개 남짓 중 앞의 것들은 덮어써져 버려지는데, 속도 명령을 정하는 데는 최신 하나면 되므로 그것이 맞다.

타이머 콜백이 정하는 것은 셋이다. 창의 한 변이 약 11 m이니 벽에서 1 m 안쪽, 곧 x와 y가 모두 1 ~ 10 안을 다닐 범위로 둔다. 거북이가 범위 밖이고 중앙과의 각이 20°보다 크면 앞으로 가지 않고 제자리에서 왼쪽으로 돈다(linear.x 0, angular.z 1.0). 그 밖에는 v1처럼 무작위로 간다. 범위 밖이어도 중앙 쪽을 보고 있으면 그대로 가게 두는 것이 요점이다 — 그래야 범위 안으로 돌아올 수 있다.

하나 더 정할 것이 있다. 노드가 뜬 직후에는 아직 자세를 한 번도 못 받은 순간이 있다. 그때 판단하면 무엇을 기준으로 판단하는 것일까? 멤버를 ConstSharedPtr로 두면 처음에는 비어 있는(nullptr) 포인터라서, 「아직 모른다」를 if (!pose_) 한 줄로 가를 수 있다. 14회 std::optional이 「값이 없을 수도 있다」를 타입으로 드러냈던 것과 같은 생각이다. 범위·여유·속도 같은 숫자는 코드 곳곳에 흩지 않고 9회의 기본 멤버 초기화자로 한자리에 모은다. 21회에 이 가운데 둘이 파라미터로 바뀐다.

  {

메시지 타입마다 만들어져 있는 타입 별칭. 풀어 쓰면 std::shared_ptr<const turtlesim::msg::Pose>다(설치된 헤더 turtlesim/msg/detail/pose__struct.hpp에 using ConstSharedPtr = …로 적혀 있다). 콜백 인자로도, 멤버 타입으로도 썼다.

메시지를 복사하는 줄이 아니다. 포인터를 복사하는 줄이다. 11회의 shared_ptr 복사라서 참조 횟수가 하나 늘고, 다음 자세가 와서 pose_가 새 포인터로 바뀌면 옛 메시지는 참조 횟수가 0이 되어 지워진다.
rclcpp::Subscription<T>::SharedPtr
구독자를 들고 있는 멤버의 타입. 발행자·타이머와 같은 이유로 멤버여야 한다 — 이것이 사라지면 구독도 끝난다.
std::cos(θ) · std::sin(θ) · std::hypot(x, y) · std::acos(c)
<cmath>의 수학 함수. 각도는 라디안으로 주고받는다 — Pose의 theta가 라디안이라 그대로 넣었다. hypot(x, y)는 √(x² + y²), 곧 벡터의 길이다. acos는 cos를 거꾸로 푼 값(0 ~ π)을 돌려준다. 좌표와 각도는 25회에서 제대로 다룬다.
std::clamp(값, -1.0, 1.0)
<algorithm>의 함수로, 값이 범위를 넘으면 끝값으로 잘라 준다. 실수 계산은 오차가 있어서 cos φ가 1.0000001처럼 나올 수 있는데, acos는 −1 ~ 1 밖의 값을 받으면 숫자가 아닌 값(NaN)을 돌려준다. 그것을 막는 한 줄이다.
0.35 (rad)
라디안으로 적은 약 20°(0.35 × 180 / π ≈ 20.1). 도는 속도가 1 rad/s이고 판단은 0.5초마다이니 한 번 판단할 때마다 약 0.5 rad(29°)씩 돈다. 「20° 안」이라는 창은 양쪽으로 40°라서, 도는 동안 한 번은 그 안에 들어온다.

    const double angle = angle_to_center(*pose_);
    const bool turn_back = outside && angle > turn_tolerance_;   // 범위 밖인데 중앙을 안 보고 있다

    if (turn_back && !turning_) {
      RCLCPP_INFO(this->get_logger(), "범위 밖 (x = %.2f, y = %.2f) — 중앙 쪽으로 돕니다", pose_->x, pose_->y);
    }
    if (!turn_back && turning_) {
      RCLCPP_INFO(this->get_logger(), "중앙을 봅니다 — 다시 출발합니다");
    }
    turning_ = turn_back;

    geometry_msgs::msg::Twist cmd;               // 여섯 칸이 전부 0 으로 시작한다
    if (turn_back) {
      cmd.angular.z = 1.0;                       // 제자리에서 왼쪽으로 돈다 (linear.x 는 0)
    } else {
      cmd.linear.x = random_between(0.2, max_speed_);
      cmd.angular.z = random_between(-1.0, 1.0);
    }
    cmd_pub_->publish(cmd);
  }

  // 바라보는 방향과 「중앙으로 가는 방향」 사이의 각 (0 ~ π rad)
  double angle_to_center(const turtlesim::msg::Pose & p) const
  {
    const double dx = center_ - p.x;             // 중앙으로 가는 방향
    const double dy = center_ - p.y;
    const double hx = std::cos(p.theta);         // 바라보는 방향 (길이 1)
    const double hy = std::sin(p.theta);
    const double cos_angle = (dx * hx + dy * hy) / std::hypot(dx, dy);   // 내적 ÷ 두 길이의 곱
    return std::acos(std::clamp(cos_angle, -1.0, 1.0));
  }

  // lo 와 hi 사이의 실수 하나를 고르게 뽑는다
  double random_between(double lo, double hi)
  {
    std::uniform_real_distribution<double> dist(lo, hi);
    return dist(gen_);
  }

  const double max_speed_ = 1.2;       // 앞으로 가는 속도의 상한 (m/s)
  const double margin_ = 1.0;          // 벽에서 이만큼 안쪽까지만 다닌다 (m) → 1 ~ 10
  const double map_size_ = 11.0;       // 지도 한 변의 길이 (m)
  const double center_ = 5.5;          // 지도 가운데 (x, y 모두)
  const double turn_tolerance_ = 0.35; // 중앙과 이 각(약 20°) 안이면 다시 출발한다 (rad)
  bool turning_ = false;               // 지금 돌아서는 중인가 — 로그를 바뀔 때만 찍는 데 쓴다

  std::mt19937 gen_{std::random_device{}()};   // 난수 생성기 — 실행할 때마다 다른 씨앗으로 시작한다
  rclcpp::Publisher<geometry_msgs::msg::Twist>::SharedPtr cmd_pub_;
  rclcpp::Subscription<turtlesim::msg::Pose>::SharedPtr pose_sub_;
  rclcpp::TimerBase::SharedPtr timer_;
  turtlesim::msg::Pose::ConstSharedPtr pose_;  // 마지막으로 받은 자세 (처음에는 비어 있다)
};

int main(int argc, char ** argv)
{
  rclcpp::init(argc, argv);
  auto node = std::make_shared<TurtleDrive>();
  rclcpp::spin(node);            // 타이머·구독 콜백은 이 안에서 불린다
  rclcpp::shutdown();
  return 0;
}

Ctrl+C — 거북이는 1초쯤 더 가다가 선다

우리 노드에는 Ctrl+C 때 「서라」를 보내는 줄이 없다. 그래도 거북이는 선다. 다만 바로 서지 않고, 마지막 명령대로 약 1초 더 간 뒤에 선다(컨테이너에서 재 보니 마지막 명령 뒤 1.08초). 우리 노드가 한 일이 아니라 ③절 첫머리에서 본 turtlesim의 규칙, 곧 속도 명령이 1초 넘게 안 오면 세우는 명령 타임아웃이다. 모든 로봇의 구동 노드가 이렇게 만들어져 있다는 보장은 없어서, 프로젝트 노드에는 내 노드 쪽에서도 타임아웃 정지를 넣는다(27회).

받은 노드 코드 — 빌드가 돼도 보는 일곱 줄

「돌아다니다가 벽 근처에서 되돌아오는 노드를 만들어 줘」라고 하면 오는 코드에는 ROS 1 시절 예제의 모양이 자주 섞여 있다(「조금 더 알아두면」). 아래 일곱 줄은 모두 빌드를 막지 않는다. 그래서 빌드 성공은 이 중 어느 것도 보증하지 않는다.

검사할 것이렇게 오는 경우가 많다오늘 어디서
1콜백이 불리는 자리(spin)가 있나main이 while (rclcpp::ok()) + sleep_for로 돌고 spin이 없다. 구독 콜백이 한 번도 안 불려 자세가 처음 값 (0, 0)에 머문다③
2주기마다 할 일이 타이머인가while 반복이 sleep_for로 주기를 직접 센다③
3콜백 인자를 ConstSharedPtr로 받나const Pose msg — 값 전달. 콜백마다 복사한다⑤
4발행자·구독자·상태가 노드의 멤버인가전역 변수. 전역 변수는 shutdown 뒤에 지워져서 Ctrl+C 때 Segmentation fault로 끝나기도 한다19회 노드 상속 · ②
5「아직 못 받음」을 따로 다루나기본값 x = 0, y = 0을 진짜 자세처럼 읽는다⑤
6숫자에 이름이 있나큐 깊이 1000, 1.0·10.0·1.5가 맨숫자로 흩어져 있다② · ⑤
7새 의존성이 두 파일 양쪽에 있나#include만 더하고 package.xml은 그대로다이 절 위
해석: 1번은 거북이를 엉뚱하게 움직이고, 4번은 끝낼 때 프로그램을 죽인다. 나머지는 지금 거북이의 움직임을 바꾸지 않아서 「돌아가니 됐다」로 넘어가기 쉽다. 받은 코드는 ⑤절의 v2와 나란히 놓고 이 일곱 줄을 훑으면 된다. 모양이 조금 달라도 된다(예: 람다 대신 std::bind — 「조금 더 알아두면」).

// 20회 연습문제 — wall_watch 원본. 오늘 배운 것을 하나도 안 쓴 노드 (돌아가기는 한다)
#include <algorithm>
#include <chrono>
#include <iostream>
#include <thread>

#include "rclcpp/rclcpp.hpp"
#include "turtlesim/msg/pose.hpp"

using namespace std::chrono_literals;

turtlesim::msg::Pose g_pose;      // 마지막으로 받은 자세
bool g_received = false;

void pose_callback(const turtlesim::msg::Pose msg)
{
  g_pose = msg;
  g_received = true;
}

int main(int argc, char ** argv)
{
  rclcpp::init(argc, argv);
  auto node = rclcpp::Node::make_shared("wall_watch");
  auto sub = node->create_subscription<turtlesim::msg::Pose>("/turtle1/pose", 1000, pose_callback);

  while (rclcpp::ok()) {
    rclcpp::spin_some(node);
    if (g_received) {
      const float nearest = std::min(std::min(g_pose.x, 11.0889f - g_pose.x),
                                     std::min(g_pose.y, 11.0889f - g_pose.y));
      std::cout << "가장 가까운 벽까지 " << nearest << " m" << std::endl;
    }
    std::this_thread::sleep_for(500ms);
  }
  rclcpp::shutdown();
  return 0;
}

std::this_thread::sleep_for(500ms) · rclcpp::ok()
sleep_for는 <thread>의 함수로, 지금 실행 흐름을 그 시간만큼 그냥 멈춰 세운다. 그동안은 콜백도 부르지 않는다. rclcpp::ok()는 Ctrl+C 같은 끝내라는 신호가 아직 안 왔으면 true라서, spin 없이 직접 반복할 때 반복 조건으로 쓴다.
rclcpp::spin_some(node)
지금까지 도착해 있는 일만 처리하고 바로 돌아온다. spin이 「끝날 때까지 기다리며 처리」라면 이것은 「밀린 것만 한 번 처리」다. 그래서 while 안에서 부르면 콜백이 불리기는 한다 — 대신 주기를 지키고 끝낼 때를 살피는 일을 반복문이 다 떠맡는다.

✅ 오늘의 점검

조금 더 알아두면 시험 범위 아님

std::bind — 람다 대신 받는 코드에 자주 보이는 모양

인터넷 예제와 AI 답에는 콜백을 람다 대신 std::bind로 넘기는 모양이 아주 많다. v2를 이 모양으로 바꿔 빌드·실행해 보니 똑같이 1 ~ 10 안에서 돌아다니다 경계에서 돌아섰다. 

#include <functional>
// …
pose_sub_ = this->create_subscription<turtlesim::msg::Pose>(
  "/turtle1/pose", 10,
  std::bind(&TurtleDrive::on_pose, this, std::placeholders::_1));
timer_ = this->create_wall_timer(500ms, std::bind(&TurtleDrive::on_timer, this));

「TurtleDrive::on_pose를 this 객체에 대해 부르는 함수를 만들어라. 첫 번째 인자(_1)는 나중에 들어오는 것을 넘겨라」라고 읽는다. 하는 일은 [this](… msg) { on_pose(msg); }와 같다. 이 과목은 14회에 배운 람다로 쓰지만, 받은 코드에 std::bind가 있다고 틀린 것은 아니다.

왜 늘 왼쪽으로만 도나 — 도는 방향까지 고르려면

v2는 범위 밖에서 언제나 angular.z = 1.0, 곧 왼쪽으로만 돈다. 중앙이 거북이의 오른쪽에 조금 비켜 있으면 왼쪽으로 거의 한 바퀴를 돌아야 중앙을 보게 된다. ⑤절 출력의 마지막 묶음에서 5.5초나 돈 것이 그 경우다. 동작은 맞지만 시간이 걸린다.

중앙이 왼쪽에 있는지 오른쪽에 있는지는 두 방향의 외적(cross product)의 부호로 알 수 있다 — 바라보는 방향 h와 중앙 방향 d에 대해 hx·dy − hy·dx가 양수면 왼쪽, 음수면 오른쪽이다. 그 부호대로 angular.z를 +1 또는 −1로 주면 늘 짧은 쪽으로 돈다. 내적이 「얼마나 다른가」를 준다면 외적은 「어느 쪽으로 다른가」를 준다. 25회에서 좌표와 회전을 다룰 때 다시 만난다.

왜 AI는 while 반복을 자주 쓰나 — ROS 1의 버릇

ROS 1 시절의 기본 예제(talker)는 ros::Rate loop_rate(10); while (ros::ok()) { …; ros::spinOnce(); loop_rate.sleep(); } 모양이었다. 반복문 안에서 spinOnce(오늘 연습문제의 spin_some에 해당)로 콜백을 처리하고, Rate로 주기를 맞췄다. 이 모양의 예제가 오랫동안 인터넷에 쌓였고, ROS 2로 옮기면서 spinOnce만 빠뜨리면 ⑥절 검사 1번의 코드가 된다. ROS 2의 기본 예제는 타이머와 spin으로 짜여 있다. 받은 코드에 Rate나 while (rclcpp::ok())가 보이면 ROS 1 버릇이 섞였을 수 있다고 읽으면 된다(17회 「ROS 1 방식이 섞여 있으면」).

create_wall_timer와 create_timer

오늘 쓴 create_wall_timer는 이름대로 벽시계, 실제 흐르는 시간을 따른다. create_timer는 노드의 ROS 시간을 따른다. 평소에는 둘이 같지만, 22회의 ros2 bag을 기록된 시각대로 재생하거나 시뮬레이터가 시간을 느리게 돌릴 때는 ROS 시간이 실제 시간과 달라진다. 그때는 ROS 시간을 따르는 쪽이 맞다. 지금은 turtlesim이 실제 시간으로 돌므로 어느 쪽이든 같다.

콜백 안에서 바로 발행하는 노드

받은 메시지를 조금 바꿔 다른 토픽으로 바로 넘기는 노드(단위를 바꾸거나, 값을 걸러 내거나)는 타이머 없이 구독 콜백 안에서 publish한다. 그러면 받는 박자 그대로 내보낸다. ⑤절 표 첫 줄의 「안 쓸 때」가 이 경우다. 22회에 만드는 wall_range 노드 — 거북이 자세를 받아 가장 가까운 벽까지 거리만 계산해 다른 토픽으로 내보내는 노드 — 가 이 모양이다.

노드 하나에 콜백이 여럿일 때 — 한 번에 하나씩

오늘 노드에는 콜백이 둘(타이머·구독)이다. 기본 rclcpp::spin은 이것을 차례로 하나씩 부른다. 그래서 두 콜백이 같은 멤버 pose_를 읽고 써도 동시에 건드리는 일이 없다. 콜백을 여러 스레드에서 동시에 부르게 하는 방법(멀티스레드 실행기)도 있는데, 그때는 공유하는 멤버를 지키는 장치가 따로 필요하다. 이 과목의 프로젝트는 기본 spin으로 충분하다.
