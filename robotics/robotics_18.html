로봇공학 · 18회 · 3부 ROS 2

ROS 명령어

오늘 답할 질문
  1. 에이전트가 "노드를 띄웠고 잘 연결되었습니다"라고 했다. 그 말을 무엇으로 확인하나?
  2. 값이 실제로 흐르고 있는지, 흐른다면 초당 몇 번인지 어떻게 보나?
  3. 노드를 하나도 만들지 않고 터미널에서 거북이를 움직이고, 배경색을 바꾸고, 거북이를 하나 더 부를 수 있나?
  4. 명령을 보냈는데 거북이가 꿈쩍도 안 한다. 오류 메시지도 없다. 어디부터 보나?
  5. 방금 몰았던 길을 로봇 없이 똑같이 다시 보고 싶다. 무엇을 남겨 두면 되나?

지난 회차까지 노드·토픽·서비스·파라미터가 무엇인지를 세웠다. 노드는 따로 도는 프로그램이고, 토픽은 노드 사이에 계속 흐르는 메시지의 이름이고, 서비스는 한 번 묻고 한 번 답을 받는 통로이고, 파라미터는 노드가 가진 설정값이다. 오늘은 그것들이 지금 내 컴퓨터에서 실제로 어떤 상태인지를 들여다보는 명령을 다룬다.

ROS 2의 명령은 수십 개이고 옵션까지 치면 수백 개다. 원래 자료는 652줄짜리 명령어 사전이었다. 그런데 이 명령들을 외워 두어도 막상 막혔을 때 무엇을 먼저 쳐야 할지는 떠오르지 않는 경우가 많다. 명령은 에이전트도 잘 만든다. 사람에게 남는 일은 지금 무엇이 궁금한지 정하는 것과 나온 출력을 읽는 것이다.

그래서 오늘 절은 전부 같은 네 칸으로 되어 있다 — 무엇이 궁금한가 → 그때 이걸 친다 → 출력을 이렇게 읽는다 → 에이전트에게 시키면. 세 번째 칸이 알맹이다. 에이전트에게 명령을 맡기더라도 돌아온 출력을 읽는 것은 여러분이고, 그 읽기가 되어야 "잘 연결되었습니다"라는 말이 맞는지 판단할 수 있다.

한 장 요약

무엇을 먼저 볼지: 왼쪽 「무엇이 궁금한가」 열이다. 이 열의 질문을 떠올릴 수 있으면 명령은 에이전트에게 물어도 된다.

무엇이 궁금한가그때 이걸 친다출력에서 볼 곳절
내 노드가 떠 있나ros2 node list노드 이름이 목록에 있나①
이 노드가 무엇을 받고 무엇을 내보내나ros2 node info /노드Subscribers · Publishers①
어떤 토픽이 있고 타입이 무엇인가ros2 topic list -t이름 한 글자, 대괄호 안 타입②
값이 실제로 흐르나, 값이 얼마인가ros2 topic echo /토픽숫자가 바뀌나③
초당 몇 번 오나ros2 topic hz /토픽average rate④
메시지 안에 무엇이 들었나ros2 interface show 타입필드 이름과 타입⑤
노드 없이 메시지를 보내 보고 싶다ros2 topic pub받는 쪽(거북이)이 움직이나⑥
누가 보내고 누가 받나, 둘이 붙을 수 있나ros2 topic info -v /토픽count · Reliability⑦
연결을 한눈에 보고 싶다rqt_graph화살표가 이어지나⑧
서비스를 불러 보고 싶다ros2 service list · type · callresponse⑨
설정값을 읽고 바꾸고 싶다ros2 param list · get · setSet parameter successful⑩
방금 그 장면을 다시 보고 싶다ros2 bag record · playMessages 개수⑪
설치·환경 자체가 이상하다ros2 doctorchecks passed⑫
해석: 열세 줄 중 위의 일곱 줄에서 진단이 끝나는 경우가 많다. "거북이가 안 움직인다"는 하나의 증상도 원인은 여러 가지인데 — 노드가 안 떴거나, 토픽 이름이 다르거나, 값이 안 흐르거나, 둘의 설정이 안 맞거나 — 위 일곱 줄이 그 원인을 하나씩 지워 가는 순서이기도 하다. 그 순서는 ⑬절에 따로 정리했다.

아래 출력은 전부 실제로 실행해서 받은 것이다. 돌린 곳: 컨테이너(우분투 24.04 + ROS 2 Jazzy, 사용자 이름 ubuntu). 여러분의 WSL에서는 시각(숫자로 찍히는 타임스탬프)·임시 노드 번호·네트워크 주소가 다르게 나온다. 그 밖의 모양은 같다.

ros2 명령의 구조와 실습 준비 🟢 맡겨도 된다

오늘 칠 명령이 왜 다 ros2로 시작할까? ROS 1에서는 rosnode·rostopic·rosservice처럼 할 일마다 실행 파일이 따로 있었다. ROS 2는 이것을 ros2 하나로 모으고, 그 뒤에 무엇을과 어떻게를 붙이게 했다. 

ros2  <무엇을>  <어떻게>  [대상]  [옵션]
ros2  node     list
ros2  node     info    /turtlesim
ros2  topic    echo    /turtle1/pose  --once
ros2  param    set     /turtlesim     background_r 255

🆕 이 모양에서 처음 나오는 것

ros2 <무엇을> <어떻게>
두 번째 자리를 명령(command), 세 번째 자리를 동사(verb)라고 부른다. 오늘 다루는 명령은 node topic interface service param bag doctor이고, 동사는 대부분 list(목록) · info(자세히) · echo/get(읽기) · pub/set/call(보내기·바꾸기) 중 하나다.
ros2 topic -h · ros2 topic pub -h
어느 자리에서든 -h(--help)를 붙이면 그 자리에 올 수 있는 것과 옵션이 나온다. 동사 이름이 기억나지 않을 때 가장 먼저 해 볼 만한 방법이다. 탭(Tab) 키를 두 번 눌러도 후보가 나온다.

예를 들어 topic 뒤에 무엇이 올 수 있는지 물으면 이렇게 나온다. 오늘 쓰는 topic의 동사(list·echo·hz·info·pub)가 이 목록 안에 다 있다.

실습 대상은 오늘 내내 turtlesim이다. 명령이 먹으면 화면 속 거북이가 움직이므로 맞았는지 틀렸는지를 글자가 아니라 눈으로 확인할 수 있다. 터미널을 세 개 열고, 앞의 두 개에서 노드 두 개를 띄운다. 이 두 노드는 회차 끝까지 켜 둔다.

터미널 2는 그 창에 커서가 있을 때만 방향키를 받는다. 거북이를 몰 때는 터미널 2를 누르고, 명령을 칠 때는 터미널 3으로 돌아온다. 세 터미널 모두 ros2가 먹어야 한다 — .bashrc에 넣어 둔 source /opt/ros/jazzy/setup.bash가 새 터미널마다 자동으로 걸리기 때문이다. ros2: command not found가 나오면 그 줄부터 확인한다.

turtlesim 실습을 하려고 해. 터미널 하나를 여러 칸으로 나눠 쓰는 프로그램(terminator 같은 것)을 설치해 줘. sudo가 붙는 명령은 실행하기 전에 나에게 먼저 보여 주고, 설치가 끝나면 칸을 가로·세로로 나누는 단축키를 알려 줘.

① ros2 node list · info 🔴 출력은 내가 읽는다

무엇이 궁금한가

"노드를 띄웠다"는 말은 사실 두 가지를 뜻할 수 있다. 프로그램이 실행됐다는 것과, 그 프로그램이 ROS 노드로서 다른 노드에게 보인다는 것이다. 앞의 것은 터미널에 글자가 찍히는 것으로 알 수 있지만 뒤의 것은 따로 물어봐야 한다. 지금 이 컴퓨터에서 보이는 노드는 무엇 무엇인가?

그때 이걸 친다

$ ros2 node list
/teleop_turtle
/turtlesim

출력을 이렇게 읽는다

두 줄이 나왔다. 터미널 1·2에서 띄운 두 노드다. 그런데 이름을 잘 보면 친 것과 다르다.

ros2 run에 친 이름 (실행 파일)node list에 나온 이름 (노드 이름)
turtlesim_node/turtlesim
turtle_teleop_key/teleop_turtle
해석: 실행 파일 이름은 디스크에 있는 프로그램 파일의 이름이고, 노드 이름은 그 프로그램이 실행된 뒤 ROS 안에서 쓰는 이름이다. 노드 이름은 프로그램 코드 안에서 정한다. 이 구별이 뒤에서 계속 쓰인다 — ros2 run에는 실행 파일 이름을, ros2 node info·ros2 param에는 노드 이름을 넣는다. 바꿔 넣으면 이렇게 된다. 
$ ros2 node info /turtlesim_node
Unable to find node '/turtlesim_node'

무엇을 먼저 볼지: 각 줄은 이름: 타입 두 토막이다. 왼쪽이 토픽·서비스 이름, 오른쪽이 그 안에 오가는 메시지의 타입이다.

굵은 줄뜻이 회차에서 다시 쓰는 곳
Subscribers 아래 /turtle1/cmd_vel거북이는 속도 명령을 받는다⑥절 — 여기로 명령을 보낸다
Publishers 아래 /turtle1/pose거북이는 자기 위치를 내보낸다③·④절 — 이 값을 읽고 주기를 잰다
Service Servers 아래 /spawn거북이를 하나 더 만들어 달라는 요청을 받는다⑨절
해석: 이 출력 한 장이 노드의 겉모습 전부다. 코드를 열어 보지 않아도 이 노드가 무엇을 받고 무엇을 내보내는지 알 수 있다. 남이 만든 노드를 처음 쓸 때 가장 먼저 볼 만한 출력이다. /turtlesim/…_parameters로 끝나는 서비스 여섯 개는 turtlesim이 직접 만든 것이 아니라 모든 노드에 자동으로 붙는 것이다(⑩절의 ros2 param이 이 통로를 쓴다). 처음에는 건너뛰고 읽어도 된다.

에이전트에게 시키면

지금 떠 있는 ROS 2 노드 목록을 보여 주고, 노드마다 발행하는 토픽과 구독하는 토픽을 표로 정리해 줘. 표 아래에 네가 실행한 명령과 출력 원문을 그대로 붙여 줘.

프롬프트 끝의 한 문장이 중요하다. 표만 받으면 그 표가 실제 출력에서 나온 것인지 알 수 없다. 출력 원문이 같이 오면 여러분이 위에서 읽은 방식대로 대조할 수 있다.

② ros2 topic list -t 🔴 이름은 내가 대조한다

무엇이 궁금한가

노드를 하나씩 info로 열어 보는 것은 노드가 많아지면 번거롭다. 거꾸로 물을 수도 있다 — 지금 이 컴퓨터에 어떤 토픽들이 있고, 각각 어떤 타입인가? 내 코드에 적은 토픽 이름이 이 목록에 글자 하나 틀리지 않고 있는지 보는 것이 이 명령의 주된 쓰임이다.

그때 이걸 친다

$ ros2 topic list
/parameter_events
/rosout
/turtle1/cmd_vel
/turtle1/color_sensor
/turtle1/pose

$ ros2 topic list -t
/parameter_events [rcl_interfaces/msg/ParameterEvent]
/rosout [rcl_interfaces/msg/Log]
/turtle1/cmd_vel [geometry_msgs/msg/Twist]
/turtle1/color_sensor [turtlesim/msg/Color]
/turtle1/pose [turtlesim/msg/Pose]

🆕 이 출력에서 처음 나오는 것

-t
타입(type)을 대괄호 안에 같이 찍어 달라는 옵션이다. 여기서는 /turtle1/cmd_vel에 오가는 메시지가 geometry_msgs/msg/Twist라는 것을 한 번에 알아냈다.
geometry_msgs/msg/Twist
타입 이름은 패키지/종류/이름 세 토막이다. 가운데가 msg면 토픽용 메시지, srv면 서비스용(⑨절)이다. 첫 토막이 그 정의가 들어 있는 패키지라서 나중에 C++ 코드에서 이 타입을 쓸 때 어느 패키지를 의존성에 넣어야 하는지도 여기서 읽힌다.

출력을 이렇게 읽는다

토픽누가 만든 것인가어떻게 대하나
/turtle1/cmd_vel · /turtle1/pose · /turtle1/color_sensorturtlesim 노드오늘 쓰는 토픽. 이름 앞의 /turtle1/은 거북이 이름이다
/parameter_events · /rosout모든 노드에 자동으로 붙는다파라미터 변경 알림과 로그 모음. 노드가 하나라도 뜨면 늘 보인다
해석: 토픽 이름은 노드끼리 서로를 찾는 유일한 단서다. 보내는 쪽이 /turtle1/cmd_vel로 보내고 받는 쪽이 /turtle1/cmd_vel을 기다려야 이어진다. 한 글자만 달라도 ROS는 그것을 다른 토픽으로 여긴다. 오류는 나지 않는다 — ⑥절 끝의 함정 상자에서 실제로 보게 된다.

에이전트에게 시키면

ros2 topic list -t 결과를 보여 주고, 내 코드에 적힌 토픽 이름(아래에 붙임)이 그 목록에 글자 그대로 있는지 하나씩 대조해 줘. 없는 것은 목록에서 가장 비슷한 이름을 같이 알려 줘.

③ ros2 topic echo 🔴 값은 내가 본다

무엇이 궁금한가

토픽이 목록에 있다는 것은 누군가 그 이름을 쓰겠다고 했다는 뜻일 뿐이다. 실제로 값이 흐르는지는 다른 질문이다. 지금 이 토픽에 무엇이 오가고 있나? 그 값은 얼마인가?

그때 이걸 친다

거북이의 현재 위치를 한 번만 받아 본다.

$ ros2 topic echo --once /turtle1/pose
x: 5.544444561004639
y: 5.544444561004639
theta: 0.0
linear_velocity: 0.0
angular_velocity: 0.0
---

🆕 이 출력에서 처음 나오는 것

--once
메시지를 하나만 받고 끝낸다. 붙이지 않으면 Ctrl+C를 누를 때까지 계속 찍는다. 여기서는 위치가 지금 얼마인지만 알고 싶어서 붙였다.
---
메시지 하나가 끝났다는 표시다. 계속 받을 때는 이 줄을 경계로 메시지가 하나씩 이어진다.

출력을 이렇게 읽는다

x와 y는 창 안에서의 위치, theta는 거북이가 바라보는 방향이다. theta의 단위는 도가 아니라 라디안이다(0이면 오른쪽, 약 1.57이면 위쪽). 처음 위치가 5.544…인 것은 turtlesim 창의 한 변이 약 11.09이고 그 한가운데에 첫 거북이를 놓기 때문이다.

이번에는 멈추지 않고 계속 받아 둔 채로, 터미널 2에서 위쪽 화살표를 한 번, 왼쪽 화살표를 한 번 눌러 본다. 거북이에게 가는 명령 토픽 /turtle1/cmd_vel을 본다. 

$ ros2 topic echo /turtle1/cmd_vel
linear:
  x: 2.0
  y: 0.0
  z: 0.0
angular:
  x: 0.0
  y: 0.0
  z: 0.0
---
linear:
  x: 0.0
  y: 0.0
  z: 0.0
angular:
  x: 0.0
  y: 0.0
  z: 2.0
---
누른 키찍힌 메시지뜻
위쪽 화살표linear.x: 2.0앞으로 초당 2.0만큼 가라
왼쪽 화살표angular.z: 2.0제자리에서 초당 2.0 라디안 왼쪽으로 돌아라
해석: 두 가지가 보인다. 첫째, 키를 누를 때만 메시지가 하나씩 나간다. 누르지 않으면 echo 화면은 조용하다 — 그것이 고장이 아니라는 것을 알고 있어야 ④절의 결과가 읽힌다. 둘째, 메시지 하나에 숫자가 여섯 개 있지만 거북이에게 의미 있는 것은 linear.x와 angular.z 둘뿐이다. 바닥을 굴러다니는 로봇은 옆으로(y) 가거나 위로(z) 뜰 수 없기 때문이다. 터틀봇도 같다.

두 번 누른 뒤의 위치를 다시 받아 본다.

$ ros2 topic echo --once /turtle1/pose

linear_velocity: 0.0
angular_velocity: 0.0

x가 5.54에서 6.15로 늘었고 theta가 0에서 2.02가 되었다. 값이 바뀐다는 것 — 이것이 「흐르고 있다」의 증거다. 회전이 2.0 라디안쯤인 것은 turtlesim이 속도 명령 하나를 약 1초 동안 적용하기 때문이다(초당 2.0 × 1초).

⚠️ 없는 토픽을 echo 하면

이름을 한 글자 틀리게 치면 이렇게 나오고, 그 상태로 계속 기다린다.

$ ros2 topic echo /turtle1/cmd_val
WARNING: topic [/turtle1/cmd_val] does not appear to be published yet
Could not determine the type for the passed topic

첫 줄은 「아직 아무도 이 이름으로 보내지 않았다」, 둘째 줄은 「그래서 타입도 알 수 없다」는 뜻이다. 오류로 끝나지 않고 기다리는 것은, 보내는 쪽이 나중에 뜰 수도 있기 때문이다. 이 두 줄이 보이면 고장을 의심하기 전에 ②절의 목록과 이름을 대조해 볼 만하다.

에이전트에게 시키면

/turtle1/pose 토픽을 --once로 한 번 받아서 보여 줘. 그다음 내가 거북이를 움직일 테니, 5초 뒤에 한 번 더 받아서 두 결과의 x, y, theta를 나란히 비교해 줘. 두 출력 원문도 같이 붙여 줘.

④ ros2 topic hz 🔴 숫자는 내가 판단한다

무엇이 궁금한가

값이 흐르는 것을 봤다. 그런데 얼마나 자주 오는가? 로봇에서는 이것이 자주 문제가 된다. 라이다가 초당 다섯 번 재는데 내 노드가 초당 두 번밖에 처리하지 못하면, 로봇은 0.5초 전의 세상을 보고 움직이게 된다. 그 사이에 콘 앞까지 가 버릴 수도 있다. 이 토픽은 초당 몇 번 오고, 그 간격은 고른가?

$ ros2 topic hz /turtle1/cmd_vel

아무것도 나오지 않는다. 오류도 없다. ③절에서 본 것처럼 teleop은 키를 누를 때만 보내므로 지금은 셀 메시지가 없다. 일정하게 보내는 쪽이 있을 때 이 토픽이 어떻게 재지는지는 ⑥절에서 직접 메시지를 보내 본 뒤에 다시 잰다.

해석: hz가 알려 주는 것은 셋이다 — 오나 안 오나(아무것도 안 찍히면 지금 아무도 안 보낸다), 얼마나 자주 오나(average rate), 고르게 오나(max가 min보다 훨씬 크면 가끔 크게 늦는 순간이 있다). 셋째가 로봇에서 특히 중요하다. 평균은 멀쩡한데 가끔 한 번씩 0.5초가 비면, 로봇은 그 순간 반응을 놓친다.

27회에서는 이 명령이 이렇게 쓰인다 — 터틀봇의 라이다 토픽 /scan을 재면 average rate가 라이다 사양(초당 몇 번 재는가)에 가깝게 나와야 하고, 내 노드가 발행하는 속도 명령도 같은 방법으로 잰다. 지금은 turtlesim의 62.5와 10.0으로 읽는 법만 익혀 두면 된다.

마지막 문장을 넣은 이유가 있다. hz가 아무것도 안 찍을 때 에이전트가 시간이 다 돼서 끝났다고만 보고하는 경우가 있다. 「아무것도 안 왔다」는 그 자체로 중요한 결과다.

⑤ ros2 interface show 🟢 맡겨도 된다

무엇이 궁금한가

③절에서 /turtle1/cmd_vel의 메시지에는 linear와 angular가 있었고, 각각 안에 x·y·z가 있었다. 그것은 마침 그 메시지에 그런 값이 들어 있었던 것일까, 아니면 정해진 모양일까? 다음 절에서 이 토픽에 직접 메시지를 써서 보내려면 정확한 필드 이름을 알아야 한다. 이 타입의 메시지에는 어떤 필드가 어떤 타입으로 들어 있나?

그때 이걸 친다

②절의 -t가 알려 준 타입 이름을 그대로 넣는다.

$ ros2 interface show geometry_msgs/msg/Twist
# This expresses velocity in free space broken into its linear and angular parts.

Vector3  linear
	float64 x
	float64 y
	float64 z
Vector3  angular
	float64 x
	float64 y
	float64 z

$ ros2 interface show turtlesim/msg/Pose
float32 x
float32 y
float32 theta

float32 linear_velocity
float32 angular_velocity

출력을 이렇게 읽는다

한 줄이 필드 하나이고 타입 이름 순서다. #으로 시작하는 줄은 설명(주석)이다. Twist는 Vector3 타입 필드 두 개(linear·angular)로 되어 있고, 들여 쓴 줄은 그 Vector3 안에 다시 무엇이 들었는지를 펼쳐 보인 것이다. 그래서 ③절의 출력에서 linear: 아래에 x·y·z가 들여 쓰여 있었다.

필드 타입뜻C++에서 (19회 이후)
float6464비트 실수double
float3232비트 실수float
Vector3다른 메시지 타입 (x·y·z 묶음)멤버로 들어 있는 구조체
해석: 메시지 타입은 보내는 쪽과 받는 쪽이 미리 약속한 모양이다. 이 약속이 텍스트 파일로 정의돼 있고, interface show는 그 파일을 보여 준다. 코드를 쓸 때 필드 이름이 기억나지 않으면 추측하지 말고 이것을 쳐서 보는 편이 빠르다 — pose.theta인지 pose.angle인지는 이 출력에 답이 있다.

에이전트에게 시키면

ros2 interface show로 geometry_msgs/msg/Twist와 turtlesim/msg/Pose의 정의를 보여 주고, 필드마다 무슨 뜻인지 한 줄씩 한국어로 설명해 줘. turtlesim 거북이가 실제로 쓰는 필드가 어느 것인지도 표시해 줘.

⑥ ros2 topic pub 🟡 맡기되 결과는 내가 본다

무엇이 궁금한가

지금까지는 읽기만 했다. 거꾸로, 노드를 하나도 만들지 않고 터미널에서 직접 메시지를 보낼 수는 없을까? 이것이 되면 쓸모가 크다. 20회에서 거북이를 모는 노드를 짜게 되는데, 그 노드가 안 움직일 때 받는 쪽(거북이)이 문제인지 보내는 쪽(내 코드)이 문제인지를 가를 수 있다. 터미널에서 보낸 메시지로 거북이가 움직이면 받는 쪽은 멀쩡한 것이다.

그때 이걸 친다

모양은 ros2 topic pub [옵션] 토픽 타입 '값'이다. ⑤절에서 본 필드 이름을 그대로 쓴다.

$ ros2 topic pub --once /turtle1/cmd_vel geometry_msgs/msg/Twist '{linear: {x: 2.0}, angular: {z: 1.8}}'
publisher: beginning loop
publishing #1: geometry_msgs.msg.Twist(linear=geometry_msgs.msg.Vector3(x=2.0, y=0.0, z=0.0), angular=geometry_msgs.msg.Vector3(x=0.0, y=0.0, z=1.8))

🆕 이 명령에서 처음 나오는 것

'{linear: {x: 2.0}, angular: {z: 1.8}}'
보낼 값을 YAML이라는 형식으로 적은 것이다. 이름: 값을 중괄호로 묶고, 안에 또 메시지가 있으면 중괄호를 한 겹 더 쓴다. ⑤절의 들여쓰기와 모양이 같다. 적지 않은 필드는 0으로 채워진다 — 출력의 y=0.0, z=0.0이 그것이다. 바깥의 작은따옴표는 쉘이 중괄호와 띄어쓰기를 건드리지 못하게 막는 것이다.
--once · --rate N
--once는 한 번만 보내고 끝낸다. --rate N은 초당 N번씩 Ctrl+C를 누를 때까지 보낸다. 둘 다 없으면 초당 1번이다.

출력을 이렇게 읽는다

publishing #1: 줄은 보냈다는 뜻이지 누가 받았다는 뜻이 아니다. 받았는지는 받는 쪽에서 확인한다. 이 경우에는 거북이가 움직였나를 보면 된다.

위치를 받아 보면 숫자로도 확인된다.

$ ros2 topic echo --once /turtle1/pose
x: 6.602816581726074
y: 6.938989639282227
theta: 1.8143999576568604
linear_velocity: 0.0
angular_velocity: 0.0
---

theta가 1.81 — 보낸 angular.z: 1.8을 약 1초 적용한 값이다. turtlesim은 속도 명령이 1초 넘게 안 오면 거북이를 세운다. 그래서 --once로는 잠깐만 움직인다. 계속 돌게 하려면 계속 보낸다. 

$ ros2 topic pub --rate 1 /turtle1/cmd_vel geometry_msgs/msg/Twist '{linear: {x: 2.0}, angular: {z: 1.8}}'
publisher: beginning loop
publishing #1: geometry_msgs.msg.Twist(linear=geometry_msgs.msg.Vector3(x=2.0, y=0.0, z=0.0), angular=geometry_msgs.msg.Vector3(x=0.0, y=0.0, z=1.8))

publishing #2: geometry_msgs.msg.Twist(linear=geometry_msgs.msg.Vector3(x=2.0, y=0.0, z=0.0), angular=geometry_msgs.msg.Vector3(x=0.0, y=0.0, z=1.8))

publishing #3: geometry_msgs.msg.Twist(linear=geometry_msgs.msg.Vector3(x=2.0, y=0.0, z=0.0), angular=geometry_msgs.msg.Vector3(x=0.0, y=0.0, z=1.8))
^C

초당 한 번씩 보내니 거북이가 원을 그리며 계속 돈다. Ctrl+C로 멈추면 1초 뒤 거북이도 선다. ④절에서 아무것도 안 찍히던 /turtle1/cmd_vel을, 이번에는 --rate 10으로 보내 둔 채 다른 터미널에서 다시 재 본다. 

$ ros2 topic pub --rate 10 /turtle1/cmd_vel geometry_msgs/msg/Twist '{linear: {x: 0.5}}'
(… publishing #1, #2, … 줄 생략 …)

# 다른 터미널에서
$ ros2 topic hz /turtle1/cmd_vel
average rate: 9.999
	min: 0.100s max: 0.100s std dev: 0.00010s window: 11
average rate: 10.001
	min: 0.100s max: 0.100s std dev: 0.00011s window: 22

보낸 대로 초당 10번, 0.1초 간격이 재졌다. 20회에서 타이머로 명령을 보내는 노드를 만들면 그 노드가 정말 정한 주기대로 보내는지 이 방법으로 확인한다.

값을 틀리게 적으면 보내기 전에 막힌다. 두 가지가 흔하다.

$ ros2 topic pub --once /turtle1/cmd_vel geometry_msgs/msg/twist '{linear: {x: 2.0}}'
The passed message type is invalid

$ ros2 topic pub --once /turtle1/cmd_vel geometry_msgs/msg/Twist '{linear: {x: 2.0}, angular: {zz: 1.8}}'
Failed to populate field: 'Vector3' object has no attribute 'zz'

첫째는 타입 이름의 대소문자(twist ↔ Twist)가 틀린 것이고, 둘째는 없는 필드 이름(zz)을 쓴 것이다. 이 둘은 오류 메시지가 나오므로 오히려 쉽다. 정말 곤란한 것은 아래처럼 아무 오류 없이 안 되는 경우다.

⚠️ 토픽 이름 오타 — 오류 없이 거북이만 안 움직인다

🆕 이 출력에서 처음 나오는 것

--- (서비스 정의 안)
서비스 타입은 요청(request)과 응답(response) 두 부분이고, ---가 그 경계다. /spawn은 위치 x·y·방향 theta·이름 name을 받고, 만들어진 거북이의 name을 돌려준다. name을 비우면 알아서 이름을 지어 준다는 설명이 주석에 있다.
std_srvs/srv/Empty
요청도 응답도 비어 있는 서비스 타입이다(interface show로 보면 --- 한 줄뿐이다). 「그냥 해라」는 뜻만 전하는 서비스에 쓴다. /clear(그림 지우기)·/reset(처음으로)이 이것이다.

이제 부른다. 모양은 ros2 service call 서비스 타입 '요청' — ⑥절의 topic pub과 같다.

turtlesim.srv.Spawn_Response(name='turtle2')

거북이 창의 파란 배경은 코드에 박혀 있는 색일까? 그렇다면 색을 바꾸려면 코드를 고치고 다시 빌드해야 한다. 파라미터로 빼 두었다면 노드를 켠 채로 바꿀 수 있다. 프로젝트에서 조향 이득이나 속도를 맞출 때 로봇을 세우지 않고 값을 바꿔 가며 보는 것이 바로 이것이다. 이 노드는 어떤 설정값을 갖고 있고, 지금 값은 얼마이고, 바꿀 수 있나?

값이 어디까지 허용되는지는 describe로 본다. 그다음 빨강을 가득 채워 본다.

Parameter name: background_r
  Type: integer
  Description: Red channel of the background color
  Constraints:
    Min value: 0
    Max value: 255
    Step: 1

Integer value is: 255

2토픽 이름·타입이 맞나ros2 topic list -t비슷한 이름이 둘 → 오타 (⑥절 함정)
3양쪽이 다 붙어 있나ros2 topic infocount: 0 → 그쪽 노드가 그 이름을 안 쓴다
4값이 실제로 오나ros2 topic echo안 온다 → 보내는 쪽이 안 보내고 있다
5둘이 붙을 수 있나ros2 topic info -vReliability가 다르다 → QoS 불일치 (⑦절 함정, 22회)
6제때 오나ros2 topic hz사양보다 느리거나 들쭉날쭉 → 어딘가 밀리고 있다 (22회)
해석: 순서에는 이유가 있다. 4번(echo)이 5번(info -v)보다 앞인 것은 값이 아예 안 흐르는 경우를 먼저 지우기 위해서다. 그런데 4번에서 값이 보인다고 끝난 것이 아니다 — ⑦절에서 봤듯이 echo는 보내는 쪽에 맞춰 받으므로, echo에는 보이는데 내 노드만 못 받는 경우가 5번에서 걸린다. rqt_graph(⑧)는 이 순서의 1~3번을 한 장으로 미리 훑어보는 데 쓰고, ros2 doctor(⑫)는 0번이 의심스러울 때 쓴다.

이 순서는 에이전트에게 물을 때도 그대로 쓸 수 있다. 「안 돼요, 고쳐 주세요」보다 「2번까지 확인했고 이름은 맞다. 3번에서 Subscription count가 0이다」라고 말하면 답이 훨씬 좁혀진다.

turtlesim 거북이가 /turtle1/cmd_vel 명령에 반응하지 않아. 아래 순서대로 한 단계씩 확인하고, 단계마다 실행한 명령과 출력 원문, 그리고 그 단계를 통과했는지 걸렸는지를 적어 줘. 걸린 단계가 나오면 거기서 멈추고 원인 후보를 알려 줘. (1) ros2 node list (2) ros2 topic list -t (3) ros2 topic info /turtle1/cmd_vel (4) ros2 topic echo --once /turtle1/cmd_vel (5) ros2 topic info -v /turtle1/cmd_vel 의 Reliability (6) ros2 topic hz /turtle1/cmd_vel

에이전트가 「모든 단계를 통과했습니다」라고 하면, 붙어 온 출력에서 3번의 두 count와 5번의 두 Reliability만 직접 확인한다. 그 네 단어를 보는 데 10초면 된다.

🧪 이걸 해 보면 무엇을 알게 되나

오류 메시지 없이 거북이만 안 움직이는 두 가지 고장을, ⑬절의 순서로 어느 단계에서 걸리는지 직접 찾아본다. 명령을 외우는 것이 아니라 어떤 출력의 어느 단어를 보고 원인을 짚었는지를 남기는 것이 목표다. 마지막에는 몰았던 길을 bag으로 다시 그려 본다.

준비물

  • WSL 터미널 셋 (터미널 1: turtlesim_node, 터미널 2: turtle_teleop_key, 터미널 3: 명령용)
  • 옆자리 한 사람 — 서로 고장을 내 주고 찾는다. 혼자라면 고장을 낸 터미널을 보지 않기로 하고 한다
  • 메모장 하나 — 단계마다 본 줄을 적는다

절차

  1. (3분) 터미널 1·2에서 turtlesim과 teleop을 띄우고, 방향키로 거북이가 움직이는지 본다. 터미널 3에서 ros2 node list를 쳐서 두 노드가 보이는지 확인한다.
  2. (5분) 고장 A. 짝이 터미널 4를 하나 더 열고, 아래 둘 중 하나를 골라 걸어 둔다(어느 것인지 말하지 않는다). 
    # (가)
ros2 topic pub --rate 1 /turtle1/cmd_val geometry_msgs/msg/Twist '{linear: {x: 2.0}, angular: {z: 1.8}}'
# (나)
ros2 topic pub --rate 1 --qos-reliability best_effort /turtle1/cmd_vel geometry_msgs/msg/Twist '{linear: {x: 2.0}, angular: {z: 1.8}}'
    「원을 그리게 하는 명령을 보냈는데 거북이가 안 돈다」는 상황이다. 터미널 4의 화면은 보지 않는다.
  3. (10분) 터미널 3에서 ⑬절의 표를 1번부터 내려가며 친다. 단계마다 「통과 / 걸림」과 그렇게 판단한 출력의 한 줄을 메모에 적는다. 걸린 단계가 나오면 원인을 한 문장으로 쓴 뒤 짝에게 확인한다. 역할을 바꿔 다른 하나도 한다.
  4. (5분) 둘 다 찾았으면 rqt_graph를 띄워 (가)를 다시 걸어 둔다. Dead sinks·Leaf topics 체크를 껐다 켰다 하면서 /turtle1/cmd_val 사각형이 언제 보이고 언제 사라지는지 확인한다.
  5. (5분) 터미널 4를 Ctrl+C로 끄고, ⑪절에서 한 대로 ~/bags에서 /turtle1/cmd_vel을 기록하며 방향키로 원하는 모양을 그린다. ros2 bag info의 Messages가 누른 키 수와 같은지 본다.
  6. (3분) ros2 service call /reset std_srvs/srv/Empty로 처음 자리로 돌린 뒤 ros2 bag play로 재생한다. 키를 누르지 않고 같은 모양이 그려지는지 본다.

이렇게 되면 성공이다

  • 메모에 두 고장이 각각 몇 번 단계에서 걸렸는지, 그리고 그 근거가 된 줄이 적혀 있다. 실제로 받은 출력으로는 (가)가 2번에서 /turtle1/cmd_val과 /turtle1/cmd_vel 두 이름이 나란히 보이는 것으로 드러났고, ros2 topic info /turtle1/cmd_val의 Subscription count: 0으로 확인됐다. (나)는 2·3·4번을 모두 통과하고(echo에 값까지 보인다) 5번에서 BEST_EFFORT와 RELIABLE이 갈렸다.
  • rqt_graph에서 체크를 끄면 /turtle1/cmd_val이 화살표 없이 따로 뜬다 (⑧절 두 번째 그림).
  • 재생한 길이 몰았던 길과 같은 모양이다 (⑪절 그림).

액션 — ros2 action list · send_goal

①절의 node info에 Action Servers: /turtle1/rotate_absolute가 있었다. 액션은 서비스처럼 한 번 시키는 일이지만 끝날 때까지 시간이 걸리고, 그동안 진행 상황(피드백)을 알려 주는 통로다. teleop의 문자 키(e·r·t·d·g·c·v·b)가 이것을 쓴다 — 누르면 거북이가 그 방향을 볼 때까지 천천히 돈다. 명령의 모양은 서비스와 비슷하다. 

$ ros2 action list
/turtle1/rotate_absolute

$ ros2 action send_goal /turtle1/rotate_absolute turtlesim/action/RotateAbsolute '{theta: 1.5708}'
Waiting for an action server to become available...
Sending goal:
     theta: 1.5708

Goal accepted with ID: e70711962b334f32bdfbfa7a3bf167a2

Result:
    delta: -1.5520000457763672

Goal finished with status: SUCCEEDED

theta: 1.5708은 라디안으로 위쪽(90°)이다. 서비스와 달리 목표를 받아들였다(Goal accepted) → 결과(Result) → 끝난 상태(SUCCEEDED)가 차례로 온다. 액션 타입을 interface show로 보면 ---가 두 번 있어 목표·결과·피드백 세 부분으로 나뉜다.

이 과목의 프로젝트에서는 액션을 쓰지 않는다. 그런 통로가 있다는 것만 알아 두면 된다.

숨은 노드 — ros2 node list -a

⑦절에서 _ros2cli_307이라는 노드가 info -v에만 나오고 node list에는 없었다. -a(all)를 붙이면 숨은 노드까지 나온다. 오타 난 토픽으로 보내는 topic pub을 걸어 둔 채 친 실제 출력이다. 

$ ros2 node list
/teleop_turtle
/turtlesim

$ ros2 node list -a
/_ros2cli_60
/_ros2cli_daemon_58_6fec72ab9a284d25865c21b25909e29c
/teleop_turtle
/turtlesim

_ros2cli_60이 topic pub이 만든 노드이고, _ros2cli_daemon_…은 ros2 명령이 노드 목록을 빨리 보여 주려고 뒤에서 띄워 두는 도우미다. 둘 다 여러분이 만든 노드가 아니므로 평소에는 숨겨 두는 편이 읽기 쉽다.

메시지의 빈 틀 — ros2 interface proto

topic pub에 넣을 값을 처음부터 쓰기 귀찮으면, 모든 필드가 0으로 채워진 틀을 받아서 고쳐 쓸 수 있다.

$ ros2 interface proto geometry_msgs/msg/Twist
"linear:
  x: 0.0
  y: 0.0
  z: 0.0
angular:
  x: 0.0
  y: 0.0
  z: 0.0
"
같은 타입을 쓰는 서비스 찾기 — ros2 service find · 토픽의 대역폭 — ros2 topic bw

ros2 service find std_srvs/srv/Empty는 그 타입을 쓰는 서비스(/clear·/reset)를 찾아 준다. ros2 topic bw /토픽은 hz가 「초당 몇 개」를 재는 것처럼 「초당 몇 바이트」를 잰다. 카메라처럼 메시지 하나가 큰 토픽에서 통신이 버거운지 볼 때 쓴다.

27회에서는 이 명령들이 이렇게 보인다

터틀봇에서는 오늘의 /turtle1/cmd_vel 자리에 /cmd_vel이, /turtle1/pose 자리에 라이다 토픽 /scan이 온다. /scan의 타입은 sensor_msgs/msg/LaserScan이고, echo로 보면 거리 값 수백 개가 든 배열이 쏟아진다. 그리고 라이다는 대개 BEST_EFFORT로 보낸다 — ⑦절의 함정이 거기서 실제로 일어난다. 명령과 읽는 법은 오늘과 같다. 지금은 그런 토픽이 있다는 것만 알아 두면 된다.
