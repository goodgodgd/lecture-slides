왜 아직도 C++인가

오늘 답할 질문
  1. 파이썬이 훨씬 쉬운데 로봇은 왜 아직도 C++을 쓰나?
  2. 로봇을 안 하게 되면 C++은 필요 없어지나? — 게임·금융·자동차·AI 프레임워크는 무엇으로 짜여 있나
  3. Go와 Rust 같은 새 언어가 나왔는데 C++은 왜 아직 남아 있나?
  4. AI가 코드를 짜 주는데 C++을 왜 알아야 하나?
  5. C++은 왜 이렇게 복잡한가?
  6. 앞으로 아홉 번의 C++ 수업은 무엇을 하나?

오늘부터 아홉 번은 C++을 본다. 그런데 첫 시간에 문법을 하나도 다루지 않는다. "왜 이걸 배우느냐"에 대답하지 못하면 나머지 여덟 번이 그냥 문법 암기가 되기 때문이다.

이 질문에 "C++이 빠르니까"라고 답하는 것은 답이 아니다. 얼마나 빠른지를 모르면 판단할 수가 없다. 그래서 오늘은 같은 계산을 C++과 파이썬으로 각각 짜서 실제로 재는 것부터 시작한다. 자료에 나오는 숫자는 전부 그렇게 얻은 것이다.

그런데 「로봇이 C++을 쓴다」만으로는 답이 반쪽이다. 이 과를 나온 사람이 전부 로봇을 만들지는 않는다. 반도체·자동차·통신 장비·방산·게임·금융 IT — 어디로 가든 거기에 C++이 있는지, 있다면 왜 있는지를 같이 본다. 그리고 C++을 대신하겠다고 나온 언어들 — Go와 Rust — 가 C++의 무엇을 고치려 했는지도 본다. 그것을 알아야 「그래도 C++인가」를 스스로 판단할 수 있다.

마지막 질문이 가장 중요하다. AI가 코드를 짜 주는 시대에 C++을 아는 것이 무슨 소용인가. 실제 회사의 C++ 코드 1천만 줄을 1년간 추적한 연구가 있다. 거기서 나온 결론 한 줄이 이 강의 2부 전체의 뼈대다 — AI는 틀린 코드를 더 많이 만들지 않았다. 문제는 맞지만 둔한 코드였다.

한 장 요약 — 오늘 남는 것은 숫자 다섯 개다

무엇을 먼저 볼지: 맨 왼쪽 숫자 다섯 개만 외우면 오늘 수업은 남는다. 나머지는 그 숫자를 설명하는 이야기다.

숫자무엇을 잰 것인가그래서 무엇이 달라지나
168배 같은 계산(라이다 값 360개를 걸러 평균, 10만 번)을 C++과 파이썬으로 각각 돌린 시간의 비 시간 제약이 걸리는 콜백을 C++로 쓰는 이유다
200 ms 라이다가 초당 5번 들어올 때 한 스캔에 쓸 수 있는 시간 내가 짠 코드는 이 안에 끝나야 한다. 넘으면 밀린다. 게임은 16.7 ms, 초단타 매매는 수 µs — 예산이 있는 분야마다 C++이 있다
1.39 / 2 / 0.4배 AI가 짠 C++ 코드가 사람이 짠 것과 갈라진 세 자리 — 복사·직접 루프·표준 라이브러리 11회(복사와 이동)와 13회(STL)가 2부의 중심인 이유다
0.94배 AI 코드의 정확성·안전성 문제 발생률 ÷ 사람 코드의 발생률 AI는 틀린 코드를 더 많이 만들지 않는다. 그러니 "버그 잡기"는 오늘의 논지가 아니다
약 70% 마이크로소프트(2019)와 구글 크롬 팀(2020)이 각자 센, 심각한 보안 결함 중 메모리를 잘못 다뤄서 생긴 것의 비율 Rust가 나온 이유다. 그리고 C++ 안에서 같은 문제를 다루는 10회·12회가 있는 이유이기도 하다
해석: 첫 줄과 넷째 줄을 같이 읽어야 오늘의 논지가 나온다. C++이 필요한 이유는 속도고, C++을 사람이 알아야 하는 이유는 AI가 속도를 놓친다는 것이다. 두 이유는 다른 것이다. 앞의 것만 있으면 "AI에게 시키면 되지 않나"로 끝난다. 마지막 줄은 C++의 비용이다. 그 비용을 없애려고 나온 언어가 Rust이고, 그것을 알면 C++이 어디에 남고 어디에서 물러나는지가 보인다.

① 같은 일을 시켰더니 파이썬이 168배 오래 걸렸다 🔴 사람이 한다

무엇을 알고 싶은 건가

로봇 위에 올릴 프로그램의 언어를 고르려고 한다. 판단 기준이 필요한데, "C++이 빠르다"는 말은 기준이 아니다. 얼마나 빠른지, 그리고 그 차이가 로봇에서 문제가 되는 크기인지를 알아야 고를 수 있다.

느낌과 평판으로는 왜 안 되나

인터넷에서 "파이썬이 C++보다 몇 배 느리다"는 숫자는 10배부터 1000배까지 제각각이다. 무엇을 어떻게 쟀는지가 다 다르기 때문이다. 행렬 곱셈처럼 무거운 계산 한 방을 재면 파이썬도 별로 안 느리다. 안쪽이 이미 C로 짜여 있는 라이브러리(numpy 같은 것)가 대신 계산하기 때문이다. 반대로 값 하나하나를 파이썬 문법으로 훑는 계산을 재면 차이가 크게 벌어진다.

우리가 로봇에서 하는 일은 두 번째 쪽이다. 라이다가 준 거리 값 360개를 하나씩 보면서 쓸 만한지 판단하고, 골라내고, 평균을 낸다. 그래서 그 계산을 그대로 두 언어로 짜서 쟀다.

재는 데 쓴 C++ 코드

라이다 한 스캔(값 360개)을 흉내내고, 못 쓰는 값을 걸러 평균을 내는 일을 10만 번 반복한다.

// 6회 — 왜 아직도 C++인가
// 라이다 한 스캔(360개)을 받아 유효값만 걸러 평균을 내는 일을
// 10만 번(= 라이다 5Hz로 약 5.5시간 분량) 반복하고 걸린 시간을 잰다.
#include <chrono>
#include <cmath>
#include <cstdio>
#include <vector>

int main()
{
  const int N = 360;
  const int LOOPS = 100000;

  // 라이다 한 스캔을 흉내낸다. 10개마다 하나씩 측정 실패(inf)를 섞는다.
  std::vector<float> ranges(N);
  for (int i = 0; i < N; ++i) {
    ranges[i] = (i % 10 == 0) ? INFINITY : 0.2f + 0.02f * static_cast<float>(i % 300);
  }

🆕 이 코드에서 처음 나오는 것

std::vector<float> ranges(N)
실수 값을 N개 담는 그릇을 하나 만든다. 여기서는 라이다가 한 바퀴 돌며 잰 거리 360개를 담는 데 썼다. 꺾쇠 안의 float이 "무엇을 담는 그릇인지"를 말한다.
INFINITY
"무한대"라는 뜻의 실수 값이다. 여기서는 라이다가 측정에 실패한 방향을 흉내내는 데 썼다. 실제 라이다도 값이 안 잡히면 이 값을 채워 보낸다.
static_cast<float>(x)
정수를 실수로 바꿔 달라고 명시적으로 적는 것이다. 그냥 두어도 되지만, 이렇게 적어 두면 "일부러 바꾼 것"임이 코드에 드러난다.
#include <chrono> 같은 맨 위 네 줄
남이 만들어 둔 것을 쓰려면 그 이름들을 먼저 가져다 붙여야 한다. 여기서는 시계(chrono)·수학 함수(cmath)·화면 출력(cstdio)·그릇(vector) 넷을 가져왔다. 이 네 줄이 없으면 아래 코드는 한 줄도 컴파일되지 않는다.

제대로 다루는 곳: 7회(#include와 꺾쇠 <> 읽는 법) · 12회(std::vector)

다음이 실제로 시간을 재는 부분이다.

  const auto t0 = std::chrono::steady_clock::now();

  double sink = 0.0;                       // 최적화로 계산이 통째로 날아가는 것을 막는다
  for (int k = 0; k < LOOPS; ++k) {
    double sum = 0.0;
    int cnt = 0;
    for (int i = 0; i < N; ++i) {
      const float r = ranges[i];
      if (std::isfinite(r) && r >= 0.16f && r <= 8.0f) {
        sum += r;
        ++cnt;
      }
    }
    sink += (cnt > 0) ? sum / cnt : 0.0;
  }

  const auto t1 = std::chrono::steady_clock::now();
  const double ms = std::chrono::duration<double, std::milli>(t1 - t0).count();

  std::printf("C++   : %d회 반복에 %.1f ms  (한 스캔당 %.4f ms)\n", LOOPS, ms, ms / LOOPS);
  std::printf("        평균 거리 %.4f m\n", sink / LOOPS);
  return 0;
}

🆕 이 코드에서 처음 나오는 것

std::chrono::steady_clock::now()
지금 시각을 읽어 오는 시계다. 뒤로 가지 않는 시계라서 시간 차를 재는 데 쓴다. 여기서는 계산 앞뒤로 한 번씩 읽어 그 차이를 걸린 시간으로 삼았다.
std::chrono::duration<double, std::milli>(t1 - t0).count()
두 시각의 차이를 밀리초 숫자로 꺼낸다. t1 - t0만으로는 단위가 안 정해져 있어서 이렇게 단위를 지정해 꺼낸다.
std::isfinite(r)
그 값이 정상적인 숫자인지 묻는다. 무한대나 "숫자가 아님"이면 거짓이 된다. 여기서는 라이다가 측정에 실패한 방향을 버리는 데 썼다.
std::printf("... %.1f ...", ms)
화면에 찍는 함수다. %.1f는 "실수를 소수점 한 자리까지"라는 뜻의 자리 표시다.
const auto t0 = ...
두 조각이다. auto는 "타입을 여기 안 적을 테니 컴파일러가 채우라"는 뜻이고, const는 "이 값은 다시 안 바꾼다"는 표시다. 시계가 돌려주는 값의 타입 이름이 길어서 여기서는 auto로 넘겼다.

제대로 다루는 곳: 7회(auto·const) · 13회(라이다 값에 섞인 inf·NaN 거르기)

재는 데 쓴 파이썬 코드 — 한 줄 한 줄이 같은 일을 한다

# 6회 — 같은 계산의 파이썬 판. scan_filter.cpp 와 한 글자도 다르지 않은 일을 한다.
import math
import time

N = 360
LOOPS = 100000

ranges = [math.inf if i % 10 == 0 else 0.2 + 0.02 * (i % 300) for i in range(N)]

t0 = time.perf_counter()

sink = 0.0
for _ in range(LOOPS):
    s = 0.0
    cnt = 0
    for r in ranges:
        if math.isfinite(r) and 0.16 <= r <= 8.0:
            s += r
            cnt += 1
    sink += (s / cnt) if cnt else 0.0

t1 = time.perf_counter()
ms = (t1 - t0) * 1000.0

print("Python: %d회 반복에 %.1f ms  (한 스캔당 %.4f ms)" % (LOOPS, ms, ms / LOOPS))
print("        평균 거리 %.4f m" % (sink / LOOPS))

🆕 이 명령에서 처음 나오는 것

g++
C++ 소스를 실행 파일로 바꿔 주는 프로그램이다(컴파일러). 파이썬은 이 단계가 없고 바로 실행되지만, C++은 반드시 한 번 거친다.
-std=c++17
"C++ 문법은 2017년판 기준으로 읽어 달라"는 요구다. ROS 2가 C++17을 쓰므로 이 과목은 전부 이 값으로 맞춘다.
-O2
"속도가 나게 최적화해 달라"는 요구다. 알파벳 대문자 오(O)와 숫자 2다. 이것을 빼면 같은 코드가 훨씬 느려진다 — 실습에서 직접 확인한다.
-o scan_filter
만들어진 실행 파일의 이름을 정한다. 안 적으면 a.out이라는 이름이 된다.

무엇을 알고 싶은 건가

168배라는 숫자만으로는 아직 판단이 안 선다. 168배가 문제가 되는 크기인가를 알아야 한다. 그러려면 비교 대상이 필요하다.

비교 대상은 라이다가 정해 준다

이 과목에서 쓰는 라이다(LDS-02)는 초당 5번 값을 보낸다. 그러면 스캔과 스캔 사이의 간격은 1초 ÷ 5 = 0.2초 = 200 밀리초다. 내가 짠 코드가 한 스캔을 처리하는 데 쓸 수 있는 시간이 200 밀리초다. 이것을 넘기면 다음 스캔이 이미 와 있고, 그다음 스캔은 줄을 선다.

해석: 뒤의 세 줄에 붙은 「100배」·「10배」·「다섯 가지」는 내가 둔 가정이다. 잰 값이 아니다. 그런데 어떤 가정을 넣어도 168배라는 비율은 그대로 곱해진다. 첫 줄만 보면 파이썬도 예산의 0.02%밖에 안 쓴다. 넉넉하다. 문제는 계산 하나가 아니라 계산이 겹칠 때다. C++은 마지막 줄에서도 0.5%지만 파이썬은 99%다.

예산을 넘기면 무슨 일이 일어나나

처리가 200 밀리초를 넘기면 프로그램이 죽지 않는다. 그게 더 나쁘다. 들어온 메시지가 줄을 서고, 로봇은 몇 초 전에 본 장면을 보며 지금 결정을 내린다. 눈앞에 콘이 있는데 로봇이 그냥 지나가는 상황이 그렇게 생긴다. 이 이야기는 22회에서 실제로 콜백에 걸리는 시간을 재면서 다시 만난다. 지금은 "밀린다는 것은 느려지는 게 아니라 과거를 보게 되는 것"이라는 것만 알아 두면 된다.

그래서 코드를 받았을 때 물어볼 것은 "잘 도나"가 아니라 "얼마나 걸리나"다.

이 계산이 한 번에 얼마나 걸리는지 std::chrono로 재는 코드를 붙여 줘. 결과를 밀리초로 찍고, 재는 구간이 어디부터 어디까지인지 주석으로 표시해 줘.

③ 이 예산은 로봇에만 있는 것이 아니다 — C++이 쓰이는 자리 🔴 사람이 한다

무엇을 알고 싶은 건가

여기까지는 「로봇에는 200 밀리초 예산이 있고, 그래서 C++이다」였다. 그러면 로봇을 안 하게 되면 C++은 필요 없어지나? 이 과를 나온 사람이 가는 자리는 여럿이다 — 반도체, 자동차, 통신 장비, 방산, 가전, 게임, 금융 IT, 그리고 AI. 그 자리들에도 C++이 있는지, 있다면 왜 있는지를 알아야 오늘 배우는 것이 로봇 하나에 묶이지 않는다.

「C++은 로봇과 게임의 언어」로는 왜 부족한가

흔히 그렇게 말한다. 틀린 말은 아닌데 이유가 빠져 있다. 이유를 모르면 새 분야를 만났을 때 거기서 C++이 필요한지 판단할 수 없다. 이유는 앞 절에 이미 나왔다 — 예산이다. 200 밀리초는 라이다가 준 예산이었다. 다른 분야에는 다른 것이 예산을 준다. 그것이 무엇인지부터 세운다.

⚠️ 그렇다고 모두가 바닥을 만들지는 않는다

요즘 C/C++의 주 용도는 다른 언어가 가져다 쓰는 고성능 라이브러리를 만드는 것이고, 보통의 개발자는 그 라이브러리를 편한 언어에서 가져다 쓰기 때문에 C++을 직접 쓸 일이 없다는 말도 한다. 맞는 말이기도 하다. 모두가 파이썬 인터프리터나 언리얼 엔진이나 텐서플로를 만들 필요는 없다.

단, 전자정보공학과를 나와서 가게 되는 자리 — 자동차 제어기, 통신 장비, 반도체 펌웨어, 로봇, 방산 — 는 대체로 그 바닥 쪽이다. 그 자리에서는 예산이 있거나 남이 올라타거나 둘 중 하나이고, 둘 다인 경우도 많다.

그래서 C++을 배우면 남는 것은 셋이다

첫째는 위 표들의 자리에 갈 수 있는 자격이다. 둘째는 그 자리에 안 가더라도 남는 것 — 프로그래밍에 대한 이해다. C++은 메모리를 손으로 관리하는 낮은 자리부터 클래스처럼 높은 자리까지 한 언어 안에 다 있다. 그래서 C++을 한 번 지나가면 다른 언어가 무엇을 자동으로 해 주고 있었는지가 보인다. 파이썬에서 리스트를 함수에 넘기고 함수 안에서 바꿨을 때 밖의 리스트까지 바뀌는 이유가, C++을 알면 설명이 된다. 셋째는 ⑤절에서 본다 — 새로 나온 언어들이 C++의 무엇을 고치려 했는지는 C++을 알아야 보인다.

어느 분야로 가고 싶은지 정해졌다면, 그 분야의 언어를 물어보는 것도 맡길 수 있다. 단, 채용 공고를 근거로 달라고 해야 감으로 답하지 않는다.

나는 전자정보공학과 학생이고 졸업 후 (자동차 제어기 / 게임 클라이언트 / 통신 장비 / 반도체 펌웨어 / 금융 IT) 쪽으로 가고 싶어. 이 분야의 최근 채용 공고에서 요구하는 프로그래밍 언어를 빈도 순으로 정리해 주고, 각 언어가 그 분야에서 무엇을 하는 데 쓰이는지 한 줄씩 붙여 줘. 근거가 된 공고나 자료를 같이 알려 줘.

④ 그래서 파이썬을 쓰지 말라는 결론이 아니다 🟡 맡기되 검사

ROS 2는 파이썬을 정식으로 지원한다. C++용 라이브러리(rclcpp)와 파이썬용 라이브러리(rclpy)가 둘 다 공식으로 있고, 한 로봇 안에서 두 언어로 만든 프로그램이 서로 메시지를 주고받는다. 둘 중 하나를 고르는 문제가 아니라, 어디에 무엇을 쓰느냐의 문제다.

무엇을 먼저 볼지: 맨 오른쪽 열의 「시간 제약이 있나」가 갈림길이다.

⚠️ "파이썬은 느리다"를 잘못 외우면 생기는 오해

파이썬으로 큰 행렬을 곱하면 C++과 속도가 거의 같다. 계산을 파이썬이 하지 않고 안쪽이 C로 짜인 라이브러리(numpy 등)가 대신 하기 때문이다. "파이썬이 168배 느리다"가 아니라 "파이썬 문법으로 값을 하나씩 훑는 일이 168배 느리다"가 맞는 문장이다.

그런데 라이다 값에서 콘을 찾는 일은 행렬 곱 한 방으로 안 떨어진다. 점을 순서대로 훑으면서 "이 점이 앞 점과 가까운가"를 계속 물어야 한다. 하필 파이썬이 가장 불리한 모양의 계산이다.

언어를 고르는 일 자체를 에이전트에게 물어볼 수도 있다. 다만 시간 제약을 문장에 넣어야 쓸 만한 답이 온다.

라이다가 초당 5번 들어오고, 그 콜백 안에서 값 360개를 걸러 콘 위치를 계산해야 해. 한 번 처리가 200밀리초 안에 끝나야 해. C++과 파이썬 중 무엇이 맞는지 근거를 들어 알려 줘.

C++은 박사논문을 쓰다 생긴 언어다 🟢 읽을거리

이름이 농담인 언어 (15분 · 건너뛰어도 됩니다)

① 1970년대 말, 케임브리지의 박사과정 학생

덴마크 사람 비야네 스트롭스트룹(Bjarne Stroustrup)은 케임브리지에서 박사논문을 쓰고 있었다. 분산 시스템을 시뮬레이션해야 했는데, 쓰던 언어가 시뮬라(Simula)였다. 시뮬라는 클래스를 가진 최초의 언어였다. 큰 프로그램을 정리하기에 이만한 것이 없었다.

그런데 너무 느렸다. 논문에 필요한 시뮬레이션이 끝나지 않았다. 결국 그는 코드를 훨씬 낮은 수준의 언어로 처음부터 다시 짰다. 정리는 잘 되는데 느린 언어와, 빠른데 정리가 안 되는 언어 사이에서 한 번 데인 것이다.

② 그래서 둘 다 갖기로 했다

1979년 벨 연구소에 들어간 그는 "시뮬라의 정리 능력 + C의 속도"를 목표로 잡는다. 새 언어를 만들지 않고, 이미 있는 C에 클래스를 붙이는 쪽을 골랐다. 기존 C 코드가 그대로 돌아가야 사람들이 쓸 것이라고 봤기 때문이다. 이름도 그대로 "C with Classes"였다. 설명이지 이름이 아니다.

③ 여기가 재미있다 — 이름은 동료가 지었다

1983년, 릭 마시티(Rick Mascitti)라는 동료가 이름을 하나 제안한다. C에는 변수를 하나 늘리는 ++라는 연산자가 있다. 거기에 착안해 C++. "C를 하나 늘린 것"이라는 뜻이다.

언어의 이름 자체가 그 언어의 문법으로 된 농담이다. 농담으로 지은 이름이 40년 넘게 업계 표준 이름으로 남았다.

④ 그래서 지금 우리 손에 남은 것

C++이 복잡한 이유는 버리지 않고 더하기만 했기 때문이다.

옛날 C 코드가 그대로 돌아가야 했고, 옛날 C++ 코드도 그대로 돌아가야 했다. 그래서 새 문법이 들어와도 옛 문법이 안 없어진다. 같은 일을 하는 방법이 여러 개다. 포인터를 비우는 방법이 0·NULL·nullptr 셋이고, 값을 초기화하는 방법이 ()와 {}와 = 셋이다. 전부 지금도 컴파일된다.

그리고 바로 그 지점에서 AI가 평범한 쪽을 고른다. 방법이 여러 개인 언어에서 AI는 "인터넷에 가장 많은 것"을 고르는데, 인터넷에 가장 많은 C++ 코드는 최적화된 코드가 아니라 오래된 코드다. ⑥절이 그 이야기다. 그 전에 ⑤절에서, 이 복잡함을 감수하지 않고 아예 새로 시작한 언어들을 먼저 본다.

⑤ 숫자로 확인한다

  • 47년. 1979년에 시작한 언어다. 그동안 버려진 문법이 거의 없다.
  • 표준 개정 7번. C++98 · 03 · 11 · 14 · 17 · 20 · 23. 개정마다 문법이 늘었고 줄지 않았다.
  • 168배. 그 복잡함을 감수하고 얻는 것이 이 숫자다 — 오늘 잰 같은 계산에서 C++ 23.6 ms, 파이썬 3963.8 ms. 잰 곳: 컨테이너(우분투 24.04.4 LTS, g++ 13.3.0 -O2, CPython 3.12.3)

복잡함은 비용이고 속도는 이득이다. 이 강의는 그 거래를 받아들인 자리에 서 있다.

⑤ 새 언어들은 C++의 무엇을 고치려 했나 — Go와 Rust 🔴 사람이 한다

무엇을 알고 싶은 건가

C++이 그렇게 좋으면 왜 새 언어가 계속 나오나. Go나 Rust라는 이름을 들어 봤을 것이다. 어떤 회사는 C++을 버리고 Rust로 간다고 하고, 미국 정부까지 나서서 C/C++ 대신 다른 언어를 쓰라고 권고했다는 기사도 있다. 그러면 지금 C++을 배우는 것이 헛일이 되는 것 아닌가 하는 생각이 들 수 있다. 그 언어들이 C++의 무엇을 고치려 했는지를 알면 이 질문에 스스로 답할 수 있다.

「복잡하다」 말고 하나가 더 있다 — 메모리 안전성

바로 앞 이야기에서 C++의 비용은 복잡함이었다. 비용이 하나 더 있다. C++은 프로그램이 쓰는 메모리를 프로그래머가 직접 책임진다. 언제 빌리고 언제 돌려줄지, 값을 통째로 복사할지 자리만 알려 줄지를 전부 프로그래머가 정한다. 이것이 C++의 철학이다 — 프로그램 안에서 일어나는 모든 일을 프로그래머가 통제한다. 통제할 수 있으니 빠르고, 자원을 딱 필요한 만큼만 쓴다.

그 뒷면이 있다. 실수해도 아무도 잡아 주지 않는다. 이미 돌려준 메모리를 또 쓰거나, 360칸짜리 배열의 361번째 칸에 쓰거나 하는 실수가 컴파일도 되고 대개는 실행도 된다. 그러다 어느 날 엉뚱한 값을 읽거나, 죽거나, 남이 그 틈으로 들어온다. 이런 종류의 실수가 아예 일어날 수 없는 성질을 메모리 안전성이라 부른다.

얼마나 큰 문제인가. 마이크로소프트가 2019년에 자기 제품의 심각한 보안 결함을 세어 보니 약 70%가 메모리를 잘못 다뤄서 생긴 것이었다. 구글 크롬 팀이 2020년에 따로 세어 봤는데 역시 약 70%였다. 둘 다 C++로 된 수천만 줄짜리 프로그램이다. 이 숫자가 아래 두 언어가 태어난 배경이다.

Go — 구글이 「C++은 너무 크고 빌드가 느리다」에서 시작한 언어

🆕 이 절에서 처음 나오는 이름

Go
구글이 2009년에 공개한 언어다. 「고」라고 읽고, 검색할 때는 Golang이라고 쓰는 경우가 많다 (Go 두 글자로는 검색이 잘 안 되기 때문이다).
Rob Pike(롭 파이크) · Ken Thompson(켄 톰프슨) · Robert Griesemer(로버트 그리즈머)
셋 다 사람 이름이고 Go의 설계자다. 켄 톰프슨은 1970년대 벨 연구소에서 유닉스와 C 언어를 만든 사람 중 하나다. C의 아버지 격인 사람이 C++을 보고 다른 답을 낸 셈이다.

2000년대 후반 구글의 서버 프로그램은 대부분 C++이었고, 코드가 커지면서 세 가지가 힘들어졌다. 빌드가 너무 오래 걸렸고, 문법이 너무 많아 팀원마다 다른 C++을 썼고, CPU가 여러 개인 서버에서 동시에 여러 요청을 처리하는 코드를 짜기가 어려웠다. 설계자 롭 파이크의 회고에 따르면 2007년 어느 날 45분짜리 C++ 빌드를 기다리는 동안 새 언어 이야기가 시작됐다고 한다.

그래서 Go는 C++에서 덜어내는 쪽으로 갔다.

  • 문법을 확 줄였다. 예약어가 25개다. C++은 그 서너 배다. 같은 일을 하는 방법이 대체로 하나뿐이라 누가 짜도 비슷하게 생긴다.
  • 메모리는 언어가 치운다. 프로그래머가 돌려주는 것을 잊어도 실행 중에 언어가 알아서 회수한다. 이 장치를 가비지 컬렉터(garbage collector, GC)라고 한다. 파이썬과 자바도 같은 방식이다.
  • 동시 처리를 쉽게 만들었다. 요청 하나마다 가벼운 실행 단위(고루틴, goroutine)를 하나씩 띄우는 식으로 짠다.
  • 컴파일이 빠르고, 실행 파일 하나로 배포된다. 큰 프로그램도 수 초 안에 빌드된다.

그 대가가 하나 있다. GC가 언제 돌지 프로그래머가 정하지 못한다. GC가 도는 동안 프로그램은 잠깐 멈춘다. 대개는 밀리초 단위라 서버에서는 문제가 안 된다. 그런데 ②절의 예산이 있는 자리에서는 이야기가 달라진다 — 내 코드는 1 ms에 끝났는데 GC가 그 위에 10 ms를 얹는 일이 내가 모르는 순간에 생긴다.

실제 사례가 있다. 채팅 서비스 디스코드(Discord)는 Go로 짠 서버 하나에서 약 2분마다 응답이 튀는 현상을 겪었다. 코드에는 문제가 없었다. GC가 2분마다 돌았던 것이다. 2020년에 그 서비스를 Rust로 다시 쓰자 튀는 현상이 사라졌다고 회사가 직접 밝혔다. ②절의 표현으로 하면, GC는 예산을 내 허락 없이 쓰는 동거인이다.

그래서 Go는 C++을 밀어냈다기보다 서버 쪽의 C++·자바·파이썬 자리에 들어갔다. 도커(Docker)와 쿠버네티스(Kubernetes) 같은 클라우드의 바닥 도구가 대부분 Go이고, 국내외 IT 회사의 서버 코드에도 많이 들어가 있다. 게임 엔진·자동차 제어기·로봇 콜백처럼 예산이 촘촘한 자리는 처음부터 겨냥하지 않았다.

Rust — 모질라가 「GC 없이 메모리 안전」을 목표로 만든 언어

🆕 이 절에서 처음 나오는 이름

Rust
「러스트」라고 읽는다. 2006년 그레이든 호어(Graydon Hoare, 사람 이름)가 개인 프로젝트로 시작했고, 2009년부터 모질라가 후원해 2015년에 1.0이 나왔다.
Mozilla(모질라)
파이어폭스(Firefox) 브라우저를 만드는 비영리 재단이다. 파이어폭스는 C++로 된 수백만 줄짜리 프로그램이고, 보안 결함의 대부분이 위에서 말한 메모리 문제였다.

브라우저는 Go의 길로 갈 수 없었다. GC를 넣으면 화면이 멈칫거리고 메모리를 더 먹는다. 그래서 Rust의 목표는 처음부터 「C++만큼 빠르면서, 메모리 실수는 컴파일러가 잡는다」였다. 실행 중에 검사하면 느려지니 컴파일할 때 잡기로 한 것이다.

방법은 규칙 세 줄이다.

  • 값마다 주인이 하나다. 주인이 사라지면 그 값도 같이 사라진다. 돌려주는 것을 잊을 수가 없다.
  • 남에게 빌려 줄 수는 있다. 단, 읽기만 하는 쪽은 여럿이어도 되지만 고치는 쪽이 있으면 그 순간에는 그 하나뿐이어야 한다.
  • 이 규칙에 어긋나는 코드는 컴파일이 안 된다. 그래서 실행 중에는 검사 비용이 0이다.

이 규칙을 소유권(ownership)이라고 부른다. 그 결과 Rust는 C++과 비슷한 속도를 내면서 「이미 돌려준 메모리를 또 쓰는」 종류의 실수가 문법상 불가능해진다. (하드웨어를 직접 만지는 자리처럼 컴파일러가 판단할 수 없는 곳은 unsafe라고 표시하고 사람이 책임진다.)

대가는 두 가지다.

  • 배우기 어렵다. 처음 몇 주는 「컴파일러와 싸운다」는 말이 있다. 여태 되던 코드를 컴파일러가 거부하는데, 왜 거부하는지 이해하는 데 시간이 든다.
  • 이미 있는 C++ 라이브러리를 그대로 못 쓴다. 사이에 연결 계층을 만들어야 하고, 그 계층은 다시 unsafe가 된다. OpenCV·PCL·언리얼 엔진 같은 것을 Rust에서 쓰려면 이 문제에 걸린다.

그런데도 Rust는 「새로 짜는 시스템 코드」 자리에 빠르게 들어가고 있다. 리눅스 커널이 2022년(6.1판)부터 Rust 코드를 받기 시작했고, 마이크로소프트도 2023년부터 윈도우 커널 일부를 Rust로 다시 쓰고 있다. 구글은 안드로이드의 새 코드를 Rust 등으로 쓰기 시작한 뒤 메모리 안전 결함의 비율이 2019년 76%에서 2024년 24%로 줄었다고 밝혔다. 2024년 2월에는 미국 백악관(ONCD)이 새 소프트웨어를 메모리 안전 언어로 쓰라고 권고하는 보고서를 냈다.

여러분에게 더 가까운 예도 있다. 요즘 파이썬 도구들 — 코드 검사기 ruff, 패키지 설치기 uv, 데이터프레임 polars — 이 Rust로 쓰여 있다. ③절에서 「남이 올라타는 바닥은 C++」이라고 했는데, 그 바닥을 새로 깔 때 Rust를 고르는 곳이 늘고 있다는 뜻이다.

해석: 셋이 다른 것은 결국 한 줄 — 메모리를 누가 책임지나다. C++은 프로그래머에게, Go는 실행 중의 GC에게, Rust는 컴파일러에게 맡겼다. 각자 대가가 있고, 그 대가를 감당할 수 있는 자리가 다르다. Go의 대가(GC 멈춤)는 예산이 있는 자리에서 못 치르고, Rust의 대가(기존 라이브러리)는 20년치 C++ 위에 선 분야에서 못 치른다. 그 두 자리가 겹치는 곳이 로봇·게임·자동차이고, 그래서 거기는 아직 C++이다.

그러면 로봇은 언제 Rust로 가나

언어의 좋고 나쁨이 아니라 라이브러리의 문제다. 로봇에 필요한 것 — 센서 드라이버, 좌표 변환, 지도 작성, 길찾기, 시뮬레이터 — 이 이미 전부 C++로 쓰여 있다. ROS 2를 Rust에서 쓰는 시도(ros2_rust)가 있지만 아직 공식 지원이 아니고, 그 위에 얹힌 Nav2·MoveIt 같은 것은 여전히 C++이다. 게임도 같다 — 언리얼 엔진이 C++이니 그 위의 게임도 C++이다. 자동차도 AUTOSAR가 C++14를 기준으로 정해 두었다. 새 언어가 온다면 새 코드부터 오고, 기존의 것은 오래 남는다. 리눅스 커널이 지금 그렇게 가고 있다.

C++을 알면 이 둘이 보인다

반대로 읽으면 이렇다. Rust의 소유권 규칙은 C++11이 들여온 「이동」과 「스마트 포인터」를 컴파일러가 강제하는 것에 가깝다. 11회(복사와 이동)와 12회(스마트 포인터)를 지나면 Rust 문서의 첫 장이 읽힌다. Go의 GC는 파이썬이 하는 것과 같은 방식이다. C++에서 메모리를 한 번 손으로 다뤄 보면 GC가 무엇을 대신해 주고 무엇을 가져가는지가 보인다. C++이 첫 언어로 나쁘지 않은 이유가 이것이다. 다른 언어가 자동으로 해 주는 것을 한 번은 손으로 해 본 사람이 그 자동화를 판단할 수 있다.

이 절의 「메모리 실수」가 무엇인지는 코드를 받았을 때 물어보면 된다. 컴파일러는 안 잡아 주지만 에이전트는 대체로 짚어 준다.

이 C++ 코드에서 다 쓴 메모리를 다시 쓰거나, 배열 범위를 넘어 읽고 쓰거나, 돌려주는 것을 잊는 자리가 있는지 봐 줘. 있으면 어느 줄이 왜 위험한지, 그리고 Rust 컴파일러라면 무엇이라고 거부했을지도 한 줄씩 붙여 줘.

⑥ AI는 틀린 코드가 아니라 둔한 코드를 준다 🔴 사람이 한다

여기까지는 "왜 C++인가"였다. 이제 "왜 사람이 C++을 알아야 하는가"다. AI가 C++ 코드를 잘 짜 준다면 사람이 배울 이유는 크게 줄어든다. 그래서 AI가 짠 C++ 코드가 사람이 짠 것과 어디가 다른지를 본다.

근거로 삼는 것은 실제 회사의 C++ 코드 약 1천만 줄을 1년간 추적한 연구다. 같은 회사, 같은 코드베이스에서 AI가 만든 코드와 사람이 만든 코드를 나눠 세었다.

무엇을 먼저 볼지: 맨 아래 줄부터 읽는다. 나머지 세 줄의 뜻이 거기서 정해진다.

왜 하필 C++에서 이런 일이 생기나

앞의 이야기와 이어진다. C++은 같은 일을 하는 방법이 여러 개다. 그리고 AI는 인터넷에 있는 코드를 재현한다. 인터넷에 있는 C++ 코드는 최적화된 코드보다 옛날 교과서 코드가 훨씬 많다. 그래서 "맞기는 한데 15년 전 방식"인 코드가 나온다. 파이썬에는 이 문제가 훨씬 덜하다. 방법이 대체로 하나뿐이기 때문이다.

그래서 사람이 하는 일은 이것이다

이 코드에서 불필요한 복사가 일어나는 자리가 있으면 짚어 줘. 값으로 받는 함수 인자와, 통째로 대입하는 자리를 특히 봐 줘.

이 문장을 쓰려면 "복사가 비싸다"는 것을 알아야 한다. 그것이 사람이 C++을 아는 이유다. 코드를 짜기 위해서가 아니라 무엇을 요구할지 알기 위해서다.

왜 -O2 하나로 6배가 나나

-O2를 붙이지 않으면 컴파일러는 소스에 적힌 그대로 기계어를 만든다. 값을 읽고, 계산하고, 다시 메모리에 넣고, 다음 줄에서 또 읽는다.

-O2를 붙이면 컴파일러가 결과가 같아지는 선에서 코드를 다시 짠다. 반복해서 읽는 값은 레지스터에 붙잡아 두고, 매번 같은 결과가 나오는 계산은 루프 밖으로 빼고, 짧은 함수는 부르는 자리에 통째로 펼쳐 넣는다.

우리가 잰 값은 146.0 ms → 23.6 ms였다. 같은 소스, 같은 컴퓨터, 옵션 세 글자 차이다. "C++이 파이썬보다 빠르다"는 말이 성립하려면 이 세 글자가 붙어 있어야 한다는 뜻이기도 하다. 잰 곳: 컨테이너(우분투 24.04.4 LTS, g++ 13.3.0)

C++의 단점 네 가지 — 알고 시작하는 편이 낫다
  1. 어렵다. 문법을 전부 아는 사람이 없다고 할 정도로 크다. 이 강의가 문법을 다 가르치지 않는 이유가 이것이다.
  2. 빌드 시간이 있다. 파이썬은 저장하고 바로 돌리지만 C++은 매번 컴파일을 기다린다. 헤더를 많이 포함할수록 길어진다.
  3. 파일이 두 개씩이다. 클래스 하나에 헤더(.hpp)와 소스(.cpp)가 따로 있고 둘을 맞춰 줘야 한다. 8회에서 다룬다.
  4. 남의 라이브러리를 가져오기 불편하다. 파이썬은 pip 한 줄이면 되는데 C++은 직접 받아 빌드해야 하는 경우가 많다. 9회에서 다룬다.

2·3·4번은 이 강의에서 실제로 겪게 된다. 겪은 직후에 해결책을 준다. 1번은 겪지 않게 하려고 이 강의가 존재한다.
